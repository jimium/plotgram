# 16 · 大图性能、门控降级与 WASM 工程

> 布局是**超线性**算法的集合，规模一上来就会有"某一相突然吃掉 90% 时间"的现象。
> 本篇给出：各相的复杂度预算、已知热点与优化手段、规模门控与降级策略、并行化的可行边界、
> 以及 WASM 环境的具体限制（本项目的主要交付环境）。

---

## 1. 复杂度预算表

设 $V$ 节点、$E$ 边、$L$ 层、$W$ 最大层宽、$D$ = dummy 节点数。
**关键事实：分层布局的真实规模是 $V + D$，而 $D$ 可以是 $V$ 的数倍**（长边多时）。

| 相 | 理论复杂度 | 实测占比（$V\approx$ 数千的 DAG） | 主要热点 |
|---|---|---|---|
| 解析 / 建模 | $O(\text{src})$ | < 2% | 字符串分配 |
| 文本度量 | $O(\text{chars})$ | **5–25%** | 字体 shaping（CJK 尤重） |
| P1 去环 | $O(V+E)$ | < 1% | — |
| P2 分层（NS） | 实践近线性，最坏无强多项式界 | 3–15% | `enter_edge` 搜索 |
| dummy 化 | $O(D)$ | 2% | 内存分配 |
| **P3 定序** | $O(\text{iter}\cdot E\log W)$ | **30–60%** | 交叉计数 + transpose |
| P4 坐标（BK） | $O(V+D+E)$ | 5% | — |
| **边路由** | $O(E \cdot \text{search})$，OVG 最坏 $O(V^2)$ | **20–50%** | A\* 搜索、可见图构造 |
| nudging（VPSC） | $O(C\log C)$ 每维 | 3–8% | 约束构造 |
| 标签 | $O(n\log n)$ ~ $O(n^2)$ | 2–10% | 冲突检测 |
| 落笔 + SVG | $O(\text{output})$ | 5–15% | 字符串拼接 |

**结论：优化只有两个真目标 —— P3 定序与边路由。** 其它相的优化基本是浪费（除文本度量在 CJK 场景）。

---

## 2. P3 定序的优化

### 2.1 必做（数量级级别）
1. **Barth–Jünger–Mutzel 交叉计数**（$O(E\log V)$ 替代 $O(E^2)$）——见 14 篇 §4.3。
2. **transpose 的局部判定**：交换相邻两点的交叉数变化只依赖这两点的邻接，$O(\deg_u+\deg_v)$，不要全层重算。
3. **提前收敛**：连续 N 轮无改进就停；交叉数为 0 立即停。dot 默认 24 轮，多数图 4–8 轮就收敛。
4. **长边链抽象**：跨 $k$ 层的边产生 $k-1$ 个 dummy，它们的序应作为**一个整体**处理（块级 sifting，Bachmaier 2010），
   否则宽层上 dummy 数量主导一切。哪怕不做块级 sifting，也应给 dummy 设置更高边权（1/2/8 中的 8）让它们自然对齐。

### 2.2 可选
- **sifting** 替代/补充 transpose：质量更好但更慢，建议只在 $V$ 小于阈值或"质量模式"下开。
- **只在变化的层上迭代**（增量场景）：维护 dirty 层集合。
- **分块并行**：sweep 本质是串行（第 $i$ 层依赖 $i-1$ 层），但**同一层内的 transpose 可以按不相交对并行** —— 收益有限，不建议先做。

### 2.3 内存
dummy 节点用**紧凑数组**（SoA）而非每个一个堆对象：
```rust
struct LayerOrder { nodes: Vec<NodeRef>, pos: Vec<u32> }   // pos 是 nodes 的逆映射
```
`pos` 逆映射数组是必需的（交叉计数与 transpose 都要 $O(1)$ 查位置）。

## 3. 边路由的优化

### 3.1 选对图（最大收益）
- **规则布局（分层结果）用通道图**：节点数级别的顶点，比 OVG 小一到两个数量级；
- **只在自由布局 / 拖动后用 OVG**；
- OVG 构造用扫描线 $O(n\log n + |E_{vis}|)$，不要 $O(n^2)$ 双循环。

### 3.2 A\* 的加速
1. **状态含方向**（正确性要求，见 03 篇）→ 状态数 ×4，必须用高效容器：
   `dist: Vec<f64>` 索引为 `vertex*4 + dir`，而不是 HashMap。
2. **可采纳启发式**：$h = |dx| + |dy| + \lambda_{bend}\cdot b_{min}$，其中 $b_{min}$ 是"从当前方向到达目标至少需要的转弯数"（0/1/2，查表）。
   这个 $b_{min}$ 项让搜索显著收窄，且仍可采纳。
3. **双向搜索**：长距离边收益明显（约 2×）。
4. **共享数据结构**：所有边复用一个 `dist`/`visited` 缓冲，用**时间戳标记**避免每次清零：
   ```rust
   if stamp[i] != cur_stamp { dist[i] = INF; stamp[i] = cur_stamp; }
   ```
5. **批量排序**：按"长度降序"路由（长边先占好走廊），短边后路由更容易绕开 —— 也是质量优化。

### 3.3 nudging 的规模控制
nudging 的约束数与"同走廊段对数"成平方关系。对策：
- 只在**同一走廊**内构造约束（走廊分组后各自求解，天然并行）；
- 每个走廊内先按区间着色分 track，**只对同 track 的相邻段**加约束；
- 走廊内段数超阈值 → 降级为均匀分布（放弃最优 nudging，但仍无重合）。

## 4. 规模门控与降级（Graceful Degradation）

**核心思想**：不承诺"任意规模都最优"，而是承诺"任意规模都在有限时间内给出可用结果，并如实报告降级"。

### 4.1 门控设计
```rust
struct Budget {
    max_nodes_full_quality: usize,   // 例：2_000
    max_edges_orthogonal: usize,     // 例：5_000
    max_total_ms: u64,               // 软预算
}
```
降级阶梯（从轻到重）：

| 级别 | 动作 | 观感损失 |
|---|---|---|
| L0 | 全质量 | — |
| L1 | 关闭 sifting，降低 sweep 轮数（24→8） | 交叉略增 |
| L2 | 关闭精确 nudging，改均匀分布 | 边间距不最优 |
| L3 | 边路由改"直角三段折线"（不搜索） | 可能穿越空隙 |
| L4 | 边改直线（无正交） | 风格改变 |
| L5 | 关闭标签避让，只放不重叠的标签，其余隐藏 | 信息缺失（需 UI 提示） |
| L6 | 边捆绑 / 聚合（把同源同宿的边聚成一束） | 抽象化 |
| L7 | 节点聚合（按组折叠） | 需交互展开 |

**纪律**：
- 降级必须**在诊断输出中显式记录**（哪一级、被哪个阈值触发），否则用户会以为"算法就这水平"；
- 降级阈值是**参数**，走 profile（20 篇），不写死；
- 每个降级级别都要有基准 case，避免降级路径本身腐化（降级路径最容易 bit-rot）。

### 4.2 时间预算的实现
不要在算法内部到处查时钟（WASM 下时钟调用有成本，且违反 §6 的纪律）。做法：
- 在**相边界**检查预算（每相开始/结束）；
- 迭代型相在**每轮迭代**结束检查（轮次是天然的检查点）；
- 通过项目的 perf 抽象取时间，不用裸 `Instant`。

## 5. 并行化的可行边界

Rust 下用 rayon 很方便，但布局的可并行点比想象的少：

| 可并行 | 说明 |
|---|---|
| ✅ **连通分量分别布局** | 天然独立，收益随分量数线性。最值钱的并行点。 |
| ✅ **各走廊的 nudging** | 走廊间无约束（前提：走廊划分正确）。 |
| ✅ **边路由**（只读走廊图 + 后置冲突消解） | 需要"先并行搜路径、再串行分配 track"的两段式。 |
| ✅ **文本度量** | 纯函数，按标签并行。CJK 场景收益大。 |
| ✅ **度量/指标计算** | 基准脚本里并行跑 case。 |
| ⚠️ 力导向的斥力计算 | 可并行，但 Barnes–Hut 树构造是串行瓶颈。 |
| ❌ P3 sweep | 层间严格串行依赖。 |
| ❌ Network Simplex | 换基串行。 |
| ❌ VPSC | block merge 串行（可分维度并行 x/y，但交替算法要求顺序）。 |

**确定性要求下的并行纪律**：
- 并行只允许在"结果与顺序无关"的地方；
- 归约必须**先按 id 排序再合并**（不能靠 rayon 的 reduce 顺序）；
- 并行浮点求和顺序不确定 → 力导向的并行斥力累加会破坏确定性。对策：分块固定划分 + 块内固定顺序 + 块间按块号有序合并。
- **WASM 默认单线程**（见 §6），所以并行只对 CLI / 服务端有效 → 优先级低于算法优化。

## 6. WASM 工程约束（本项目的主战场）

### 6.1 时间
- `std::time::Instant` 在 wasm32-unknown-unknown 上**panic 或返回无意义值**；
- AGENTS.md 已定纪律：会编到 WASM 的布局代码禁止裸 `Instant/SystemTime`，统一走项目 perf 抽象。
- perf 抽象的形态建议：
  ```rust
  // 原生：Instant；wasm：performance.now()；或 no-op 特性关闭
  pub fn now_ms() -> f64;
  ```
  并让"计时"成为可编译期关闭的特性（`--no-default-features` 下变 no-op），避免为计时付出跨 FFI 成本。

### 6.2 线程
- 需要 `SharedArrayBuffer` + COOP/COEP 头 + `wasm-bindgen-rayon` 才能多线程；
- 站点部署要改 nginx 头（本项目 `deploy/nginx/`），且 iframe 嵌入场景常不可用；
- **结论：把单线程性能当作唯一目标**，多线程当作可选加速。

### 6.3 二进制体积
布局引擎进 WASM 后体积敏感（首屏加载）：
- `opt-level = "z"` 或 `"s"`，`lto = true`，`codegen-units = 1`，`panic = "abort"`；
- `wasm-opt -Oz`；
- 避免拉入重依赖：**正则、通用 QP 求解器、多边形布尔库、完整字体栈**是常见体积杀手；
- 字体：只嵌入子集，或让宿主页面提供度量（但会带来"布局依赖 DOM"的耦合，不推荐）；
- 用 `twiggy` 定位体积。

### 6.4 内存
- WASM 线性内存增长不可收缩 → 峰值内存决定一切。避免"一次性构造全量 OVG"这类峰值结构；
- 建议为大结构提供 arena/复用（dummy 节点、A\* 缓冲、约束数组）；
- `Vec::with_capacity` 预留（节点数已知），减少 realloc 拷贝。

### 6.5 跨 FFI 边界
- 一次调用传全图 JSON 是最省心的做法，但序列化可能占总时间 20%+；
  优化：输出用紧凑二进制或字符串化 SVG（只跨一次边界），**不要每个节点一次调用**。
- 不要在布局循环里回调 JS（度量文本尤其忌讳）→ 文本度量必须在 Rust 侧完成（这也是选择 ttf-parser/rustybuzz 的理由）。

### 6.6 数值一致性
- WASM 的 f64 遵循 IEEE754，与原生一致；但 **`f32` 的 SIMD 与数学库（sin/cos/exp）实现可能不同**；
- 数学库差异会让快照测试在原生与 WASM 下不一致 → 对策：布局关键路径避免超越函数，或统一用自实现的多项式近似，或量化后再断言（15 篇 §7.2）。

## 7. 性能测量纪律

- 只用 `--release` 测（AGENTS.md）；debug 下的 Rust 慢 10–50×，结论完全无效；
- **报 p50 / p95**，不报均值；
- **分相计时**（09 篇诊断输出）：没有分相数据的性能讨论都是猜；
- 固定机器、固定线程数，把绝对值当趋势；
- WASM 与原生分别测，比值本身是有用指标（正常 1.5–3×；若某相 >5× 说明该相踩了 WASM 的坑）；
- 火焰图：原生用 `cargo flamegraph` / `samply`；WASM 用浏览器 Performance 面板（需 `debug = true` 保留符号）。

## 8. 优化决策流程（避免瞎优化）

```
1. 先有基准集与分相计时（11 篇）
2. 找到占比 > 20% 的相 —— 只优化它
3. 判断是"算法复杂度问题"还是"实现常数问题"
     复杂度问题 → 换算法（如 O(E²) 交叉计数 → BJM）
     常数问题   → 数据结构（HashMap → Vec 索引）、减少分配、缓存友好
4. 改一件事，重跑基准，记录 delta
5. 若收益 < 5%，回滚（复杂度不值得）
```

**常见的常数级优化（收益大、风险低）**：
- `HashMap<NodeId, T>` → `Vec<T>` 按稠密索引（NodeId 需连续化）——通常 2–5×，且顺便解决确定性问题；
- 避免每轮迭代重新分配 Vec（复用缓冲 + `clear()`）；
- 结构体拆成 SoA（提高 cache 命中）——只对最热的循环做；
- 字符串：SVG 输出用一个 `String` 预留容量 + `write!`，不要 `format!` 拼接；
- 排序键预计算（避免比较器里做浮点运算）。

**反模式**：在没有分相数据时"顺手优化"解析器/落笔层 —— 它们从来不是瓶颈。

## 9. 给本项目的建议

1. **先把分相计时与规模指标（V/E/D、各相耗时、峰值内存估算）打进诊断输出**，进基准报告（11 篇）。
2. **P3 优先**：确认已用 BJM 计数 + 局部 transpose 判定 + 提前收敛 + dummy 边权；这是最大头。
3. **路由第二**：分层图确认走的是通道图而非 OVG；A\* 用数组 + 时间戳，不用 HashMap。
4. **门控降级表落地**（§4.1 的 L0–L7），阈值进 profile，触发写诊断。
5. **NodeId 连续化 + Vec 索引**替换热点里的 HashMap —— 同时满足性能与确定性两条要求。
6. **WASM 侧**：perf 抽象、体积预算（设一个 KB 上限并在 CI 中检查）、避免 JS 回调、量化输出。
