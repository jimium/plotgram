16 · 大图性能、门控降级与 WASM 工程（Large Graph Performance & WASM）

布局是超线性算法的集合，规模一上来就会有「某一相突然吃掉 90% 时间」的现象。本篇给出各相复杂度预算、已知热点与优化手段、规模门控与降级策略、并行化的可行边界，以及 WASM 环境的具体限制（本项目的主要交付环境）。

2P3 定序的优化

2.1 必做（数量级级别）

  1. Barth–Jünger–Mutzel 交叉计数（ 替代 ）——见 14 篇 §4.3。
  2. transpose 的局部判定：交换相邻两点的交叉数变化只依赖这两点的邻接，，不要全层重算。
  3. 提前收敛：连续 N 轮无改进就停；交叉数为 0 立即停。dot 默认 24 轮，多数图 4–8 轮就收敛。
  4. 长边链抽象：跨 层的边产生 个 dummy，它们的序应作为一个整体处理（块级 sifting，Bachmaier 2010），否则宽层上 dummy 数量主导一切。哪怕不做块级 sifting，也应给 dummy 设置更高边权（1/2/8 中的 8）让它们自然对齐。

2.2 可选

  • sifting 替代/补充 transpose：质量更好但更慢，建议只在 小于阈值或「质量模式」下开。
  • 只在变化的层上迭代（增量场景）：维护 dirty 层集合。
  • 分块并行：sweep 本质是串行（第 层依赖 层），但同一层内的 transpose 可以按不相交对并行 —— 收益有限，不建议先做。

2.3 内存

dummy 节点用紧凑数组（SoA）而非每个一个堆对象：

3边路由的优化

3.1 选对图（最大收益）

  • 规则布局（分层结果）用通道图：节点数级别的顶点，比 OVG 小一到两个数量级；
  • 只在自由布局 / 拖动后用 OVG；
  • OVG 构造用扫描线 ，不要 双循环。

3.2 A* 的加速

  1. 状态含方向（正确性要求，见 03 篇）→ 状态数 ×4，必须用高效容器：dist: Vec<f64> 索引为 vertex*4 + dir，而不是 HashMap。
  2. 可采纳启发式：，其中 是「从当前方向到达目标至少需要的转弯数」（0/1/2，查表）。这个 项让搜索显著收窄，且仍可采纳。
  3. 双向搜索：长距离边收益明显（约 2×）。
  4. 共享数据结构：所有边复用一个 dist/visited 缓冲，用时间戳标记避免每次清零：
    rust 
    if stamp[i] != cur_stamp { dist[i] = INF; stamp[i] = cur_stamp; }
  5. 批量排序：按「长度降序」路由（长边先占好走廊），短边后路由更容易绕开 —— 也是质量优化。

3.3 nudging 的规模控制

nudging 的约束数与「同走廊段对数」成平方关系。对策：

  • 只在同一走廊内构造约束（走廊分组后各自求解，天然并行）；
  • 每个走廊内先按区间着色分 track，只对同 track 的相邻段加约束；
  • 走廊内段数超阈值 → 降级为均匀分布（放弃最优 nudging，但仍无重合）。

4规模门控与降级（Graceful Degradation）

核心思想：不承诺「任意规模都最优」，而是承诺「任意规模都在有限时间内给出可用结果，并如实报告降级」。

4.1 门控设计

rust 
struct Budget {
    max_nodes_full_quality: usize,   // 例：2_000
    max_edges_orthogonal: usize,     // 例：5_000
    max_total_ms: u64,               // 软预算
}

降级阶梯（从轻到重）：

级别动作观感损失
L0全质量—
L1关闭 sifting，降低 sweep 轮数（24→8）交叉略增
L2关闭精确 nudging，改均匀分布边间距不最优
L3边路由改「直角三段折线」（不搜索）可能穿越空隙
L4边改直线（无正交）风格改变
L5关闭标签避让，只放不重叠的标签，其余隐藏信息缺失（需 UI 提示）
L6边捆绑 / 聚合（把同源同宿的边聚成一束）抽象化
L7节点聚合（按组折叠）需交互展开
⚠降级纪律（容易腐化的部分）
  • 降级必须在诊断输出中显式记录（哪一级、被哪个阈值触发），否则用户会以为「算法就这水平」；
  • 降级阈值是参数，走 profile（20 篇），不写死；
  • 每个降级级别都要有基准 case，避免降级路径本身腐化（降级路径最容易 bit-rot）。

4.2 时间预算的实现

不要在算法内部到处查时钟（WASM 下时钟调用有成本，且违反 §6 的纪律）。做法：

  • 在相边界检查预算（每相开始/结束）；
  • 迭代型相在每轮迭代结束检查（轮次是天然的检查点）；
  • 通过项目的 perf 抽象取时间，不用裸 Instant。

5并行化的可行边界

Rust 下用 rayon 很方便，但布局的可并行点比想象的少：

可并行说明
✅ 连通分量分别布局天然独立，收益随分量数线性。最值钱的并行点。
✅ 各走廊的 nudging走廊间无约束（前提：走廊划分正确）。
✅ 边路由（只读走廊图 + 后置冲突消解）需要「先并行搜路径、再串行分配 track」的两段式。
✅ 文本度量纯函数，按标签并行。CJK 场景收益大。
✅ 度量/指标计算基准脚本里并行跑 case。
⚠️ 力导向的斥力计算可并行，但 Barnes–Hut 树构造是串行瓶颈。
❌ P3 sweep层间严格串行依赖。
❌ Network Simplex换基串行。
❌ VPSCblock merge 串行（可分维度并行 x/y，但交替算法要求顺序）。
⚠确定性要求下的并行纪律
  • 并行只允许在「结果与顺序无关」的地方；
  • 归约必须先按 id 排序再合并（不能靠 rayon 的 reduce 顺序）；
  • 并行浮点求和顺序不确定 → 力导向的并行斥力累加会破坏确定性。对策：分块固定划分 + 块内固定顺序 + 块间按块号有序合并。
  • WASM 默认单线程（见 §6），所以并行只对 CLI / 服务端有效 → 优先级低于算法优化。

6WASM 工程约束（本项目的主战场）

6.1 时间

  • std::time::Instant 在 wasm32-unknown-unknown 上panic 或返回无意义值；
  • AGENTS.md 已定纪律：会编到 WASM 的布局代码禁止裸 Instant/SystemTime，统一走项目 perf 抽象。
  • perf 抽象的形态建议：
    rust 
    // 原生：Instant；wasm：performance.now()；或 no-op 特性关闭
pub fn now_ms() -> f64;
    并让「计时」成为可编译期关闭的特性（--no-default-features 下变 no-op），避免为计时付出跨 FFI 成本。
⚠AGENTS.md 硬约束：WASM 计时纪律

会编到 WASM 的布局 / 引擎代码内禁止裸 std::time::{Instant, SystemTime}；统一走项目的 perf 抽象（勿钉死 v1 路径）。原因：Instant 在 wasm32-unknown-unknown 上会 panic 或返回无意义值，且每次跨 FFI 取时钟都有成本。落地形态：now_ms() -> f64，并允许编译期关闭以省 FFI 开销。

6.2 线程

  • 需要 SharedArrayBuffer + COOP/COEP 头 + wasm-bindgen-rayon 才能多线程；
  • 站点部署要改 nginx 头（本项目 deploy/nginx/），且 iframe 嵌入场景常不可用；
  • 结论：把单线程性能当作唯一目标，多线程当作可选加速。

6.3 二进制体积

布局引擎进 WASM 后体积敏感（首屏加载）：

  • opt-level = "z" 或 "s"，lto = true，codegen-units = 1，panic = "abort"；
  • wasm-opt -Oz；
  • 避免拉入重依赖：正则、通用 QP 求解器、多边形布尔库、完整字体栈是常见体积杀手；
  • 字体：只嵌入子集，或让宿主页面提供度量（但会带来「布局依赖 DOM」的耦合，不推荐）；
  • 用 twiggy 定位体积。

6.4 内存

  • WASM 线性内存增长不可收缩 → 峰值内存决定一切。避免「一次性构造全量 OVG」这类峰值结构；
  • 建议为大结构提供 arena/复用（dummy 节点、A* 缓冲、约束数组）；
  • Vec::with_capacity 预留（节点数已知），减少 realloc 拷贝。

6.5 跨 FFI 边界

  • 一次调用传全图 JSON 是最省心的做法，但序列化可能占总时间 20%+；优化：输出用紧凑二进制或字符串化 SVG（只跨一次边界），不要每个节点一次调用。
  • 不要在布局循环里回调 JS（度量文本尤其忌讳）→ 文本度量必须在 Rust 侧完成（这也是选择 ttf-parser/rustybuzz 的理由）。

6.6 数值一致性

  • WASM 的 f64 遵循 IEEE754，与原生一致；但 f32 的 SIMD 与数学库（sin/cos/exp）实现可能不同；
  • 数学库差异会让快照测试在原生与 WASM 下不一致 → 对策：布局关键路径避免超越函数，或统一用自实现的多项式近似，或量化后再断言（15 篇 §7.2）。

7性能测量纪律

  • 只用 --release 测（AGENTS.md）；debug 下的 Rust 慢 10–50×，结论完全无效；
  • 报 p50 / p95，不报均值；
  • 分相计时（09 篇诊断输出）：没有分相数据的性能讨论都是猜；
  • 固定机器、固定线程数，把绝对值当趋势；
  • WASM 与原生分别测，比值本身是有用指标（正常 1.5–3×；若某相 >5× 说明该相踩了 WASM 的坑）；
  • 火焰图：原生用 cargo flamegraph / samply；WASM 用浏览器 Performance 面板（需 debug = true 保留符号）。

8优化决策流程（避免瞎优化）

pseudo 
1. 先有基准集与分相计时（11 篇）
2. 找到占比 > 20% 的相 —— 只优化它
3. 判断是"算法复杂度问题"还是"实现常数问题"
     复杂度问题 → 换算法（如 O(E²) 交叉计数 → BJM）
     常数问题   → 数据结构（HashMap → Vec 索引）、减少分配、缓存友好
4. 改一件事，重跑基准，记录 delta
5. 若收益 < 5%，回滚（复杂度不值得）

常见的常数级优化（收益大、风险低）：

  • HashMap<NodeId, T> → Vec<T> 按稠密索引（NodeId 需连续化）——通常 2–5×，且顺便解决确定性问题；
  • 避免每轮迭代重新分配 Vec（复用缓冲 + clear()）；
  • 结构体拆成 SoA（提高 cache 命中）——只对最热的循环做；
  • 字符串：SVG 输出一个 String 预留容量 + write!，不要 format! 拼接；
  • 排序键预计算（避免比较器里做浮点运算）。
⚠反模式

在没有分相数据时「顺手优化」解析器/落笔层 —— 它们从来不是瓶颈。§1 的预算表已经写明：解析 <2%、落笔 5–15%，而 P3 + 路由合计 50–90%。优化非热点相 = 给确定性测试添麻烦却不收益。

9给本项目的建议

  1. 先把分相计时与规模指标（V/E/D、各相耗时、峰值内存估算）打进诊断输出，进基准报告（11 篇）。
  2. P3 优先：确认已用 BJM 计数 + 局部 transpose 判定 + 提前收敛 + dummy 边权；这是最大头。
  3. 路由第二：分层图确认走的是通道图而非 OVG；A* 用数组 + 时间戳，不用 HashMap。
  4. 门控降级表落地（§4.1 的 L0–L7），阈值进 profile，触发写诊断。
  5. NodeId 连续化 + Vec 索引替换热点里的 HashMap —— 同时满足性能与确定性两条要求。
  6. WASM 侧：perf 抽象、体积预算（设一个 KB 上限并在 CI 中检查）、避免 JS 回调、量化输出。
✓一句话收敛

大图性能的真问题不是「让算法更快」，而是「把预算花在 P3 与路由两相，其余相用门控降级兜底，并在 WASM 这种峰值敏感、单线程、无裸时钟的环境里把上述纪律编译期固化」。
