# 架构图领域通用性反思

> 状态：讨论中
> 日期：2026-07-18
> 作者：讨论纪要

## 1. 核心问题

当前 `architecture` 图表类型的 entity type **过度绑定软件开发领域**，限制了架构图作为通用图形范式的表达能力。

### 1.1 现状：9 种 type 全是 IT 领域概念

见 [`profile/mod.rs`](../../.../../../crates/plotgram-core/src/profile/mod.rs#L108-L118)：

```
frontend, backend, service, database, gateway, cache, queue, storage, external
```

这些 type 全部指向软件/互联网行业的特定组件。

### 1.2 问题：换个行业就没法用了

| 行业/场景 | 需要表达的节点类型 | 当前 type 够用吗 |
|-----------|-------------------|-----------------|
| 组织架构 | 部门、团队、岗位、人员 | ❌ 完全不匹配 |
| 硬件架构 | CPU、内存、主板、外设 | ❌ 不匹配 |
| 建筑/平面 | 房间、走廊、电梯、楼梯 | ❌ 不匹配 |
| 工艺流程 | 工位、物料、检测、包装 | ❌ 不匹配 |
| 生态系统 | 生产者、消费者、分解者 | ❌ 不匹配 |

但这些场景从**图形结构特征**上看，都是「架构图」：
- 节点是并存的实体（不是过程步骤）
- 有分组/分层/分区的概念
- 边表达连接/依赖/流动关系
- 没有明确的「开始/结束」

---

## 2. 三层结构分析

当前的 type 体系分为三层，问题主要出在第二层：

### 2.1 第一层：基础形状（通用，没问题）

见 [`render/visual.rs`](../../.../../../crates/plotgram-core/src/render/visual.rs#L60-L77) 的 `NodeShape` 枚举：

```
Rect           矩形
RoundedRect    圆角矩形
Circle         圆形
Diamond        菱形
Cylinder       圆柱体
Hexagon        六边形
Person         人形
Stadium        体育场形
Parallelogram  平行四边形
Document       文档形
Cloud          云形
Subprocess     子流程（双边框）
```

共 12 种基础形状，**领域无关**，任何行业都能用。

### 2.2 第二层：主题映射（问题所在）

在主题 JSON 的 `entity_types` 中，用**领域语义**命名 type，然后映射到形状 + 颜色：

```json
"entity_types": {
  "service":   { "shape": "rounded_rect", "fill": "蓝色系" },
  "database":  { "shape": "cylinder",     "fill": "橙色系" },
  "gateway":   { "shape": "diamond",      "fill": "青色系" },
  ...
}
```

**问题**：type 名是语义化的（`service`, `database`...），绑定了特定领域。

### 2.3 第三层：图表类型闭集（强化了领域绑定）

见 [`profile/mod.rs`](../../.../../../crates/plotgram-core/src/profile/mod.rs#L108-L118)，每种图表类型有自己的 type 白名单：

```rust
const ARCHITECTURE_ENTITY_TYPES: &[&str] = &[
    "frontend", "backend", "service", "database",
    "gateway", "cache", "queue", "storage", "external",
];
```

这进一步把「架构图」限定在了软件架构的范畴内。

---

## 3. 对比：Mermaid 的思路

Mermaid 没有专门的 `architecture` 图表类型，而是用通用的 `graph`：

- `graph TD` / `graph LR` — 通用节点-边图
- 形状通过语法选择：`id[矩形]` / `id{菱形}` / `id[(圆柱)]`
- 没有预设的领域语义，用户自己定义标签和含义
- 布局算法单一（分层布局），不区分场景

**优点**：通用、灵活、什么都能画
**缺点**：缺少场景优化（布局、分组、语义约束）

---

## 4. 待讨论的方向

### 方向 A：type 去领域化，形状即 type

把 entity type 从「语义类型」改成「形状类型」，直接用形状名：

| 形状类型 | 对应现在的 type | 通用语义 |
|---------|----------------|---------|
| `rect` | frontend, storage | 矩形，普通节点 |
| `rounded` | service, backend | 圆角矩形，主要组件 |
| `cylinder` | database | 圆柱体，存储类 |
| `diamond` | cache, gateway | 菱形 |
| `hexagon` | — | 六边形 |
| `parallelogram` | queue | 倾斜矩形 |
| `dashed` | external | 虚线边框 |
| `person` | person | 人形 |
| `stadium` | start, end | 体育场形 |

- 领域语义交给 `semantic` 属性和 label
- 架构图和流程图的 type 统一，区别只在布局算法

### 方向 B：保持语义 type，但开放扩展

- 保留现有语义 type 作为「内置推荐」
- 允许用户自定义 type（自定义形状 + 颜色）
- 图表类型不做闭集校验，type 完全开放

### 方向 C：拆分「图表类型」和「布局算法」

- 图表类型 = 默认布局 + 默认 type 集合 + 默认路由
- 用户可以自由切换布局算法（`layout: sugiyama` / `layout: grouped` / `layout: force`）
- 「架构图」退化为一个预设（分组布局 + 组件语义 type），不是硬约束

### 方向 D：架构图改名为「拓扑图/结构图」

- 不叫 `architecture`，改叫 `topology` 或 `structure`
- type 从 IT 领域语义改为更通用的结构角色
- 强调「结构表达」而非「软件架构」

---

## 5. 核心共识（待确认）

1. **架构图是图形结构范式，不是领域分类** — 应该能表达任何行业的结构关系
2. **当前 type 体系过于绑定软件领域** — 限制了适用范围
3. **形状是通用的，语义是用户的** — 形状系统应该领域无关

## 7. 代码核对：`type` 到底被谁消费

> 结论先行：整条渲染管线里，**唯一把架构图 type 锁死的就是「校验闭集」这一处**；主题层本就对未知 type 兜底，架构图布局根本不读 type 语义。

将 `type` 在整条管线的消费者逐一追踪后，得到下表：

| 消费点 | 代码位置 | 对未知 type 的行为 |
|--------|---------|-------------------|
| **校验闭集** | [`validation/attrs.rs` L44-53](../../../crates/plotgram-core/src/validation/attrs.rs#L44-L53) | **硬报错** `invalid_enum_value` ← 唯一真正的闸门 |
| 主题级联 | [`theme/schema.rs` node_block L478-485](../../../crates/plotgram-core/src/theme/schema.rs#L478-L485) | 已优雅兜底：`unwrap_or(&d.node_default)` |
| DSL 样式声明 | [`prepare/styles.rs` L40-47](../../../crates/plotgram-core/src/prepare/styles.rs#L40-L47) | 仅 warning（unknown_style_selector） |
| 布局语义 | sugiyama_v2 / circular / mindmap | 仅 flowchart/state/mindmap 用 type 判定 initial/final/start/end/root |
| **架构图布局** | architecture_v2（全目录） | **完全不消费 type 语义**，分组靠显式 group 语法 |

**关键发现**：对架构图而言，`type` 纯粹是渲染（形状 + 颜色）属性，布局不读它；且主题层对未知 type 已兜底为 `node_default`。因此开放架构图 type 的风险面极小。

## 8. 定性：这是一个可精确定位的设计缺陷

是设计缺陷，但不是「考虑不周」式的模糊问题，而是一个**抽象层次错配（category error）**：

> **把「开放结构画布」当成「闭合记法语言」来建模了。**

系统里混着两类本质不同的图：

- **闭合记法（bounded notation）**：state、sequence、mindmap、ER。它们有真正的**文法**——`initial/final`、`actor/lifeline`、`root/branch` 不只是样式，而是**布局算法的语义输入**（sugiyama 用它定 source/sink，mindmap 用它定根）。对这些图，type 闭集校验是**正确的**。
- **开放画布（open canvas）**：architecture（及潜在的 topology / 组织架构 / 硬件图）。它的布局**不消费 type 语义**，type 只驱动形状与颜色。对这类图，闭集校验没有任何算法上的必要性，纯粹把「软件领域推荐清单」硬编码成了「合法性边界」。

缺陷根因在 [`profile/mod.rs` L61-63](../../../crates/plotgram-core/src/profile/mod.rs#L61-L63)：

```rust
pub fn restricts_entity_type_values(&self) -> bool {
    !self.entity_types.is_empty()   // ← 把「有推荐清单」等同于「必须闭集校验」
}
```

这里把两个**正交**的概念绑成了一个：

1. 这个图有哪些**推荐/内置** type（用于补全、主题映射、文档提示）
2. 这个图是否**只允许**这些 type（合法性边界）

对 state 两者恰好重合，未暴露问题；对 architecture，第 2 条根本不该成立。ER（`entity_types` 为空 → `restricts=false` → 任意 type 合法）已经证明这条路可行，architecture 只是没享受同样待遇。

所以后续方案的本质不是「加功能」，而是**修正这个错配**——让 architecture 回到它本该属于的「开放画布」类别。

## 9. 选定方向：B 方案详细路线

设计目标：**推荐 type 与合法边界解耦**；内置 type 保留为「推荐 + 主题映射」，不再作为拒绝用户的依据；未知 type 优雅降级而非报错。

### 阶段 0：明确分治原则（决策，不改码）

- **保持闭集**：state、sequence、mindmap、flowchart——type 是布局文法的一部分，乱写会破坏布局。
- **改为开放**：architecture（及未来 topology/structure）——type 不参与布局，全面开放。

地基结论：**不是取消所有闭集校验，而是按「记法 vs 画布」分类施策**。

### 阶段 1：profile 层解耦「推荐清单」与「校验策略」

在 [`DiagramProfile`](../../../crates/plotgram-core/src/profile/mod.rs#L16-L45) 引入显式开关：

```rust
pub struct DiagramProfile {
    ...
    pub entity_types: &'static [&'static str],   // 语义变为「推荐/内置」，不再等于「合法边界」
    pub entity_types_open: bool,                 // 新增：true=开放画布，false=闭合记法
}
```

改写判定：

```rust
pub fn restricts_entity_type_values(&self) -> bool {
    !self.entity_types.is_empty() && !self.entity_types_open
}
```

- architecture profile 设 `entity_types_open: true`，同时**保留** `ARCHITECTURE_ENTITY_TYPES`（仍用于主题映射与补全提示）。
- state/sequence/mindmap/flowchart 设 `entity_types_open: false`。
- ER 不变（本就空集）。

**为何保留推荐清单而非清空**：清空会同时丢掉主题 entity_types 映射、`default_entity_type` 补全、编辑器补全提示。保留清单 + 开放校验，才是「内置推荐 + 用户扩展」的正解。

### 阶段 2：校验层——未知 type 降级为 warning

[`validation/attrs.rs` L44-53](../../../crates/plotgram-core/src/validation/attrs.rs#L44-L53) 对开放 profile 已不会进入 error 分支（`restricts_entity_type_values()` 返回 false）。为保留引导价值，加一条**轻提示**：

- 开放 profile 且 type 不在推荐清单内 → 发 **info/warning**（如「`部门` 不是内置 type，将使用默认形状；可用 `shape`/`fill` 自定义外观」），而非 error。
- 闭合 profile 行为不变（继续 error）。
- 需新增诊断类型（如 `custom_entity_type_hint`），级别 Warning。

### 阶段 3：让自定义 type 能自定义外观

开放后 `type: 部门` 默认落到 `node_default`（圆角矩形 + 中性色）。保证三条自定义通道通畅（多数已存在，需验证）：

1. **内联属性**：`节点 { type: 部门, shape: hexagon, fill: "#..." }` — 确认 `shape` 作为内联 standard 属性能覆盖 node_default（style cascade 第 5 层）。
2. **DSL 声明**：`node_style 部门 { shape: hexagon, fill: "..." }` — [`prepare/styles.rs`](../../../crates/plotgram-core/src/prepare/styles.rs#L90-L120) 已按 type 字符串匹配，unknown selector 仅 warning，天然支持；需确认 `shape` 在 `allowed_keys_for_decl(Node)` 白名单内。
3. **主题扩展**：用户/项目主题 JSON 里新增 `entity_types: { "部门": {...} }`，[`node_block`](../../../crates/plotgram-core/src/theme/schema.rs#L478-L485) 已能命中。

产出主要是**验证 + 补齐 `shape` 作为可覆盖键**，非大改。

### 阶段 4：默认兜底可预测化（可选增强）

未知 type 现统一落 `node_default`。若希望多种自定义 type 视觉可区分，可加**确定性调色兜底**：按 type 名稳定哈希 → 映射到主题调色板某个 role 色。

- **必须确定性**（AGENTS.md 第 2 条）：用 type 名稳定 hash，不依赖 HashMap 迭代序，保证同名 type 每次渲染同色。
- 非必需，默认可先不做，优先保证「能用」。

### 阶段 5：测试与文档

- profile 测试：「architecture 接受任意 type 不报错」「内置 type 仍走主题映射」「state 仍拒绝非法 type」。
- 校验测试：`type: 部门` 在 architecture 下产出 warning 而非 error。
- 更新 [`entity-types.md`](../visual-language/entity-types.md) 与 architecture 规范：说明「内置 type = 推荐，非限制；可自定义 type + shape/fill」。

## 10. 风险与边界（明确不碰什么）

- **绝不动 state/sequence/mindmap 的闭集**——它们的 type 是布局文法输入，开放会静默破坏布局。
- **主题层不用改**——`node_block` 兜底已就绪，侧面印证原始设计里数据层早想开放，只有校验层没跟上。
- **无向后兼容负担**（AGENTS.md 第 1 条）：直接改 `restricts_entity_type_values` 语义，不留兼容层。
- **改动面小且集中**：核心即 profile（加字段 + 改一方法）+ validation（error 降 warning）两处，其余为验证与测试。相比方向 A（重构 type→shape 整套语义、动 theme 映射与布局语义读取），B 改动量约为其 1/5，且不丢失任何现有语义资产。
