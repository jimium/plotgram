# 架构图领域通用性反思

> 状态：讨论中
> 日期：2026-07-18
> 作者：讨论纪要

## 1. 核心问题

当前 `architecture` 图表类型的 entity type **过度绑定软件开发领域**，限制了架构图作为通用图形范式的表达能力。

### 1.1 现状：9 种 type 全是 IT 领域概念

见 [`profile/mod.rs`](../../.../../../crates/plotgram-core/src/profile/mod.rs#L108-L118)：

```
frontend, backend, service, database, gateway, cache, queue, storage, external
```

这些 type 全部指向软件/互联网行业的特定组件。

### 1.2 问题：换个行业就没法用了

| 行业/场景 | 需要表达的节点类型 | 当前 type 够用吗 |
|-----------|-------------------|-----------------|
| 组织架构 | 部门、团队、岗位、人员 | ❌ 完全不匹配 |
| 硬件架构 | CPU、内存、主板、外设 | ❌ 不匹配 |
| 建筑/平面 | 房间、走廊、电梯、楼梯 | ❌ 不匹配 |
| 工艺流程 | 工位、物料、检测、包装 | ❌ 不匹配 |
| 生态系统 | 生产者、消费者、分解者 | ❌ 不匹配 |

但这些场景从**图形结构特征**上看，都是「架构图」：
- 节点是并存的实体（不是过程步骤）
- 有分组/分层/分区的概念
- 边表达连接/依赖/流动关系
- 没有明确的「开始/结束」

---

## 2. 三层结构分析

当前的 type 体系分为三层，问题主要出在第二层：

### 2.1 第一层：基础形状（通用，没问题）

见 [`render/visual.rs`](../../.../../../crates/plotgram-core/src/render/visual.rs#L60-L77) 的 `NodeShape` 枚举：

```
Rect           矩形
RoundedRect    圆角矩形
Circle         圆形
Diamond        菱形
Cylinder       圆柱体
Hexagon        六边形
Person         人形
Stadium        体育场形
Parallelogram  平行四边形
Document       文档形
Cloud          云形
Subprocess     子流程（双边框）
```

共 12 种基础形状，**领域无关**，任何行业都能用。

### 2.2 第二层：主题映射（问题所在）

在主题 JSON 的 `entity_types` 中，用**领域语义**命名 type，然后映射到形状 + 颜色：

```json
"entity_types": {
  "service":   { "shape": "rounded_rect", "fill": "蓝色系" },
  "database":  { "shape": "cylinder",     "fill": "橙色系" },
  "gateway":   { "shape": "diamond",      "fill": "青色系" },
  ...
}
```

**问题**：type 名是语义化的（`service`, `database`...），绑定了特定领域。

### 2.3 第三层：图表类型闭集（强化了领域绑定）

见 [`profile/mod.rs`](../../.../../../crates/plotgram-core/src/profile/mod.rs#L108-L118)，每种图表类型有自己的 type 白名单：

```rust
const ARCHITECTURE_ENTITY_TYPES: &[&str] = &[
    "frontend", "backend", "service", "database",
    "gateway", "cache", "queue", "storage", "external",
];
```

这进一步把「架构图」限定在了软件架构的范畴内。

---

## 3. 对比：Mermaid 的思路

Mermaid 没有专门的 `architecture` 图表类型，而是用通用的 `graph`：

- `graph TD` / `graph LR` — 通用节点-边图
- 形状通过语法选择：`id[矩形]` / `id{菱形}` / `id[(圆柱)]`
- 没有预设的领域语义，用户自己定义标签和含义
- 布局算法单一（分层布局），不区分场景

**优点**：通用、灵活、什么都能画
**缺点**：缺少场景优化（布局、分组、语义约束）

---

## 4. 待讨论的方向

### 方向 A：type 去领域化，形状即 type

把 entity type 从「语义类型」改成「形状类型」，直接用形状名：

| 形状类型 | 对应现在的 type | 通用语义 |
|---------|----------------|---------|
| `rect` | frontend, storage | 矩形，普通节点 |
| `rounded` | service, backend | 圆角矩形，主要组件 |
| `cylinder` | database | 圆柱体，存储类 |
| `diamond` | cache, gateway | 菱形 |
| `hexagon` | — | 六边形 |
| `parallelogram` | queue | 倾斜矩形 |
| `dashed` | external | 虚线边框 |
| `person` | person | 人形 |
| `stadium` | start, end | 体育场形 |

- 领域语义交给 `semantic` 属性和 label
- 架构图和流程图的 type 统一，区别只在布局算法

### 方向 B：保持语义 type，但开放扩展

- 保留现有语义 type 作为「内置推荐」
- 允许用户自定义 type（自定义形状 + 颜色）
- 图表类型不做闭集校验，type 完全开放

### 方向 C：拆分「图表类型」和「布局算法」

- 图表类型 = 默认布局 + 默认 type 集合 + 默认路由
- 用户可以自由切换布局算法（`layout: sugiyama` / `layout: grouped` / `layout: force`）
- 「架构图」退化为一个预设（分组布局 + 组件语义 type），不是硬约束

### 方向 D：架构图改名为「拓扑图/结构图」

- 不叫 `architecture`，改叫 `topology` 或 `structure`
- type 从 IT 领域语义改为更通用的结构角色
- 强调「结构表达」而非「软件架构」

---

## 5. 核心共识（待确认）

1. **架构图是图形结构范式，不是领域分类** — 应该能表达任何行业的结构关系
2. **当前 type 体系过于绑定软件领域** — 限制了适用范围
3. **形状是通用的，语义是用户的** — 形状系统应该领域无关
