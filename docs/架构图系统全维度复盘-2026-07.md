# 架构图系统全维度复盘报告

> 日期：2026-07-12  
> 范围：`crates/plotgram-core/src/layout`、`crates/plotgram-core/src/pipeline`、`crates/plotgram-eval`、现有 benchmark/docs  
> 覆盖模块：架构图/流程图默认布局算法、正交路由算法、整体执行 Pipeline

## 1. 复盘目标与方法

本次复盘聚焦三类问题：

1. 逻辑缺陷排查：验证布局、正交路由、总 Pipeline 的业务逻辑完整性、算法正确性、模块交互合理性。
2. 优化空间评估：从执行效果、可视化美观度、工程实用度三条主线梳理优化方向，并尽量映射到现有可量化指标。
3. 技术债梳理：识别评估链路、代码结构、注释、测试、性能热点方面的债务。

采用的方法：

- 静态审计核心源码入口与关键阶段函数。
- 对照既有设计文档、踩坑复盘文档与 benchmark/eval 产物。
- 以“谁在最终写入结果”而不是“局部函数看起来合理”作为主判据，优先排查阶段时序与状态传递问题。

## 2. 当前系统概览

### 2.1 主执行链路

- 总 Pipeline 为 `parse -> prepare -> validate -> layout -> render -> encode`，入口位于 `crates/plotgram-core/src/pipeline/mod.rs`。
- 布局主 Pipeline 位于 `crates/plotgram-core/src/layout/pipeline.rs`，核心顺序为：
  - 布局策略计算节点坐标
  - Node Frame 对齐
  - Group Frame 整形
  - 预路由反馈
  - 路由 + refine
  - post-route group/frame 修正
  - 末尾 snap/repulse
  - orthogonal sanitize + label avoidance
- 架构图默认布局走 `architecture_v2`，流程图默认布局在无 group 时走 `sugiyama_v2`，有 group 时走 `flowchart/group_divide`。
- 架构图与流程图默认边路由均落到 orthogonal family，路径核心位于 `crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/`。

### 2.2 现有量化基础

仓库已经具备可复用的度量基础，可直接作为后续整改 KPI：

- 质量指标：`LayoutMetrics` 已覆盖节点重叠、边穿节点、边交叉、标签重叠、拐点数、画布面积、边长、宽高比、面积利用率等，位于 `crates/plotgram-eval/src/metrics.rs`。
- 综合得分：默认权重为 Correctness 40%、Compactness 20%、Uniformity 20%、Aesthetics 20%，并提供图类型差异化权重。
- 基准数据：`benchmark-data/report.md` 记录了 22 个架构图 warm-cache 基准结果，当前整体约为 `2.4x` 加速，但 `c.k8s-platform-stack` 仍为 `132.8ms`，是大图热点样本。

## 3. 问题清单

以下问题按“明确逻辑错误/流程断层优先，其次是策略级质量缺口”排序。风险等级分为 `高`、`中`、`低`。

| ID | 模块 | 风险 | 问题描述 | 主要证据 | 影响 |
|---|---|---|---|---|---|
| P01 | Layout Pipeline | 高 | `snap: false` 会直接短路 `run_post_route_group_frame`，不仅关闭像素量化，还连带跳过 group frame restore、增量重路由与画布更新。 | `layout/pipeline.rs` 中 `run_post_route_group_frame()` 以 `!edge_snap_config.enabled` 早退。 | 用户只想关闭 snap，却意外关闭后路由几何恢复，导致组框、边路径与节点位移可能失配。 |
| P02 | PreparedDiagram / Render Pipeline | 高 | `PreparedDiagram` 允许以 `with_layout_plan()` 注入 diagram 与 plan 的任意组合，但 `compute_layout_with_plan()` 只校验 diagram 配置，不校验 plan 是否仍匹配当前 diagram。 | `ast.rs`、`render/scene.rs`、`layout/mod.rs`。 | 调用方可能得到“当前 DSL 属性”和“实际执行 plan”不一致的结果，形成静默分裂。 |
| P03 | Architecture Layout | 高 | `architecture_v2` 在 FAS 之后才注入不可逆约束边，可能重新引入环，但后续 rank/order 仍沿用旧去环结果。 | `node/architecture_v2/layout/mod.rs`、`node/architecture_v2/layout/acyclic.rs`；对比 `sugiyama_v2/graph.rs` 是先注入约束再去环。 | 约束多时会出现 rank 异常、层次不稳定或与约束语义冲突。 |
| P04 | Flowchart Group Divide | 高 | `topological_sort_groups()` 先对跨组边累计入度，再只对 `out_edges` 去重；多条 `A -> B` 会导致 `B` 入度多算、释放时少减。 | `node/flowchart/group_divide.rs`。 | 正常 DAG 会被误判成“存在剩余环”，组排序错误，直接影响分组堆叠结果。 |
| P05 | Orthogonal Reroute | 高 | corridor 快速 reroute 成功时直接 `grid.insert_path()` 覆盖新路径，但没有先移除旧路径。 | `edge_routing_orthogonal/conflict_reroute.rs`。 | SegmentGrid 残留幽灵段，后续 spacing/scoring 看到假冲突，导致误判和连锁重路由。 |
| P06 | Lane Assignment | 高 | `force_shift_trunk_coord()` 兜底分支提交位移时绕过 `validate_shift()` 的几何合法性校验。 | `edge_routing_orthogonal/lane_assignment.rs`。 | 可能引入邻段反转、退化短段、穿节点或新的微台阶，是几何破坏型缺陷。 |
| P07 | Architecture Internal Pipeline | 中高 | `GroupBoundsPhase` 已计算 group bounds 后，`GroupAlignmentPhase` 仍继续移动节点，但未重算 group bounds。 | `node/architecture_v2/pipeline.rs`。 | `ctx.groups` 可能成为过期框，影响总尺寸、路由壳层与后续 group/frame 协同。 |
| P08 | Flowchart Group Divide | 中 | 分治路径把组内子图所有实体的 `group_id` 清空，且 `groups` 直接置空，嵌套 group 语义在组内布局阶段被扁平化。 | `node/flowchart/group_divide.rs`、`node/flowchart/mod.rs`。 | 组框还能画出来，但内部排布不再尊重嵌套分组边界，复杂泳道/嵌套流程图效果退化。 |
| P09 | Flowchart × Orthogonal | 中 | `divide_flowchart_with_groups()` 未回填 `hints.sugiyama_ranks`，而正交路由的边排序明确依赖该信息。 | `node/flowchart/group_divide.rs`、`edge_routing_orthogonal/layer_order.rs`。 | 分治后的流程图路由退化为仅按连接度排序，通道占用质量下降。 |
| P10 | Orthogonal Corridor | 中 | `planned_cross_axis_offset_for_edge()` 对多段 corridor chain 只读取第一段 lane 信息。 | `edge_routing_orthogonal/corridor_route.rs`。 | 多 group 链路会出现“前段分开、后段又并回”的不连续 lane 行为。 |
| P11 | Orthogonal Corridor | 中 | `validated_corridor_path()` 只检查穿节点/穿组，不检查边间距约束。 | `edge_routing_orthogonal/mod.rs`。 | corridor 路径会优先注入一批“合法但过密”的路径，后续只能依赖 X-1/X-3 补救。 |
| P12 | Grid Snap / Align Override | 中 | `align: full` 与 `align: layer-only` 会把 architecture 默认的 `Centroid` 对齐强度降成 `OverlapOnly`。 | `layout/grid_snap.rs`。 | 配置语义反直觉，用户显式“全开”反而削弱默认布局质量。 |
| P13 | Route Feedback / Post-route Hook | 中 | 节点位移后是否重路由使用了两套阈值：`1.0` 与 `NODE_MOVE_REROUTE_EPS = 2.0`。 | `layout/route_feedback.rs`、`layout/post_route_hook.rs`、`layout/pipeline.rs`。 | 小位移在不同阶段触发条件不一致，容易留下边几何/标签的局部不同步。 |
| P14 | Direct Render / Validation | 中 | 标准 `pipeline::run()` 会先 `validate`，但 direct render/layout API 不走完整 validation；`plotgram-eval::engine` 与 `edge_routing_bench` 直接调 `compute_layout(&Diagram)` 绕过 `validation::validate`，只在 layout 阶段做有限配置校验。 | `pipeline/mod.rs`、`validation/mod.rs`、`render/scene.rs`、`plotgram-eval/src/engine.rs:298`、`plotgram-eval/src/bin/edge_routing_bench.rs:217`。 | CLI 与库调用/服务调用/评测入口的行为不完全一致，坏配置可能被静默回退。 |
| P15 | Sugiyama Postprocess | 中 | `normalize_layout_result_to_padding()` 先移动节点，再用移动后的最小值计算 group 的平移量，导致 group 与总尺寸不一定同步。 | `node/sugiyama_v2/postprocess.rs`。 | 组框与节点的 padding 归一化可能出现偏差，尤其影响 ER 相关收尾逻辑。 |
| P16 | Orthogonal Port Coordination | 中 | `coordinate_port_sides()` 使用“先到先锁死”的单次贪心，全局 `switched_pairs` 会剥夺另一端更合理的调整机会。 | `edge_routing_orthogonal/mod.rs`。 | 结果确定但质量依赖遍历顺序，在 hub 节点场景更容易留下 stub 交叉和端口分散。 |

## 4. 优化空间评估

### 4.1 算法执行效果

#### 现状判断

- 布局与路由的主体框架已经成型，且具备多阶段修复能力。
- 真正限制结果上限的不是单个启发式弱，而是“阶段间状态没有完全闭合”，例如：
  - group/frame 恢复被 snap 开关误伤
  - flowchart 分治结果没有把 `sugiyama_ranks` 传给路由
  - architecture group bounds 在后续移动后可能过期

#### 优化方向

1. 先修阶段闭环问题，再调局部启发式。
2. 统一“节点移动后需要重路由”的阈值与 helper，避免不同阶段各自定义触发条件。
3. 对布局结果向路由传递的 `LayoutHints` 建立最小完备契约，至少覆盖：
   - `sugiyama_ranks`
   - `edge_routing_style`
   - `group_routing`
   - `space_budget`

#### 建议 KPI

| 指标 | 当前依据 | 建议目标 |
|---|---|---|
| 路由通过率 | 可由 `LayoutMetrics.edge_node_crossings == 0`、`edge_through_groups == 0`、lint error 归零联合表征 | 核心 showcase 通过率 >= 95% |
| 布局有效率 | 可由 `node_overlap_pairs == 0`、`NodeOutsideGroup == 0`、`GroupOverlap == 0` 表征 | 架构图/流程图 showcase >= 95% |
| 后处理稳定性 | 以 post-route 之后是否仍发生 group/node 不一致表征 | P0 问题清零后再引入回归基线 |

### 4.2 可视化美观度

#### 现状判断

- 现有 `LayoutMetrics` 已可量化：
  - 节点重叠
  - 边交叉
  - 标签遮挡
  - 拐点数量
  - 画布利用率
  - 宽高比偏离
- `benchmark-data/report.md` 显示部分样例仍有路由轻微退化，说明性能优化阶段对视觉质量已有副作用迹象。

#### 优化方向

1. corridor 路由必须把 spacing 作为准入条件，而不是完全交给后处理补救。
2. lane assignment 兜底路径必须重新纳入几何合法性验证。
3. flowchart 分治补齐 `sugiyama_ranks` 后，重建“低层先占通道”的边排序优势。
4. 对架构图 `align` 覆盖语义做明确化，避免显式配置反向削弱默认美观度。

#### 建议 KPI

| 指标 | 当前依据 | 建议目标 |
|---|---|---|
| 节点重叠率 | `node_overlap_pairs / C(n,2)` | 核心 showcase 维持 0 |
| 连线交叉率 | `edge_crossings / edge_count` | 相比当前基线下降 15% 以上 |
| 标签遮挡率 | `(label_node_overlaps + label_label_overlaps) / edge_count` | 相比当前基线下降 30% 以上 |
| 画布利用率 | `area_utilization` | 架构图提升到 >= 18%，流程图 >= 22% |
| 弯折复杂度 | `bend_count / edge_count` | 大图样例下降 10%~15% |

### 4.3 工程实用度

#### 现状判断

- 大图性能已有明显提升，但 `c.k8s-platform-stack` 仍是重灾区。
- refine 与 orthogonal router 都有明确性能热点。
- 用户配置灵活性已有基础，但存在“配置名语义与实际行为不一致”的问题。

#### 优化方向

1. 将 `c.k8s-platform-stack` 固定为大图门禁样例。
2. 为 orthogonal/corridor/refine 建立基线断言，不只输出日志。
3. 统一 eval 入口，避免不同 bench 工具走不同计算路径。
4. 明确 `align`、`snap`、`layout`、`edge_routing` 的覆盖语义，消除隐式副作用。

#### 建议 KPI

| 指标 | 当前依据 | 建议目标 |
|---|---|---|
| 大图单图耗时 | `benchmark-data/report.md` 中 `c.k8s-platform-stack = 132.8ms` | 降到 < 100ms |
| Layout 总耗时 | 22 图总耗时 370.5ms | 再降 15%~20% |
| 路由评测一致性 | 目前 `edge_routing_bench` 与 eval 入口不统一 | 所有 eval/bench 统一走同一 prepare+plan+layout 入口 |
| 用户配置可预期性 | 通过配置一致性问题数衡量 | P0/P1 配置语义问题清零 |

## 5. 优化优先级排序

### P0：先修确定性逻辑错误

建议纳入最近一轮迭代，优先级最高。

1. 修复 `snap: false` 误伤 post-route group frame 的早退逻辑。
2. 修复 `flowchart/group_divide::topological_sort_groups()` 的重复入度 bug。
3. 修复 `conflict_reroute` corridor 快速路径未移除旧 SegmentGrid 残留段的问题。
4. 修复 `lane_assignment` fallback 路径绕过合法性校验的问题。
5. 修复 `edge_routing_bench` / `bench` 的输入扩展名不一致问题（`.dfy` → `.pgm`）。注：`edge_routing_bench` 并未删除，仍是当前可用的评测二进制；评测入口不统一的问题见 6.1 节。

### P1：补齐布局与路由阶段契约

1. 给 flowchart 分治结果补 `sugiyama_ranks`。
2. 让 architecture_v2 在节点继续移动后重算 group bounds，或显式约束后续 phase 不再写节点。
3. 统一节点移动后的 reroute 阈值与 helper。
4. 让 corridor 准入检查纳入 spacing 约束，而不是完全依赖后处理补救。
5. 增加 diagram/plan 一致性校验，避免 `PreparedDiagram` 缓存 plan 失效后静默执行旧 plan。

### P2：做质量与工程化增强

1. 重新设计 `align` 覆盖语义，保留算法默认强度。
2. 让 port coordination 从单次贪心升级为双端协调或带回看的一轮局部优化。
3. 优化 refine 中 `analyze_edge_node_crossings` 的大图热点。
4. 对 benchmark/eval 输出补充版本元数据、timeout 政策与权重配置。

## 6. 技术债整改建议

### 6.1 评测链路债务

#### 问题

- `edge_routing_bench` / `bench` 的文件扫描逻辑查找 `.dfy`，但注释、错误提示和文件名裁剪都以 `.pgm` 为准（已修复）。
- 评测入口不统一（源码核验）：
  - `plotgram-eval::engine`（第 298 行）与 `edge_routing_bench`（第 217 行）直接调用 `compute_layout(&Diagram)`，**绕过 `validation::validate`**。
  - `plotgram-eval::baseline`（第 341、356 行）走 `parse_prepare_validate` → `compute_layout_with_plan`，与标准 `pipeline::run()` 路径一致。
  - 二者口径差异：engine 路径不会因配置非法而 fail fast，坏配置会被静默回退。

#### 建议

- 让 `engine` / `edge_routing_bench` 与 `baseline` 对齐：统一走 `parse_prepare_validate` → `compute_layout_with_plan`，或在 engine 内显式调用 `validation::validate`。
- 在 benchmark 输出中固化以下字段：
  - `metric_weight_profile`
  - `timeout_policy`
  - `baseline_version`
  - `layout_entry`

### 6.2 Pipeline 结构债务

#### 问题

- `route_feedback.rs` 与 `layout/pipeline.rs` 中存在重复的 `space_budget -> push -> reroute` 兜底逻辑。
- 后处理阶段调用点偏多，行为契约分散，不利于确认“最终谁写结果”。

#### 建议

- 抽出统一的 `apply_residual_space_budget_and_reroute()` helper。
- 对 post-route 阶段引入更清晰的阶段命名和单一职责：
  - `restore_group_frame`
  - `reroute_after_node_moves`
  - `final_snap_and_repulse`
  - `final_orthogonal_sanitize`
  - `final_label_avoidance`

### 6.3 测试债务

#### 现状

- `layout` 目录下 dedicated 测试文件主要集中在：
  - `orthogonal_tests.rs`
  - `group_frame_tests.rs`
  - `refine_tests.rs`
  - `layout_tests.rs`
  - `test_fixtures.rs`
- 虽然仓库内已有大量内联 `#[test]`，但针对“模块交互断层”的回归测试仍不足。

#### 缺口

建议补以下定向测试，而不是泛化加大量低价值测试：

1. `snap: false` 不应跳过 group frame restore。
2. flowchart 多条跨组边不应污染 group topo sort。
3. corridor reroute 成功后 SegmentGrid 不应残留旧路径。
4. lane assignment fallback 不得引入穿节点或邻段反转。
5. flowchart group divide 应向 orthogonal router 传递有效 rank hints。
6. `PreparedDiagram` 与 `LayoutPlan` 不一致时应 fail fast 或至少报警。

### 6.4 注释与可维护性债务

#### 现状

- 模块级文档总体较好，但核心控制流文件仍偏难追踪：
  - `layout/pipeline.rs`
  - `layout/route_feedback.rs`
  - `layout/node/architecture_v2/two_phase.rs`
- 当前问题不是“完全没注释”，而是“阶段边界和回退条件解释不足”。

#### 建议

- 只给关键入口函数补阶段注释，不做全仓机械补注释。
- 优先补充以下内容：
  - 阶段输入/输出的权威数据结构
  - 允许继续移动节点的最后阶段
  - 何时允许重建 labels / groups / ranks
  - 何时只是视觉后处理、不能再改变拓扑

### 6.5 性能债务

#### 现状

- 当前全量架构图 benchmark 总耗时为 `370.5ms`，已有明显优化。
- 但 `c.k8s-platform-stack` 仍为 `132.8ms`，且报告中指出候选数达到 `9907`。
- refine 与 orthogonal path selection 仍是大图热点。

#### 建议

1. 以 `c.k8s-platform-stack` 建立强基线，目标 < `100ms`。
2. 针对 refine crossing 分析引入更强的空间索引。
3. 对 orthogonal path candidate 的分层候选数、硬过滤拒绝率、degraded 数做 CI 级别趋势监控。

## 7. 建议落地路线

### 第一阶段：修正确性

- 处理 P0 问题，优先恢复阶段闭环和几何合法性。
- 产出一组最小回归测试，锁住 bug 不反弹。

### 第二阶段：修契约与口径

- 统一评测入口。
- 完整梳理 `LayoutHints` 与 post-route 阶段职责。
- 补齐 flowchart 分治和 orthogonal router 之间的 rank 契约。

### 第三阶段：做效果提升

- 基于现有 `LayoutMetrics` 和 benchmark 建立可对比基线。
- 面向大图样例做专项优化，避免在小图上用肉眼评估替代全量验证。

## 8. 总结

当前系统的主要矛盾不是“缺少算法”，而是“已有算法足够复杂，但阶段契约还没有完全闭合”。  
本轮复盘识别出 6 个高风险问题、10 个中低风险问题，其中多项属于明确逻辑错误，优先级高于局部启发式调优。

建议后续迭代遵循以下原则：

1. 先修 Pipeline 时序与状态闭环，再调局部评分函数。
