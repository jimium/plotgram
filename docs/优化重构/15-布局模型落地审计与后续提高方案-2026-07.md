## 0. 结论

当前布局重构已经完成了最难的一部分：

1. 图类型入口已基本迁入 `recipes/`。
2. 分层类布局已抽出 `engines/layered`。
3. 坐标 IR、PAVA 和 projected optimizer 已进入 `kernel/coordinate`。
4. flowchart、ER、state 的 Sugiyama 路径以及 architecture 的部分路径已经调用统一坐标求解器。
5. 代码已经具备从旧式“算法函数集合”演进到 Kernel/Recipe 架构的主体骨架。

但如果按文档 11–13 的完成定义衡量，当前仍属于：

> **算法内核已迁移，Recipe 外形已建立；生命周期、硬约束语义、冻结边界和旧层清理尚未完全收口。**

这不是目录美化问题。当前存在几项会直接影响正确性的实现缺口：

- `HardConstraint::MinSeparation` 被 auditor 检查，却没有被 projection/optimizer 真正执行。
- `LowerBound` / `UpperBound` / `Fixed` 会在 PAVA 之后单次覆盖，可能重新破坏层内分离；auditor 又不检查这些 bound。
- route feedback 保存的 flowchart 变量 `stable_id` 与真实 entity id 不一致，且横向图仍固定回写 `x`。
- `movable`、`AxisVariable`、`VarKind::Axis` 尚未形成有效求解语义。
- P3 阶段只守 P1 budget，不守 P2 budget；“分层优化”尚未完整实现。
- 多个 Recipe 仍通过覆盖 `execute()` 绕过自己的 `compile/solve/product`。
- router、group frame、SpaceBudget guard 和 architecture post-layout 仍能在 solver 之后改节点。

因此后续工作不应继续优先增加 objective 或调权重。正确顺序是：

```text
先修硬约束求解正确性
  → 收口 Recipe 生命周期
  → 收口节点写权与冻结类型
  → 删除旧目录/别名/重复图模型
  → 再做 active-set、双轴需求、增量布局等算法提升
```

## 1. 当前实际架构

### 1.1 已经落地的主链

当前无 group flowchart 的主链大致是：

```text
FlowchartLayout
  → FlowchartLayoutRecipe::execute
  → LayeredKernel::compute
      → effective DAG / FAS
      → rank
      → order
      → proper graph / dummy
  → assign_coordinates_brandes_koepf
      → BK 初值
      → CoordinateProblem builder
      → basic + structure objectives
      → kernel::coordinate::optimizer::solve
      → P0 audit
      → materialize NodeLayout
  → group bounds / canvas bounds / hints
  → LayoutPipeline
```

关键落点：

- 配方接口：`layout/kernel/recipe.rs`
- 坐标调用包装：`layout/kernel/coordinator.rs`
- 坐标模型：`layout/kernel/coordinate/model.rs`
- 投影：`layout/kernel/coordinate/projection.rs`
- 优化器：`layout/kernel/coordinate/optimizer.rs`
- 审计：`layout/kernel/coordinate/auditor.rs`
- 分层引擎：`layout/engines/layered/`
- 坐标 builder/objectives：`layout/engines/coordinate/`
- 图类型配方：`layout/recipes/`

### 1.2 已落地且应保留的设计

以下方向是正确的，不建议推倒重来：

1. `CoordinateProblem` 使用连续 `VarId` 和 `Vec` 热路径。
2. 层内 order 先冻结，再用一维 separation chain 表达 P0。
3. BK 收缩为 warm start 和 P3 稳定目标。
4. 目标统一表示为稀疏线性残差平方。
5. solver 使用固定迭代数、固定 backoff，不依赖 wall-clock。
6. architecture 与 flowchart 共享数学内核，不强行共享业务结构识别。
7. 非分层算法仍可使用自己的几何 solver，只统一 Recipe 生命周期。

### 1.3 与目标架构仍有差距的主链

当前后半段实际上仍是：

```text
Recipe / solver
  → LayoutResult（仍是 nodes/groups/edges/hints 混合容器）
  → node align / GroupFrame
  → SpaceBudget enrich
  → vertical rank gap 直接推节点
  → router
  → refine / budget guard
  → group frame 恢复与 architecture 专属重申
  → 再次重路由
  → route-feedback 重新 solve 后直接回写节点
  → NodeFreeze
  → edge finalize
```

这说明 `CoordinateSolver 是最终节点相对坐标唯一写者` 还没有在整条生命周期上成立。

## 2. P0：应优先修复的求解正确性问题

### 2.1 `hard` 中的 MinSeparation 没有进入投影

证据：

- `projection::project_bounds` 对 `HardConstraint::MinSeparation` 直接跳过。
- `auditor::audit_p0` 又会检查该约束。
- `route_feedback_resolve` 正在向 `enhanced.hard` 添加这种约束。

实际结果：

```text
route feedback 编译出 MinSeparation
  → solver 不执行
  → auditor 可能报错
  → 调用方仍可能继续消费结果
```

建议：

1. 不允许用一个枚举同时表示“可执行硬约束”和“只审计约束”。
2. 将一维差分约束统一编译为 `DifferenceConstraint` 图：

```text
x[right] - x[left] >= distance
```

3. 对层内相邻 separation 保留 PAVA 快路径。
4. 对额外同轴差分约束采用以下二选一：
   - 编译进对应 layer chain，前提是 left/right 在同层且顺序相邻或可传递折算；
   - 进入通用 active-set / Dykstra difference projection。
5. 跨层变量若没有同一物理轴上的顺序语义，不应生成 `left/right` separation；应生成 spacing demand 到正确 rank/scope。
6. solver 只有在所有 hard constraint 被实际投影或明确判定不可行后才能返回 `FeasibleSolution`。

退出判据：

- IR 中每一种 hard constraint 都有执行器。
- auditor 不再能发现“solver 明知但未执行”的约束类型。

### 2.2 PAVA 与 bound 的交集没有被正确求解

当前顺序是：

```text
project_all_layers
  → project_bounds 一次
```

如果 bound 把一个中间节点推到邻居附近，层内 separation 会被重新破坏。设计文档提到 Dykstra，但实现尚未落地。

建议：

1. 对单层的 chain + per-variable lower/upper/fixed 做专用 bounded isotonic projection。
2. 若首期不实现专用算法，则执行固定轮次 Dykstra：

```text
layer separation projection
  ↔ bounds/fixed projection
```

3. 轮次固定，结束后必须做完整 hard audit。
4. 未达到容差时返回 `Infeasible` 或 `ProjectionNotConverged`，不得仅以层内 separation 结果判断成功。

### 2.3 auditor 没有覆盖全部 P0

`audit_p0` 当前只检查：

- `layers[].separations`
- `hard::MinSeparation`

它没有检查：

- `LowerBound`
- `UpperBound`
- `Fixed`
- `movable == false`
- 非有限值
- layer vars 与 var_id 的一致性
- 同一变量的冲突 fixed

建议将审计拆成：

```text
validate_problem(problem)       # IR 结构合法性
audit_hard_feasibility(problem) # 解是否满足 P0
audit_objective_budgets(...)    # P1/P2 预算是否守住
```

并返回结构化诊断，而不是只返回 `Vec<String>`。

### 2.4 Infeasible 结果仍可能被物化

当前多个调用点取得 `solver_result.coordinates` 后直接写入节点，`status` 主要用于日志。

建议把 API 改成：

```rust
enum CoordinateSolveOutcome {
    Feasible(CoordinateSolution),
    Infeasible(InfeasibleReport),
}
```

`CoordinateSolution` 构造时已经通过完整 P0 audit；调用方拿不到“不可行但仍可随手物化”的坐标。

### 2.5 route feedback 的变量身份与坐标轴不可靠

flowchart builder 当前给真实变量生成 `n{petgraph_index}`，最终节点 map 使用真实 entity id。`route_feedback` 却用 `var.stable_id` 查找节点，因此 flowchart 路径无法可靠取回和回写真实节点。

同时 route feedback 固定读取和写入 `x`：

```text
center = node.x + width / 2
node.x = new_center - width / 2
```

对 left-to-right 图，CoordinateProblem 实际求的是 `y` 轴。

建议：

1. IR 使用稳定 typed id：

```rust
enum LayoutObjectId {
    Node(StableNodeId),
    Dummy(DummyId),
    RegionAxis(RegionId),
    MacroBlock(ScopeId),
}
```

2. `CoordinateProblem` 显式携带 `axis: Axis::X | Axis::Y`。
3. materializer 保存 `VarId → LayoutObjectId`，禁止通过格式化字符串反查。
4. route feedback 只产生 `SpacingDemand`，由原 Recipe 重新编译并物化；不得在 routing 层手写节点坐标。

## 3. P1：Recipe 与生命周期仍是过渡态

### 3.1 Recipe trait 的签名迫使复杂配方绕路

当前接口：

```text
compile(&Diagram) → Problem
solve(&Problem) → Solution
product(&Solution, &Diagram) → LayoutResult
```

主要问题：

1. `solve` 拿不到 prepared facts 或共享 kernels。
2. `compile` 无法返回结构化错误。
3. `audit` 无返回值，调用方不能阻止物化。
4. `product` 再次读取原始 Diagram，编译边界不完整。
5. `execute` 可任意覆盖，导致 trait 生命周期无法成为真实契约。

直接表现：

- flowchart 的 `product()` 是 `unreachable!`。
- ER 的 `product()` 是 `unreachable!`。
- state 的 `product()` 是 `unreachable!`。
- architecture 的 `solve()` 是占位，实际逻辑全在 `execute()`。
- state 的 `solve()` 与 `execute()` 甚至走两套不同调用路径。

建议接口：

```rust
pub trait LayoutRecipe {
    type Draft;

    fn name(&self) -> &'static str;

    fn compile(
        &self,
        input: &PreparedLayoutInput,
        kernels: &LayoutKernels,
    ) -> Result<Self::Draft, LayoutError>;

    fn solve(
        &self,
        draft: &mut Self::Draft,
        kernels: &LayoutKernels,
    ) -> Result<NodeLayoutProduct, LayoutError>;

    fn apply_spacing_demands(
        &self,
        draft: &mut Self::Draft,
        demands: &[SpacingDemand],
    ) -> DemandApplyReport;

    fn routing_spec(&self, product: &NodeLayoutProduct) -> RoutingSpec;
}
```

`execute()` 应只存在于统一 Coordinator，Recipe 不再覆盖。

### 3.2 `LayoutCoordinator` 名实不符

`kernel/coordinator.rs` 当前只做：

```text
CoordinateProblem → solve → audit
```

它不是文档 12 所定义的布局生命周期协调器。`FlowchartRecipeAdapter` 和 `ArchitectureRecipeAdapter` 也只提供日志名称。

建议：

1. 将现有类型重命名为 `CoordinateKernel::solve` 或普通函数。
2. 删除两个仅提供名字的 adapter。
3. 新建真正的 `LayoutCoordinator`，管理：
   - prepare
   - recipe compile
   - recipe solve
   - demand probe / bounded re-solve
   - hard audit
   - node/group freeze
   - routing handoff
4. Coordinator 不读取 diagram type 业务语义。

### 3.3 缺少稳定的 Prepared Input 和 Product 边界

当前 Recipe 直接读取 `Diagram`，并直接生成混合态 `LayoutResult`。因此：

- graph index 在 flowchart/architecture/state 中重复构建；
- node metrics、声明序、scope、edge identity 没有统一事实源；
- route feedback 只能把 `CoordinateProblem` 塞进 hints 反向恢复状态；
- `LayoutResult` 同时表示候选节点、冻结节点、已路由边和最终产品。

建议引入：

```text
PreparedLayoutInput
  - StableGraph
  - NodeMetrics
  - GroupTree / ScopeTree
  - DeclarationOrder
  - UserConstraintSet
  - Direction

NodeLayoutProduct
  - nodes
  - groups
  - topology metadata
  - spacing state
  - routing contract
  - diagnostics

FrozenNodeProduct
  - 只读 nodes/groups
  - routing contract
  - stable identity maps
  - deterministic fingerprint
```

不要再通过 `LayoutHints` 装入可变求解器状态来跨阶段通信。

### 3.4 freeze 仍是旁路守卫，不是类型状态

当前同时存在两种冻结机制：

- `kernel/frozen.rs`：单节点 wrapper + map snapshot。
- `edge_stages.rs::NodeFreeze`：对 `LayoutResult` 做 fingerprint。

但 router 的签名仍是：

```text
route(&Diagram, LayoutResult) → LayoutResult
```

也就是说，路由器在类型上仍拥有节点写权。

建议：

```text
NodeLayoutProduct
  → freeze_nodes()
  → FrozenNodeProduct
  → RoutingCoordinator::route(&FrozenNodeProduct)
  → RoutedEdgeProduct
```

`FrozenNodeProduct` 不提供 mutable node map。整体画布平移通过唯一的 `translate_all` 同步变换 nodes/groups/edges/annotations/labels。

### 3.5 solver 后仍有节点写者

当前可见的写者包括：

- `route_feedback::apply_pre_route` 的 vertical rank gap。
- `route_feedback` 的 re-solve 回写。
- `demand/space_budget_guard.rs`。
- `group/frame` 的 restore/realign。
- `recipes/architecture/post_layout.rs`。
- architecture coordinate 后的 infrastructure layer 居中。
- `snap/grid_snap.rs` 中部分节点量化逻辑。
- refine/push 与残余 overlap 路径。

建议建立正式写权清单：

```text
compile/analyze        只产 facts/intents
solve/compose          唯一相对坐标写者
global finalize        只允许刚体平移或统一合法量化
demand feedback        只新增 intent 后重解
freeze                 封闭节点与组几何
route/refine/postroute 只能改边
```

architecture 的 infrastructure 居中、hub centroid、cross-scope pendant 必须编译为 objective/constraint，或明确属于 composition solver；不能在 CoordinateSolver 之后直接改节点。

## 4. P1：坐标模型和 optimizer 需要补全

### 4.1 虚拟轴模型尚未真正落地

`AxisVariable` 已定义，但 `CoordinateProblem` 没有 axes 集合；`VarKind::Axis` 也没有实际 builder 使用。

结果是文档中最重要的：

- split–join region axis
- fan mirror axis
- architecture hub/client centroid axis
- macro alignment axis

仍主要被退化为节点间 pair objective。

建议：

1. 删除独立 `AxisVariable` 结构，统一成 `Variable`：

```rust
enum VariableKind {
    Node(StableNodeId),
    Dummy(DummyId),
    Axis(RegionId),
    Band(RankId),
    MacroBlock(ScopeId),
}
```

2. axis 不属于 layer separation chain，但可以参与 objective。
3. 每个无硬锚 component 增加 gauge constraint，避免整体平移自由度导致漂移。
4. StructureModel 输出 axis identity 和 membership，Recipe builder 只负责转成残差。

### 4.2 分层优化只实现了一半

当前 optimizer：

- P2/P3 会检查 P1 budget；
- P3 不检查 P2 budget；
- `p1_tolerance` 默认值为 0，当前没有稳定的外部赋值证据；
- `best_coords` 虽然记录，却没有在 phase 末恢复；
- 接受条件允许 `best_loss + epsilon`，最终坐标可能不是记录到的 best。

建议：

```text
solve P1 → 保存 best P1 + budget
solve P2 → 同时约束 P1 budget，保存 best P2 + budget
solve P3 → 同时约束 P1/P2 budget
每个 phase 返回该 phase 的 best feasible snapshot
```

budget 应按问题尺度归一化：

```text
tolerance(priority)
  = normalized_physical_error²
  × active_term_count
```

不要用巨型权重模拟优先级，也不要使用固定绝对 loss。

### 4.3 缺少 Problem canonicalization 和 validation

建议 solve 前统一：

1. 检查 `var_id == index`。
2. 检查 initial 长度。
3. 检查 layer vars 不重复。
4. 检查 separation 长度。
5. 检查所有 coefficient var id 合法。
6. 合并同一 term 内重复系数。
7. 删除零系数与零权重 term。
8. 拒绝 NaN/Infinity/负尺寸/负权重。
9. 按稳定 `(priority, source, vars)` 排序 objective。
10. 建立 typed provenance id，避免诊断依赖静态 note 字符串。

### 4.4 求解结果诊断过于粗糙

当前主要诊断是：

- status
- P1/P2/P3 loss
- iterations
- max violation
- `Vec<String>`

建议增加：

```text
problem_signature
component_count
active_separation_count
projection_rounds
phase_iterations[P1/P2/P3]
phase_stop_reason
objective_loss_by_source
axis_deviation_by_region
hard_violation_by_source
infeasible_core
gauge_anchor
warm_start_delta
materialization_delta
```

这些数据应进入结构化 `LayoutDiagnostics`，日志只是可选 view。

## 5. P2：性能、扩展性与代码结构

### 5.1 builder 存在重复和 O(V²) 提取

`engines/coordinate/builder.rs` 中：

- `build_coordinate_problem`
- `build_with_mapping`

包含大段重复构造逻辑。

`extract_centers` 又通过 stable-id 字符串对每个节点扫描全部 vars。

建议：

1. 只保留一个 builder，始终返回 `BuildOutput`。
2. `BuildOutput` 保存双向连续映射：

```text
object_to_var
var_to_object
```

3. materialize 为 O(V)。
4. `stable_id` 只用于诊断，不作为热路径 join key。

### 5.2 optimizer 每轮有不必要分配

当前每个 phase/iteration 会构造或克隆：

- priority term 引用 Vec
- gradient
- candidate
- previous coordinates
- P1 term Vec

建议将 `CoordinateProblem` 编译成 `CompiledCoordinateProblem`：

```text
terms_by_priority
coefficient CSR/flat spans
layer projection workspace
gradient/candidate/best reusable buffers
component ranges
```

首期不需要并行；固定 component 顺序串行即可保持确定性。

### 5.3 增加 component decomposition

依据 objective/hard constraint 的变量关联图分量求解：

1. layer separation 会连接同层相邻变量。
2. structure objective 会连接跨层节点和 axis。
3. 互不相连的 weak components 可独立求解。
4. component 按最小 stable object id 排序。
5. 求解后由 composition/packing kernel 安排 component 间距。

收益：

- 降低大图迭代成本。
- route demand 可只重解受影响 component。
- diagnostics 可定位到局部结构。

### 5.4 引入 active-set 后端，但不改变 IR

Projected gradient 可继续作为稳定基线。中期可增加：

```text
PAVA 找 active separation blocks
  → 每个 block 压缩成平移变量
  → 构建小型稀疏二次问题
  → 解 block/axis 位移
  → 更新或释放 active constraints
```

建议触发条件：

- projected optimizer 达到 max iteration；
- active separation 比例高；
- axis objective 较多；
- component 变量数超过阈值。

无论后端如何变化，输入仍是同一个 `CompiledCoordinateProblem`。

### 5.5 主轴与横轴需求应统一成 AxisProblem，而不是只处理 x

当前统一 solver 主要解决 cross-axis 坐标；竖向 rank gap 仍由外部推点。

建议把内核抽象成一维 `AxisProblem`：

```text
CrossAxisProblem
  - 层内节点顺序
  - split/join/centroid objectives

MainAxisBandProblem
  - rank band 起点/高度
  - rank gap demand
  - label/feedback/loop 所需带宽
  - scope-local band constraints
```

两者共享：

- variable/object identity
- difference constraints
- projection
- objective residual
- diagnostics

但由 Recipe 决定先后顺序和语义。这样可删除 `enforce_vertical_rank_gaps` 这一类 solver 外写者。

### 5.6 StableGraph 尚未真正统一

当前仍并存：

- Sugiyama 的 petgraph + proper graph NodeIndex。
- architecture 的字符串 `GraphIndex`。
- route feedback 和 hints 中的字符串 map。

建议逐步引入 `StableGraph`：

1. declaration order 生成稳定 NodeId/EdgeId。
2. `HashMap<String, NodeId>` 只做查询。
3. Recipe 编译 effective graph view。
4. LayeredKernel、CoordinateKernel、RoutingContract 都使用同一 NodeId/EdgeId。
5. proper graph 的 dummy id 显式保存原 edge id 与 segment index。

这会同时解决 route feedback identity、跨模块 join 和确定性问题。

## 6. P2：目录与 API 清理

### 6.1 旧路径和兼容 re-export 不应长期保留

`layout/mod.rs` 当前仍包含大量“过渡期/向后兼容”别名：

- `demand::band as edge_band_demand`
- `group::frame as group_frame`
- `quality::lint` / `quality::metrics`
- `pipeline::plan` / `pipeline::registry`
- `snap::grid_snap` / `snap::canvas_finalize`
- `routing as edge`
- `recipes as node`
- `engines::layered as sugiyama_v2`

仓库规则已经明确无需向后兼容。长期保留会造成：

- 搜索结果重复；
- 新代码继续依赖旧名；
- 文档路径与真实所有权不一致；
- `layout/node/` 旧目录和新 `recipes/engines` 同时存在，阅读时难以判断权威实现。

建议：

1. 以真实模块路径为唯一入口。
2. 一次性改完 crate 内引用后删除别名。
3. 删除不参与当前 module tree 的旧 `layout/node/` 重复文件。
4. 删除 orphan tests 和仅为兼容存在的 wrapper。
5. 更新核心手册 §4 的代码落点。

### 6.2 `common/` 仍需继续收缩

`engines/common` 当前包含 graph、pack、overlap、group bounds、canvas bounds 等多类能力。

建议按不变量归属：

```text
kernel/graph
kernel/layered
kernel/coordinate
kernel/compose
kernel/demand
model
```

只有满足“至少两个 Recipe 使用、无图类型分支、可独立说明不变量”的模块才进入 Kernel。

### 6.3 `LayoutResult` 应退回最终 DTO

`LayoutResult` 当前被用作所有阶段的可变工作区，并通过 `hints` 携带：

- coordinate problem
- frozen nodes
- route annotations
- group routing state
- space budget
- debug stats

建议将其限制为最终渲染 DTO。内部使用：

```text
LayoutDraft
NodeLayoutProduct
FrozenNodeProduct
RoutingProduct
FinalLayout
```

阶段状态不再通过可选 hints 猜测。

## 8. 分阶段执行计划

### L0：修复硬约束执行语义

范围：

1. 实现所有 hard constraint 的真实投影。
2. auditor 覆盖 bounds/fixed/finite。
3. infeasible 不再物化。
4. 修复 best snapshot 和 P1/P2 budget。
5. 给 CoordinateProblem 增加 axis 与稳定 object mapping。

退出判据：

- solver 返回 Feasible 时，完整 P0 audit 必过。
- route demand 不再生成“只审计、不执行”的约束。

### L1：统一 Recipe 真生命周期

范围：

1. 引入 `PreparedLayoutInput`。
2. 修改 Recipe trait。
3. flowchart 首先移除 bypass。
4. 再迁 ER、state。
5. architecture compile 产出真实 hierarchical draft。
6. sequence/circular/mindmap 保留各自 solver，但走同一生命周期。

退出判据：

- 所有 Recipe 都真实执行 compile → solve → product。
- 不存在 `unreachable!("product called directly")`。
- architecture 的 `solve()` 不再是占位。

### L2：建立真正的 LayoutCoordinator

范围：

1. 重命名/删除现有坐标 adapter coordinator。
2. Coordinator 管 prepare、solve、demand feedback、audit、freeze。
3. route feedback 只返回 demand。
4. feedback 最多固定 1–2 轮。
5. re-solve 后重建 group product 和 routing contract。

退出判据：

- 所有节点移动可追溯到一次 Recipe solve/compose。
- route/refine 不再直接写节点。

### L3：双轴空间需求收口

范围：

1. `SpaceBudget` 拆为 `SpacingDemandStore` 与 `RoutingContract`。
2. 横向 pair demand 编译进 cross-axis problem。
3. rank band demand 编译进 main-axis band problem。
4. 删除 horizontal/vertical gap 直接推点。
5. group frame 恢复改为 composition solve，而不是 route 后补救。

退出判据：

- 节点冻结后不再有 budget guard。
- 布局空间需求和路由消费契约是两个只读数据对象。

### L4：Architecture 语义目标化

范围：

1. infrastructure row 居中进入 objective。
2. hub/client centroid 进入 objective。
3. group sizing/containment 进入 macro problem。
4. cross-scope pendant 进入 composition intent。
5. 删除 architecture post-layout node mutation。

退出判据：

- architecture 相对坐标只有 coordinate/compose kernel 写入。
- pipeline 不再出现 `algo == "architecture"` 节点修复分支。

### L5：性能和可观测性

范围：

1. compiled sparse problem。
2. reusable workspace。
3. component decomposition。
4. active-set 后端。
5. typed diagnostics。
6. 稳定 problem/result signature。

### L6：删除过渡层

范围：

1. 删除 `layout/node/` 旧重复树。
2. 删除兼容 re-export。
3. 删除无调用方 `LayoutRecipeDyn`。
4. 删除旧 overlap/push/align pass。
5. 更新文档 13 状态与核心手册时序。

## 9. 建议验收口径

### 9.1 架构不变量

1. Recipe compile 不写坐标。
2. Kernel 不读取 `DiagramType`。
3. 同一节点的相对坐标只由 solve/compose 物化一次。
4. demand feedback 不接收 mutable nodes。
5. freeze 后 router/refine 无法取得 mutable nodes。
6. final canvas transform 原子地平移所有几何和 annotation。

### 9.2 求解不变量

1. 所有 hard constraint 都有执行器。
2. Feasible 结果完整 P0 violation 为 0。
3. rank/order 不被 coordinate solver 修改。
4. P3 不得突破 P1/P2 budget。
5. 同输入 problem signature 与 coordinates 完全确定。
6. 无随机数、无 wall-clock timeout、WASM 路径无裸 `std::time`。

### 9.3 质量指标

建议长期记录：

```text
hard_violation_count
infeasible_problem_count
solver_degraded_count
objective_loss_p1/p2/p3
axis_deviation
mirror_deviation
active_separation_ratio
component_count
solver_iterations
coordinate_write_after_freeze
route_feedback_rounds
materialization_delta
```

临时全局优化期间质量轨不阻挡迁移，但穿组与确定性仍是硬底线。

---

## 10. 不建议做的事

1. 不继续给当前 optimizer 增加 magic weight 来掩盖硬约束缺口。
2. 不保留“新 Recipe + 旧 engine execute bypass”长期双轨。
3. 不把 sequence/circular/mindmap 强塞进 CoordinateSolver。
4. 不建立动态阶段 DSL 或十几个 hook 的万能 Recipe。
5. 不让 Kernel 接受 `DiagramType` 或 entity 类型分支。
6. 不在 route/refine 后追加新的节点补救 pass。
7. 不使用环境变量作为正式算法配置或架构开关。
8. 不为兼容旧路径保留转发模块。

## 11. 推荐优先级

近期必须完成：

1. hard constraint 投影与 auditor 一致。
2. route feedback identity/axis 修正并改为 demand-only。
3. Recipe 生命周期真实化。
4. freeze 类型边界。
5. architecture solver 后写者清零。

1. 双轴 AxisProblem。

5. StableGraph 统一。

后期能力：

1. 增量布局与 warm start。
2. 用户 pin/容器 fixed bounds。

4. 上一次布局稳定性 objective。
5. playground 可视化 solver trace。

## 12. 最终完成定义

完成本轮后，布局模型应满足：

1. `PreparedLayoutInput` 是所有 Recipe 的统一事实入口。
2. 每个图类型拥有真实、可独立阅读的 Recipe。
3. 分层、坐标、组合、需求是独立 Kernel。
4. 所有 hard constraint 被 solver 真正执行。
5. Coordinate/Composition Kernel 是节点相对坐标唯一写者。
6. route feedback 只产生 demand，且重解有界。
7. freeze 后节点和组在类型上不可修改。
8. `LayoutResult` 只作为最终 DTO。
9. 不再存在旧 `layout/node/` 双轨和兼容 alias。
10. 架构正确性依赖 typed state 和 hard audit，而不是 debug fingerprint 与日志约定。
