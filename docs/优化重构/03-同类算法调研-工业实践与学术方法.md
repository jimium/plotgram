# 同类算法调研：正交路由与分层布局的工业实践

> 日期：2026-07-20
> 目的：梳理 ELK、yFiles、Graphviz、draw.io 等同类产品的核心算法，提炼可借鉴的设计

---

## 1. ELK (Eclipse Layout Kernel)

### 1.1 分层布局（ELK Layered）

ELK Layered 是 Sugiyama 方法的工业级实现，支持 140+ 配置选项。

**核心阶段**：
1. **Cycle Breaking**：DFS-based + 用户约束
2. **Layering**：Network Simplex（最长路径 + 紧凑化）
3. **Crossing Minimization**：Layer-by-layer sweep + 多层迭代
4. **Node Placement**：Brandes-Köpf 四趟 + 可选 Simple / Linear Segments
5. **Edge Routing**：多种策略可选

**关键设计决策**：
- **Edge Routing 与 Node Placement 解耦**：先定节点坐标，再独立路由边
- **Port Constraints**：端口方向约束在布局阶段就注入，而非路由后修复
- **Spacing 系统**：`spacing.nodeNode`、`spacing.edgeNode`、`spacing.edgeEdge`、`spacing.nodeNodeBetweenLayers` 多层间距配置
- **Self-loops**：有专用阶段，在 crossing minimization 后、edge routing 中处理

**可借鉴**：
- 间距系统的分层设计（node-node / edge-node / edge-edge 独立配置）
- Port constraint 前置（布局阶段就考虑端口方向）
- 自环与主路由的统一框架

### 1.2 边路由策略

ELK 支持多种边路由：
- **Polyline**：简单折线（类似当前 flowml）
- **Orthogonal**：正交路由（A* on grid + channel assignment）
- **Splines**：B-spline 曲线
- **Libavoid**：集成 libavoid 库的正交/多段线路由

**ELK Orthogonal 的核心**：
- 基于 **channel** 的路由：将节点间空间划分为水平/垂直 channel
- 每个 channel 有容量（可容纳的边数）
- 边被分配到 channel 后，在 channel 内按 lane 排列
- 全局优化：最小化总弯折数 + 通道拥塞

**Libavoid 集成（2022 新增）**：
- 基于 Wybrow 的 orthogonal connector routing 算法
- 构建 obstacle-avoiding visibility graph
- 支持固定节点位置的路由（适合交互式编辑器）
- 路径质量优于 ELK 原生 orthogonal

### 1.3 对 flowml 的启示

| ELK 特性 | flowml 现状 | 差距 |
|----------|------------|------|
| 间距分层配置 | 单一 NODE_OBSTACLE_PAD | 中 |
| Port constraint 前置 | 路由后 stub_fix 修复 | 大 |
| Channel-based 全局路由 | 逐边贪心 | 大 |
| 自环统一框架 | 独立模块 | 中 |
| 140+ 配置选项 | 2 个选项 | 小（非核心） |

## 2. yFiles / yWorks

### 2.1 OrthogonalEdgeRouter

yFiles 的 `OrthogonalEdgeRouter` 是商业级正交路由的标杆：

**核心算法**：
- **Channel-based routing**：将绘图区域划分为 channel 网络
- **Path finding**：在 channel 网络上搜索最优路径（考虑长度、弯折、拥塞）
- **Nudging**：多轮迭代分离平行边束
- **Bus routing**：多边共享总线（hyperedge）

**关键特性**：
- **Scope 概念**：路由范围可以是全图或子图（增量路由）
- **Edge group**：同源/同宿边自动分组，共享 trunk
- **Minimum distance**：边-节点、边-边、边-组的最小距离硬约束
- **Self-loops**：在统一框架内处理，自动选择最优方向和尺寸
- **Crossing minimization**：路由阶段有显式交叉最小化

**Nudging 细节**：
- 检测平行段束（同方向、同通道、间距 < 阈值）
- 按束中心对称分布
- 渐进式偏移（非一次性平移）
- 支持不同间距的束（语义相关边更近）

### 2.2 对 flowml 的启示

| yFiles 特性 | flowml 现状 | 可借鉴度 |
|------------|------------|---------|
| Channel 网络全局路由 | 候选枚举 | 高（Phase B） |
| 渐进式 nudging | 一次性 lane shift | 高 |
| Bus routing | semantic_trunk_merge | 中（已有基础） |
| 自环统一框架 | 独立模块 | 高（Phase A） |
| 交叉最小化 | 无 | 高（Phase C） |
| 最小距离硬约束 | 软惩罚 | 中 |

## 3. Graphviz (ortho 模式)

### 3.1 算法特征

Graphviz 的 `ortho` 路由模式相对简单：
- 基于 **visibility graph** 的路径搜索
- 障碍物膨胀后构建可见性图
- Dijkstra 最短路径
- 无全局通道分配
- 无 nudging

**优点**：
- 实现简单，路径质量有下界保证（最短路径）
- 自环在 visibility graph 中自然处理

**缺点**：
- 无平行边分离（多边重叠）
- 无 bus/trunk 合并
- 无组感知
- 性能在大图上较差（O(n³) visibility graph）

### 3.2 对 flowml 的启示

- Visibility graph 是路径搜索的可靠 fallback
- 自环可以通过 visibility graph 自然处理（无需特殊模块）
- 但纯 VG 缺乏美学优化（无 nudging、无 bundling）

## 4. draw.io / mxGraph

### 4.1 路由策略

draw.io 使用 **Manhattan routing**（曼哈顿路由）：
- 简单的正交路径生成（L 形 / Z 形 / U 形）
- 障碍物检测 + 绕行
- 用户可手动调整 waypoint
- 无全局优化

**特点**：
- 交互式优先：用户拖拽 > 自动布局
- 简单但可预测
- 自环：固定矩形环，用户可调

### 4.2 对 flowml 的启示

- 简单路由 + 用户交互 是一种有效策略
- 但对 AI 生成场景（无用户交互），自动质量更重要
- flowml 的定位（AI agent 生成）需要比 draw.io 更高的自动路由质量

## 5. Wybrow Orthogonal Connector Routing (学术)

### 5.1 核心算法

Wybrow, Marriott, Stuckey (2009) 提出的正交连接器路由：

**算法步骤**：
1. **Obstacle inflation**：将障碍物按最小间距膨胀
2. **Visibility graph construction**：
   - 从每个障碍物顶点发射水平/垂直射线
   - 射线碰到另一个障碍物或边界时停止
   - 形成正交可见性图
3. **Path search**：
   - 在可见性图上用 Dijkstra/A* 搜索
   - 边权 = 线段长度 + bend_cost（转弯惩罚）
   - 起点/终点通过 "escape edges" 连接到图
4. **Path simplification**：去除冗余折点

**关键创新**：
- **Sparse visibility graph**：不是全量 O(n⁴)，而是只保留"有用"的可见性边
- **Bend-aware cost**：转弯惩罚使路径自然偏好少弯折
- **Obstacle-avoiding guarantee**：路径保证不穿越膨胀后的障碍物

### 5.2 对 flowml 的适用性

**高度适用**：
- flowml 的障碍物（节点、组）都是矩形，与论文假设一致
- 正交路径是 flowml 的核心需求
- 弯折惩罚直接对应"不必要弯折"问题
- 障碍物膨胀直接对应"贴边"问题

**需要扩展**：
- 论文假设固定节点位置（flowml 也是路由前固定节点）
- 论文不处理 bus/trunk 合并（flowml 需要额外阶段）
- 论文不处理组边框（需要将组视为特殊障碍物）
- 性能：大图需要稀疏化策略

## 6. 算法对比总结

| 维度 | flowml | ELK | yFiles | Graphviz | Wybrow |
|------|--------|-----|--------|----------|--------|
| 路径搜索 | 候选枚举 | Channel + A* | Channel + PF | Visibility | Visibility |
| 全局优化 | 无 | Channel 分配 | Pool-based | 无 | 无 |
| 平行分离 | Lane shift | Nudging | 渐进 Nudge | 无 | 无 |
| 自环 | 独立模块 | 统一框架 | 统一框架 | VG 内 | VG 内 |
| 组感知 | 走廊三段式 | 透传 | Group-aware | 无 | 无 |
| 交叉最小化 | 无 | 有 | 有 | 无 | 无 |
| 增量路由 | 支持 | 部分 | 支持 | 无 | 支持 |
| 确定性 | 强 | 强 | 强 | 强 | 强 |

## 7. 推荐技术路线

基于调研，推荐 flowml 的技术演进路线：

### 短期（保持现有架构）
- 自环纳入主路由框架（参考 ELK/yFiles 统一处理）
- 组边框硬约束（参考 yFiles minimum distance）
- 弯折惩罚调优（参考 Wybrow bend-aware cost）

### 中期（引入新路径搜索）
- **正交 Visibility Graph**（参考 Wybrow 2009）作为主路径搜索
- 保留现有 scoring 作为路径质量评估（VG 找到候选后仍用 scorer 选最优）
- 走廊系统作为 VG 的"高速公路"（走廊坐标上的边权降低）

### 长期（全局优化）
- Channel assignment（参考 ELK）替代逐边贪心
- 渐进式 nudging（参考 yFiles）替代一次性 lane shift
- 显式交叉最小化阶段
