② 层当初想解决什么？

代码注释写得很清楚：这是一套 空间契约（Space Contract）—— 布局预留 → 路由消费 → 后处理守约，避免末端「刚好不碰」式补丁。

  • 共用对象：不绑死 Sugiyama；flowchart / architecture 都可往 hints.space_budget 塞契约。
  • 共用操作：对任意 HashMap<id, NodeLayout> 做 enforce_horizontal_gaps。
  • 共用时序：挂在 pipeline 的预路由 / refine 路径，而不是某个算法内部。
  • 理想目标：第一层布局就把缝留够；② 只守约、少补丁。
  • 现实落点：第一层常留不够 → ② 变成「布局之后的通用推节点补丁 + 布局↔路由反馈环」。

理想设计（契约）

SpaceBudget 更像「需求单」，不是「随便推一下」：

① 节点布局尽量预留缝 ↓ 写入 SpaceBudget（pair_gaps…） ② 预路由：压力 enrich + 守约 ↓ ③ 路由：按 clearance / corridor 消费 ↓ ④ 后处理：检查契约，失败才兜底

所以：是的，它被设计成第一层之后的共享层；但本意是「通用空间契约」，不完全等于「万能补丁箱」。

现实摩擦（为何和文档冲突）

当第一层（如 Sugiyama coordinate）已经为对称/主轴摆好节点时：

  • enforce_horizontal_gaps 再推一层 → 破坏对称
  • route feedback / refine 再 enforce → 多写者
  • 统一坐标求解若只改①，②仍可把结果推歪

文档方案要把②从「直接推点」收成「只产 SpacingIntent，有界回到①重解」。

直接回答你的问题

大体正确：SpaceBudget / route feedback 被放在 pipeline 共享层， 就是为了在「任意第一层节点布局算法」之后，用同一套机制补缝、消化路由压力、在布局与路由之间反馈。

更精确一点：当初目标不完全是「事后万能补丁」，而是想建成跨算法的 空间契约（预留 / 消费 / 守约）。只是实践中，第一层常做不到一次留够， 于是②层越来越像通用补丁；这也是现在和「单一坐标写者」打架的原因。
