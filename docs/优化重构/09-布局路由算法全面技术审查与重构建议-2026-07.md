## 1. 当前算法架构概述

### 1.1 总体管线

```
Diagram (AST)
  → LayoutPipeline::run()
      ├── strategy.compute()          ← 节点布局（按图类型分派）
      ├── apply_node_frame()          ← grid_snap + group_frame
      └── run_routing_pipeline()
            ├── pre-route             ← 边路由策略选择
            ├── router.route()        ← 边路由主体
            ├── refine                ← 穿障检测 + 节点推开
            ├── snap_and_repulse      ← 像素量化 + 组边框排斥
            ├── sanitize_ext          ← 激进消毒（merge_overshoot=true）
            ├── enforce_separation    ← 正反向 gap + dock 共锚
            └── label_resolve         ← 最终标签避让
  → canvas_finalize
```

落点：`crates/plotgram-core/src/layout/pipeline.rs`（465 行）

### 1.2 布局算法层

| 算法 | 适用图类型 | 落点 | 核心方法 |
|------|-----------|------|---------|
| Sugiyama V2 | flowchart / state / ER | `layout/node/sugiyama_v2/` | rank(832L) → order(461L) → coordinate(1470L) → postprocess(130L) |
| Architecture V2 | architecture | `layout/node/architecture_v2/` | two_phase(macro_block+intra) → group_layout_hint(776L) → post_layout(631L) |
| Mindmap | mindmap | `layout/node/mindmap.rs`(1240L) | 递归树布局 + 深度感知 + 左右分区 |
| Force-directed | 通用 | `layout/node/force_directed.rs`(1119L) | Barnes-Hut 力导向 |
| Circular | 通用 | `layout/node/circular/`(943L) | 圆形布局 |
| Sequence | sequence | `layout/node/sequence.rs`(509L) | 生命线 + 消息排序 |

**Sugiyama V2 关键特性**：
- Brandes-Köpf 四趟坐标分配 + 中位数融合
- `enforce_fan_symmetry()`：Phase C1 新增，同源 fan-out 对称约束
- `align_pendants_under_anchors()`：V3b 悬挂对齐
- spine_weight=1.5 主干加权 compaction

**Architecture V2 关键特性**：
- 两阶段布局：macro_block（组级）+ intra（组内 Sugiyama）
- 组布局提示（group_layout_hint）：组间距、排列方向
- 跨作用域 pendant 对齐（post_layout）

### 1.4 正交路由管线详细阶段

```
route_edges_orthogonal_inner()  ← run.rs (743L)
  │
  ├── Phase 1+2: phase_port_slot()
  │     ├── 端口选择（几何规则 + Port Solver 可选）
  │     ├── Slot 分配（同侧均匀分布）
  │     └── 平行边偏移计算

  │
  ├── Phase 4: phase_route_edges()
  │     ├── 候选枚举（直连/单折/双折/走廊/外环）
  │     ├── OVG fallback（Dijkstra 最短正交路径）
  │     ├── Channel Planner 候选注入

  │
  ├── Phase 4b: replan_slots()        ← slot 排序修正

  ├── Phase 4e: phase_stub_fix()      ← 反向 stub 端口翻转
  ├── Phase 4f: phase_lane()          ← 车道分离 + 正反向 gap

  ├── S4: monitor corridor reroute    ← 监控枢纽边外环重路由
  ├── Phase 4g: phase_sanitize()      ← 保守消毒（collapse + simplify）
  ├── S4.x: escape repair             ← sanitize 后穿模修复
  ├── B.2: monitor local trunk        ← 局部 trunk 合流
  ├── C2: crossing_reduction()        ← 路由后交叉消解

```

## 2. 现存问题诊断

### 2.1 已解决问题（Phase A-D）

| 原问题 | 解决方案 | 状态 |
|--------|---------|------|
| 自环固定右上角 | 空间感知方向选择 + 自适应尺寸 | ✅ 已解决 |
| 边贴组边框 | 走廊最小宽度 + scoring 惩罚增强 + 硬排斥 | ✅ 已解决 |
| 不必要弯折 | BEND_PENALTY 32 + 准直连候选 + straighten 扩展 | ✅ 已解决 |
| 回环边抢道 | 侧通道预留 + feedback 延后路由 | ✅ 已解决 |
| 候选枚举路径质量上限 | OVG Dijkstra 全局最优路径 | ✅ 已解决 |
| Fan-out 不对称 | enforce_fan_symmetry() 坐标修正 | ✅ 已解决 |
| mindmap 路由性能 | 跳过 ObstacleIndex O(n²) 构建 | ✅ 已解决 |

### 2.2 部分解决问题

**C2 交叉最小化**：
- 检测算法已统一（含共线端点检测），已重新启用
- 但 `shifted_segment_clearance()` 约束（平行段 ≥10px，非平行 ≥8px）阻止了所有平移
- 根因：密集图中安全空间不足，任何平移都会违反 clearance
- 影响：代码就绪但无实际交叉消解效果

**Port Solver**：
- 已默认开启，MIN_IMPROVEMENT=2.0 防退化
- 但当前 benchmark 集上无实际变更（几何初始分配已足够好）
- 根因：OVG 路径搜索已能处理大多数端口配置，Port Solver 的边际收益极小

### 2.3 仍存在的结构性问题

#### 2.3.1 后处理层过厚（写权竞争）

当前正交路由后处理仍有 5+ 阶段串行修改边几何：

```
replan_slots → straighten → reroute → stub_fix → lane → sanitize
```

每个阶段都可能：
- 触发重路由，引入新弯折
- 修改前一阶段的成果（写权竞争）
- 增加调试难度和不确定性

**具体写权冲突案例**（手册 §1 已记录）：
- sanitize 的 `ensure_outward_stub` 会吃掉 S4 外环 U 形 → 需要 S4.x 修复
- snap_and_repulse 抖回微台阶 → 需要 sanitize_ext 再消一次
- lane_assignment 的 gap 调整可能被后续 sanitize 的 collapse 覆盖

#### 2.3.2 逐边贪心 vs 全局优化

当前路由仍是逐边贪心：
- Channel Planner 仅提供候选坐标，不强制路由结果
- 先路由的边占据通道，后路由的边避让
- `reroute_conflicting_edges` 是事后修复，非全局优化
- 没有全局通道容量约束（同通道多边仅靠 lane 偏移）

**对比 ELK**：
- ELK 有独立的 channel assignment 阶段，全局分配通道坐标
- 通道容量约束：同通道多边按 lane 严格分离
- 交叉最小化在路由阶段而非后处理

#### 2.3.3 OVG 大图性能

- ecommerce: 34ms vs 无 OVG 33ms（+4%）
- 根因：OVG 构建 O(n² log n) + 每条 degraded 边 Dijkstra O(E log V)
- 当前缓解：空间过滤（bbox+80px）+ 零克隆搜索
- 残余问题：固定 80px margin 不自适应，大图过滤效果有限

#### 2.3.4 既有单测失败（15 个）

当前 `cargo test -p plotgram-core --lib` 有 15 个失败：
- 正交路由测试（bundling、coordinate switch、concentrate mode）
- grid_snap 测试
- architecture 布局测试
- SVG 渲染测试

这些是 Phase A-D 改动引入的回归，需要修复以稳定测试基线。

#### 2.3.5 有机路由 ObstacleIndex（非 mindmap）

- mindmap 已跳过（Phase D4），但 flowchart/architecture 使用有机路由时仍构建
- ObstacleIndex::build() 对角点对做 O(n²) 可见性预计算
- 63 节点 → 252 角点 → 31,626 对 → 87ms
- 非 mindmap 场景确实需要穿障检测，但可改为懒构建

## 3. 重构建议

### 3.1 P0：短期修复（1-2 周）

#### P0-1. 修复 15 个既有单测失败

**目标**：测试基线稳定，所有 `cargo test -p plotgram-core --lib` 通过。

**方法**：
- 逐个分析失败原因（多数是 Phase A-D 改动后期望值未更新）
- 区分「行为正确但期望过时」vs「真实回归」
- 更新测试期望或修复代码

**验证**：`cargo test -p plotgram-core --lib` 全绿。

#### P0-2. C2 交叉最小化 clearance 约束优化

**目标**：在稀疏图上产生实际交叉消解效果。

**当前问题**：
- `MIN_EDGE_CLEARANCE = 8.0`（非平行）/ `10.0`（平行）过于严格
- 密集图中任何平移都违反 clearance → 所有尝试被拒绝

**方案**：
- 将 clearance 检查从「全局所有边段」缩小为「仅被平移段的局部邻域」
- 引入渐进式 clearance：先尝试严格约束，失败后放松到 6px
- 对 product-gate 中 crossings.total > 0 的图（如 typical-microservice: 9）定向验证

**落点**：`edge_routing_orthogonal/crossing_reduction.rs` 的 `shifted_segment_clearance()`

**验证**：typical-microservice crossings 9 → ≤7，product-gate 质量轨不退化。

#### P0-3. 非 mindmap 有机路由 ObstacleIndex 懒构建

**目标**：flowchart/architecture 使用有机路由时，仅在确实需要穿障检测时才构建 ObstacleIndex。

**方案**：
- 第一遍：快速检测所有边是否可能穿障（直线段 vs 节点 bbox 粗检）
- 若无边可能穿障 → 跳过 ObstacleIndex 构建
- 若有 → 构建完整 ObstacleIndex

**落点**：`edge_routing_organic.rs` 的 `build_obstacle_context` 调用处

**验证**：无穿障的有机路由图性能显著提升；有穿障的图行为不变。

### 3.2 P1：中期优化（2-4 周）

#### P1-1. 后处理层合并

**目标**：将 replan + straighten + stub_fix 合并为单阶段「端口修正」。

**当前问题**：
- 三阶段分别修改 slot 锚点、路径对齐、端口方向
- 阶段间存在写权竞争（straighten 对齐后 stub_fix 可能翻转端口）
- 每阶段独立遍历所有边，O(3n) 可压缩为 O(n)

**方案**：
```rust
// 新阶段：phase_port_correction()
// 合并 replan_slots + straighten_align + stub_fix 为单次遍历
// 对每条边：
//   1. 检测 slot 排序是否与实际路由方向一致（原 replan）
//   2. 检测正对端口是否可对齐（原 straighten）
//   3. 检测 stub 是否反向（原 stub_fix）
//   4. 按优先级执行修正：stub_fix > replan > straighten
//   5. 修正后验证不制造新违规
fn phase_port_correction(
    nodes, relations, from_side, to_side, endpoint_map,
    edges, grid, cfg, group_ctx, obstacles, corridor_plan,
) -> PortCorrectionStats
```

**写权契约**：
- 端口修正阶段是 from_side/to_side/endpoint_map 的**最终写者**
- 后续阶段（lane、sanitize）只读端口，不修改

**验证**：product-gate 质量轨不退化；单测覆盖三阶段合并后的行为。

#### P1-2. Channel Planner 升级为软约束

**目标**：Channel Planner 从「提供候选」升级为「软约束」，路由时优先使用规划通道。

**当前状态**：
- `plan_channels()` 预计算通道坐标
- 仅作为 `build_channel_detours` 的额外候选注入
- 不强制路由结果使用规划通道

**方案**：
- 在 DefaultScorer 中增加 `channel_alignment_bonus`：路径段落在规划通道坐标上时减分
- 对已规划通道的边，候选枚举优先生成经过规划通道的路径
- 通道容量约束：同通道边数超过容量时，scorer 惩罚增加

**落点**：`scoring.rs` + `path.rs`

**验证**：通道利用率提升；同通道重叠边数下降。

#### P1-3. OVG 增量构建

**目标**：大图（>50 节点）仅对 degraded 边重建局部 OVG，而非全图构建。

**方案**：
- 第一轮：用候选枚举路由所有边
- 收集 degraded 边列表
- 仅对 degraded 边的起终点邻域（bbox + margin）构建局部 OVG
- 局部 OVG 仅包含邻域内的障碍物

**性能预期**：
- 当前 ecommerce 全图 OVG: 34ms
- 局部 OVG（仅 16 条 degraded 边）: 预期 <5ms 额外开销

**落点**：`visibility_graph.rs` 新增 `build_local_ovg()`

#### P1-4. Port Solver 与 OVG 协调

**目标**：Port Solver 的端口分配结果传递给 OVG 路径搜索，避免端口-路径不协调。

**当前问题**：
- Port Solver 独立优化端口分配（最小化弯折预估）
- OVG 独立搜索路径（不感知端口分配）
- 两者可能冲突：Port Solver 选了「预估弯折少」的端口，但 OVG 在该端口下找不到好路径

**方案**：
- OVG 路径搜索时，将 Port Solver 的端口分配作为起始/终止方向约束
- 若 OVG 在约束端口下找不到路径 → 放松端口约束 → 反馈给 Port Solver 更新分配

### 3.3 P2：长期架构改进（4-8 周）

#### P2-1. 全局通道分配替代逐边贪心

**目标**：实现 ELK 级别的全局通道分配。

**设计**：
```rust
/// 全局通道分配器（替代当前逐边贪心）
/// 
/// 算法：
/// 1. 构建通道需求图：每条边需要哪些方向的通道段
/// 2. 通道坐标候选：组间隙中点、节点间隙中点、图 bbox 外侧
/// 3. 约束满足：同通道多边按 lane 严格分离（lane_pitch = parallel_gap）
/// 4. 目标函数：最小化总路径长度 + 弯折数 + 交叉数
/// 5. 求解：贪心初始化 + 局部搜索（swap 通道分配）
pub struct GlobalChannelAssignment {
    // 垂直通道 x → 分配给哪些边的哪些段
    vertical: BTreeMap<i64, Vec<ChannelSegment>>,
    // 水平通道 y → 分配给哪些边的哪些段
    horizontal: BTreeMap<i64, Vec<ChannelSegment>>,
}
```

**与当前架构的关系**：
- 替代 `lane_assignment.rs`（1548 行）的核心逻辑
- 替代 `conflict_reroute.rs`（322 行）的多轮冲突消解
- Channel Planner 升级为 GlobalChannelAssignment 的初始化

**验证**：product-gate 全面不劣化 + 通道重叠边数显著下降。

#### P2-2. 边交叉最小化升级为路由阶段硬约束

**目标**：交叉最小化从后处理（C2）升级为路由阶段的硬约束。

**方案**：
- 在逐边路由时，scorer 增加交叉惩罚：候选路径与已路由边的交叉数 × CROSSING_PENALTY
- 交叉检测复用 `crossing_reduction.rs` 的统一算法（含共线端点）
- 对交叉数 > 阈值的边，触发 OVG 重路由（搜索无交叉路径）

**落点**：`scoring.rs` 新增 `crossing_penalty()`

#### P2-3. 自适应组间距（C3）

**目标**：组间距根据穿越边数自适应调整。

**方案**：
```rust
// group_frame 阶段：在组框计算后、路由前
fn adaptive_group_spacing(
    groups: &mut HashMap<String, GroupLayout>,
    corridor_plan: &CorridorRoutePlan,
    min_corridor_width: f64,  // 40px
) {
    // 1. 对每对相邻组，计算穿越边数
    // 2. 所需走廊宽度 = max(min_corridor_width, edge_count * lane_pitch + 2*margin)
    // 3. 若当前间隙 < 所需宽度 → 推开组框
    // 4. 推开方向：远离图重心（保持整体紧凑）
    // 5. 最大推开距离：80px（避免画布过大）
}
```

**前置条件**：当前所有 product 样例 `hugging_violations = 0`，待出现真实贴边退化时再实施。

#### P2-4. 路由管线写权收敛

**目标**：每个几何字段有且仅有一个最终写者，消除写权竞争。

**当前写权表**（需收敛）：

| 字段 | 当前写者 | 目标最终写者 |
|------|---------|------------|
| from_side / to_side | port_slot → stub_fix → (多阶段) | phase_port_correction（P1-1） |
| edge.geometry | route → reroute → lane → sanitize → snap → sanitize_ext | 分两阶段：route 写初版，sanitize_ext 写终版 |
| edge.labels | route → sanitize → label_resolve | label_resolve（唯一最终写者） |
| route_annotations | freeze → S4.x refresh → D stub refresh | 每阶段末尾 refresh，最终 freeze 在 D 段 |

**原则**：
- 上游阶段写初版，下游阶段只读或做最终修正
- 禁止中间阶段修改下游已冻结的字段
- 违反写权契约的修改必须通过回归证明

### 3.4 P3：探索性研究

#### P3-1. 两轮路由（先粗后细）

**思路**：
- 第一轮：快速路由所有边（仅候选枚举，不启用 OVG/reroute/lane）
- 统计全局拥堵热力图
- 第二轮：基于拥堵信息，对拥堵区域的边启用 OVG + 全局通道分配

**预期收益**：大图性能提升（避免全图 OVG）+ 路由质量提升（拥堵感知）。

#### P3-2. 全局端口+通道联合优化

**思路**：
- 将端口分配和通道分配建模为联合约束满足问题
- 变量：每条边的 (from_port, to_port, channel_sequence)
- 约束：端口容量、通道容量、正交性
- 目标：最小化总弯折 + 交叉 + 路径长度
- 求解：ILP（小规模）/ 模拟退火（中规模）/ 贪心+局部搜索（大规模）

#### P3-3. 布局-路由联合迭代

**思路**：
- 路由完成后统计拥堵/交叉/绕行信息
- 反馈给布局阶段：调整节点位置以缓解拥堵
- 迭代 2-3 轮直到收敛

**风险**：
- 布局变动触发全量重路由，性能开销大
- 收敛性不保证（可能振荡）
- 需要 AGENTS.md §7 创新模式豁免

## 4. 性能优化方向

### 4.1 当前性能画像

| 图 | 节点数 | 边数 | 路由耗时 | 瓶颈 |
|----|--------|------|---------|------|
| stress-deep (mindmap) | 63 | 62 | 1.1ms | ✅ 已优化（原 75ms） |
| ecommerce (architecture) | ~80 | ~90 | 34ms | OVG 构建 + Dijkstra |
| cloud-native (architecture) | ~60 | ~70 | ~20ms | 候选枚举 + reroute |
| typical-microservice | ~30 | ~35 | ~8ms | 无显著瓶颈 |

### 4.2 ObstacleIndex 懒构建（扩展到非 mindmap）

**当前状态**：mindmap 已跳过（Phase D4），非 mindmap 仍全量构建。

**方案**：
```rust
// edge_routing_organic.rs
// 快速预检：直线段 vs 节点 bbox 粗检
let any_potential_collision = relations.iter().any(|rel| {
    // 仅检查起终点连线是否穿过任何非端点节点 bbox
    quick_segment_hits_any_node(start, end, from_id, to_id, &result.nodes)
});
let obstacle_index = if any_potential_collision {
    Some(build_obstacle_context(&result))
} else {
    None
};
```

**预期收益**：无穿障的有机路由图（多数 flowchart）跳过 O(n²) 构建。

### 4.3 OVG 空间索引优化

**当前问题**：固定 bbox+80px margin 不自适应。

**方案**：
- 小图（<30 节点）：全图 OVG（当前行为）
- 中图（30-80 节点）：bbox + 自适应 margin（`margin = max(80, avg_edge_length * 0.3)`）
- 大图（>80 节点）：仅对 degraded 边构建局部 OVG（P1-3）

**落点**：`visibility_graph.rs` 的 `build_ovg_with_groups()`

### 4.4 大图分层路由

**目标**：>100 节点的图分区路由，降低全局搜索复杂度。

**方案**：
- 按组（leaf group）分区
- 组内边：仅在本组障碍物上路由
- 跨组边：在组边界走廊上路由
- 边界协调：跨组边的出入口点由全局通道分配决定

**前置条件**：P2-1 全局通道分配完成。

### 4.5 并行化潜力

**分析**：
- 逐边路由存在依赖（后路由边避让先路由边的 SegmentGrid）
- 但同层无交叉的边可并行路由
- OVG 构建可并行（各障碍物的可见性检查独立）

**限制**：
- WASM 不支持多线程（当前目标平台）
- 并行化收益在 <100 节点时不显著
- 优先级低于算法优化

### 4.6 WASM 性能注意事项

- 禁止 `std::time::{Instant, SystemTime}`（AGENTS.md §6）
- 避免 O(n²) 预计算在 WASM 上执行（无 JIT 优化）
- ObstacleIndex 的 31,626 对角点检查在 WASM 上约 200ms（不可接受）
- 建议：WASM 平台默认关闭 ObstacleIndex，仅做快速直线检测

### 5.2 建议补充的指标

#### 5.2.1 边长均匀性

```rust
pub struct EdgeLengthMetrics {
    /// 同层边长的变异系数（CV = std / mean）
    pub intra_layer_cv: f64,
    /// 最长边 / 最短边 比值
    pub max_min_ratio: f64,
    /// 异常长边数（超过均值 + 2*std）
    pub outlier_count: usize,
}
```

**意义**：同层边长差异过大表示布局不均匀，视觉上「一边挤一边松」。

#### 5.2.2 通道利用率

```rust
pub struct ChannelUtilization {
    /// 走廊中实际有边通过的占比
    pub corridor_usage_ratio: f64,
    /// 最拥堵通道的边数
    pub max_channel_load: usize,
    /// 未使用走廊数
    pub unused_corridors: usize,
}
```

**意义**：走廊规划是否有效；拥堵通道是否需要扩容。

#### 5.2.3 端口分布均匀性

```rust
pub struct PortDistribution {
    /// 同节点同侧最大边数
    pub max_same_side_edges: usize,
    /// 端口利用率方差（各侧边数的方差）
    pub side_utilization_variance: f64,
}
```

**意义**：端口过度集中在一侧会导致视觉拥挤和路由困难。

#### 5.2.4 路径单调性

```rust
pub struct PathMonotonicity {
    /// 非单调路径占比（路径在主轴方向有反向段）
    pub non_monotone_ratio: f64,
    /// 非单调路径列表（边索引）
    pub non_monotone_edges: Vec<usize>,
}
```

**意义**：非单调路径（走回头路）是路由质量的直观指标。

### 5.3 美学轨转硬 FAIL 的条件与时间表

**当前状态**：美学轨全角色 WARN（观测不挡）。

**转硬条件**：

2. 容差合理：容差值经 product 样例验证，不会误挡合理改动
3. 工具链成熟：compare.sh 的美学轨逻辑经充分测试

**建议时间表**：
- Phase E2 结束时：`crossings.total` 和 `bends.avg_per_edge` 对 product 转硬
- Phase E3 结束时：全部美学指标对 product 转硬
- stress/demo 保持 WARN（可债）

## 7. 约束与原则（AGENTS.md 对齐）

### 7.1 硬红线（★）

1. **确定性迭代**：禁止 HashMap key 序驱动布局/路由；使用 BTreeMap/IndexMap/显式排序
2. **WASM 兼容**：`plotgram-core` 内禁止 `std::time::{Instant, SystemTime}`；计时走 `perf.rs`
3. **禁止图名特判**：从通用规则出发修复；不可为压 stress 数字加图名分支
4. **验证用 `cargo run -p plotgram-cli`**：勿信陈旧 binary
5. **退化可量化**：product-gate 严重度/质量轨为准；非单图观感

### 7.2 门禁分层

| 角色 | 质量轨 | 正确性轨 |
|------|--------|---------|
| product / smoke | 硬 FAIL | 硬 FAIL |
| stress | WARN（可债） | 硬 FAIL |
| demo | WARN（可债） | 硬 FAIL |
| mech | 不门禁 | 硬 FAIL |

### 7.3 创新模式（§7）适用场景

- Phase E3 全局通道分配：推翻逐边贪心架构，允许有界临时退化
- Phase E4 布局-路由联合迭代：管线时序变更，允许过程退化
- 必须：显式登记目标维度 + 临时退化范围 + 退出判据

### 7.4 无向后兼容（§1）

- 可自由重命名/删除公共 API
- 重构时直接删除旧代码，不保留兼容层
- 后处理合并时直接移除旧阶段函数
