# 14 - 布局 Recipe 生命周期收敛方案

> 定位：在 Coordinate Kernel 与 LayoutRecipe 骨架已落地的前提下，把「Recipe 挂名 + execute() 委托旧引擎」的过渡态，收敛为完整生命周期模型——每个 Recipe 拥有 compile → solve → audit → product 全链路，自选算法与内核，产出节点布局产品；对外 layout 即选配方。

---

## 一、验收标准（一句话）

删掉各 Recipe 对 `execute()` 的覆盖后，`compile → solve → audit → product` 仍能独立跑通；flowchart/state/ER 的坐标求解在 Recipe 层显式选用 Coordinate Kernel，而不是藏在 `sugiyama_v2/coordinate.rs` 里。

---

## 二、当前债务分析

### 2.1 生命周期空心化

多数 Recipe 的 `compile` / `solve` 是占位，`execute()` 直接调 `engine::compute_with_preset` 或旧布局函数。trait 的语义与实现脱节。

**正面参照**：`SequenceRecipe`、`CircularRecipe` 已较好拆分 Problem / Solution（compile 提取 IR、solve 纯计算、product 物化）；应以它们为模板。

### 2.2 求解器入口不统一

- flowchart 路径在 `sugiyama_v2/coordinate.rs` 里直接 `solve()`
- architecture 无组路径走 `LayoutCoordinator::run()`
- 存在 `LayoutRecipe`（kernel/recipe.rs）与 `coordinator::Recipe`（kernel/coordinator.rs）两套概念

### 2.3 Sugiyama 与 Recipe 边界模糊

分层（rank → order → BK）仍在 engine 黑盒内，Recipe 只做了「选 flat / 分治 / two_phase」分发，未表达「LayeredKernel + CoordinateKernel」组合。

### 2.4 Pipeline 与 Recipe 职责未写清

节点 freeze、route feedback re-solve、grid_snap 哪些属于 Recipe 产物、哪些属于 Coordinator，文档与代码不一致。

### 2.5 尚无 layout: auto

配方选择仍绑定 `layout_algo` 字符串与 registry，缺少按 `diagram_type + NodeMetrics` 的自动选型。

---

## 三、阶段划分

### Phase R1：统一概念与边界（文档 + 小改，不改行为）

**目标**：全仓库只保留一种「Recipe」叙事。

| 概念 | 定义 | 位置 |
|------|------|------|
| 布局 Recipe | 整图节点布局，Problem/Solution 由图种自定 | `kernel/recipe::LayoutRecipe` |
| Coordinate Kernel | 仅 `CoordinateProblem → solve + audit` | `kernel/coordinate/` |
| CoordinateSolveStep | 原 `coordinator::Recipe`，重命名避免混淆 | `kernel/coordinator.rs` |

具体任务：
1. 重命名 `coordinator::Recipe` → `CoordinateSolveStep`（或 `CoordinateRecipe`），明确它是 Coordinate Kernel 的调用封装，不是布局 Recipe。
2. 明确产出契约：Recipe 交付 `NodeLayoutProduct`（nodes + groups + hints + routing_profile）；边几何、label、snap 归属 pipeline。sequence 等自产边类型在 Recipe 内显式声明 `produces_edge_geometry`。
3. 删除 `LayoutRecipeDyn`（当前无调用方），或保留但标注为「预留：未来 LayoutStrategy 统一委托入口」。
4. 补充模块级文档：flowchart 从 DSL 到 nodes 经过哪几层、谁调 solve。

**退出判据**：新人读文档能回答「flowchart 从 DSL 到 nodes 经过哪几层、谁调 solve」。

---

### Phase R2：FlowchartRecipe 真拆分（行为不变，结构变）

**目标**：flowchart 成为第一个「无 execute 覆盖」的分层 DAG 配方。

建议 `FlowchartLayoutRecipe` 结构：

```rust
compile(diagram) → FlowchartDraft {
    effective_graph,
    layered: LayeredDraft { ranks, layers, sizes, gaps, bk_centers },
    coordinate: CoordinateProblem,   // builder + structure/basic objectives
    path: Flat | DivideConquer,
}

solve(draft) → FlowchartSolution {
    // Flat/Divide 子路径：先 LayeredKernel 产出 layered 部分
    // CoordinateKernel::solve + audit
    // 物化 centers → nodes
    nodes: HashMap<String, NodeLayout>,
    ranks: HashMap<String, usize>,
    coordinate_problem: Option<CoordinateProblem>,
}

product(solution, diagram) → LayoutResult {
    // + hints（sugiyama_ranks, coordinate_problem, frozen 标记）
}
```

具体任务：

1. **抽出 LayeredKernel**：从 `engine.rs` 提取 rank → order → proper graph → BK 初值 → per-layer gaps，输入/输出结构化，不直接写 NodeLayout。
2. **coordinate.rs 瘦身**：仅保留 build IR + apply solver 结果到层坐标 + normalize；删除残留 dead pass。
3. **Recipe::solve 显式调用** `kernel::coordinate::optimizer::solve`（或统一 `CoordinateKernel::run`），不再在 engine 深处隐式调用。
4. **group 分治**：视为 Recipe 内子 Recipe 调用（每个子图 compile + solve，再 compose），而非独立 bypass。

**退出判据**：
- `cargo test -p plotgram-core` 通过
- product-gate 对比节点坐标与重构前一致（或门禁关闭期记录已知差异）
- flowchart 无 `execute` override

---

### Phase R3：State / ER / Sugiyama-v2 对齐同一模式

**目标**：所有「Sugiyama + CoordinateSolver」图种共享 LayeredKernel + 不同 objective 权重/识别规则，差异只在 Recipe 的 compile（preset、structure_objectives 参数）。

- **StateRecipe**：保留「Circular vs Sugiyama」分支，但 Sugiyama 分支走 R2 拆出的 Layered + Coordinate，不整包 `engine::compute_with_preset`。
- **ErRecipe**：同 flowchart，换 ER_PRESET 与 ER 专属 weights。
- **SugiyamaV2Recipe**：generic preset 的薄封装。

**退出判据**：`structure_objectives` / `ObjectiveWeights` 按图种配置表驱动，无 `diagram_type` 分支散落在 engine。

---

### Phase R4：ArchitectureRecipe 迁入统一坐标链

**目标**：architecture 无组路径已用 Coordinator；有组 two_phase 路径逐步把 intra/macro 坐标写成同一 Coordinate IR + Kernel，删除 architecture 专属「推节点」补丁。

- two_phase：组内可选用 LayeredKernel 或 hint 几何模式，但坐标终态仍经 Kernel（或明确标注「非 Coordinate 子内核」）。
- `enforce_horizontal_demand_gaps` 等 → SpacingDemand 编译进 IR，有界 re-solve。
- 删除 architecture 与 flowchart 双轨临时 `solver_frozen` 分支（统一 freeze 契约）。

---

### Phase R5：Pipeline 收口为 LayoutCoordinator

**目标**：Recipe 之外只保留跨配方公共后半段。

```text
Recipe.execute → NodeLayoutProduct
  → LayoutCoordinator::post_layout {
       optional: route_feedback re-solve（改 IR，不调 enforce_horizontal_gaps）
       NodeFreeze::capture
       Router（消费 recipe.routing_profile()）
       label / snap（finalize only）
     }
```

- `route_feedback_resolve` 已存在：确保 flowchart 走 SpacingIntent/RouteDemand → re-solve，而非回退推节点。
- `grid_snap`：仅 finalize，solver 冻结图类型默认跳过水平推节点（保持现状契约）。
- Coordinator 不含 flowchart/arch 语义分支。

---

### Phase R6：配方选择与动态配置

**目标**：`layout: auto` 与按图规模调参。

- 实现 `PreparedLayoutInput` + `NodeMetrics`（N、E、max_fan、层宽、gap 负载等）。
- `AutoLayoutRecipe`：diagram_type → 默认 Recipe；可选 NodeMetrics → RecipeConfig tier（Compact / Standard / Spacious）。
- DSL：`layout: auto` 或省略时走 auto；显式 `layout: flowchart` 覆盖 auto。
- trace 输出：`picked_recipe`、`tier`、主要 weights（便于调试与动画）。
- 禁止：图名特判；指标与 tier 边界须单测 + 确定性排序。

---

### Phase R7：质量与可观测性（与结构重构并行）

- Kernel 单测矩阵：PAVA、各 objective 类型、P1 budget、确定性。
- Recipe 契约测：每种 Recipe 最小 diagram fixture → 断言 nodes 关键性质。
- LayoutTrace（可选 feature）：solver 降采样帧 + 阶段名，供 playground 动画。
- 删除确认无用的旧 pass 与 dead code。

---

## 四、全程原则

| 原则 | 说明 |
|------|------|
| 无图名特判 | 修结构语义，不为单张 showcase 开分支 |
| 单一坐标写者 | solve 之后 flowchart 系不得再推节点；需求用 IR 重解 |
| 确定性 | 固定排序、固定迭代上限、禁止 HashMap 驱动顺序 |
| 不保留双轨 | 迁完一条 pass 就删 direct mutation，不做长期并存 |
| Kernel 无 DiagramType | 图种差异只在 Recipe compile |
| 验证用 cargo run -p plotgram-cli | 不信陈旧 release binary |

---

## 五、不建议在本阶段做的事

- 不要引入动态阶段 DSL 或插件式 Recipe registry（保持 Rust 显式编排）。
- 不要把 Sequence/Mindmap/Circular 硬塞进 CoordinateSolver（各自保留几何内核，只统一 LayoutRecipe 接口）。
- 不要为「删 execute」而大规模改 rank/order 算法——R2 以搬结构为主，算法调优另开任务。
- 不要在 Router 未收口前把路由逻辑塞进 Recipe（除 sequence 等自产边类型）。

## 六、依赖与优先级

```text
R1（概念） → R2（flowchart 真拆分）→ R3（state/er 对齐）
                    ↓
              R5（Coordinator 后半段）← R4（architecture）
                    ↓
              R6（auto + metrics）

R7（测试/trace）与 R2 起并行
```

**最小可交付里程碑**：完成 R1 + R2 后，flowchart 即成为宏观模型的参考实现；其余图种按模板复制。

---

## 七、成功时应有的样子

用户写 `diagram flowchart { ... }`，内部等价于：

```text
AutoLayoutRecipe 或 FlowchartLayoutRecipe
  compile  → 图指标 + 分层草稿 + CoordinateProblem
  solve    → LayeredKernel（Sugiyama）+ CoordinateKernel（solve）
  audit    → P0
  product  → LayoutResult（节点已冻结语义）

LayoutCoordinator
  route（OrthogonalRoutingProfile::flowchart）
  finalize
```

开发者修 onboarding 对称：只改 `FlowchartRecipe` 的 structure 编译或权重，单测 + loss 诊断即可验证，无需在 pipeline 里找第几个 pass。

## 八、技术评估与补充意见

### 8.1 关于 execute() 覆盖的合理性

当前 Sequence/Circular 的 compile/solve/product 拆分是自然的（问题域简单、solver 独立）。但 Flowchart/Architecture 的 compute 逻辑深度耦合（rank 影响 order 影响 coordinate 影响 postprocess），强行四段拆分会引入大量中间状态传递。

**建议**：R2 的关键不是「删 execute」本身，而是让 compile 产出结构化 IR（FlowchartDraft），使 solve 可以独立测试。execute 覆盖可以保留为「编排便利」，只要内部确实走了 compile → solve → product 调用链。

### 8.2 关于 LayeredKernel 提取

这是 R2 最大的工程量。当前 `engine.rs` 是一个 ~400 行的编排函数，内部调用 rank/order/coordinate/postprocess 四个子模块。提取 LayeredKernel 意味着：

1. 定义 `LayeredDraft` 结构体（ranks + layers + sizes + gaps + initial_centers）
2. 将 rank → order → BK 初值封装为 `LayeredKernel::compute(graph, preset) → LayeredDraft`
3. coordinate builder 从 LayeredDraft 构建 CoordinateProblem（而非从 diagram 重新解析）

风险：BK 初值与 coordinate solver 的 initial 有耦合（BK 产出 centers，solver 以此为初值）。需要明确 LayeredDraft 是否包含 BK centers，还是只到 order 为止。

### 8.3 关于 coordinator::Recipe 的处理

当前 `coordinator::Recipe` 只有 `name()` + `solve()`（默认实现 = kernel solve + P0 audit）。它本质是「Coordinate Kernel 的调用封装」。

**建议**：重命名为 `CoordinateSolveStep` 或直接内联到 `LayoutCoordinator::run()` 中（删除 trait，只保留函数）。两个 adapter（FlowchartRecipeAdapter / ArchitectureRecipeAdapter）只是提供 name，可以用字符串参数替代。

### 8.4 关于 layout: auto 的时机

R6 依赖 R2-R4 完成（否则 auto 选到的 Recipe 内部还是黑盒）。建议 R6 作为独立里程碑，不与结构重构混在同一 PR 中。
