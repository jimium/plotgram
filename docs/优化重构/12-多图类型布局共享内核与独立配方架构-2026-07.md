## 0. 结论

流程图和架构图不应：

1. 完全复制成两套布局系统；
2. 也不应塞进一条通过 `if diagram_type` 和大量 hook 切换行为的巨型通用管线。

推荐结构是：

> **共享算法内核（Kernel） + 图类型独立配方（Recipe） + 统一生命周期（Coordinator）。**

三者职责分别是：

```text
Recipe      决定“这是什么图、应该经历哪些语义步骤、追求什么视觉目标”
Kernel      提供“稳定图索引、分层、排序、坐标求解、分组组合、诊断”等纯算法能力
Coordinator 管理“准备 → 编译 → 求解 → 有界反馈 → 冻结 → 路由 → 收尾”的生命周期
```

流程图和架构图共享“怎么计算”，不共享“为什么这样计算”。

最终结构：

```text
                         ┌──────────────────────────────┐
Diagram ── Prepare ────▶│       PreparedLayoutInput    │
                         └──────────────┬───────────────┘
                                        │
                    ┌───────────────────┴───────────────────┐
                    │                                       │
          ┌─────────▼─────────┐                   ┌─────────▼──────────┐
          │ FlowchartRecipe   │                   │ ArchitectureRecipe │
          │ 流程结构语义链     │                   │ 分组/宏观结构语义链 │
          └─────────┬─────────┘                   └─────────┬──────────┘
                    │                                       │
                    └───────────────────┬───────────────────┘
                                        │ 调用共享能力
                         ┌──────────────▼───────────────┐
                         │        Layout Kernels         │
                         │ graph / layered / coordinate  │
                         │ compose / demand / audit      │
                         └──────────────┬───────────────┘
                                        │
                              NodeLayoutProduct
                                        │
                         ┌──────────────▼───────────────┐
                         │ LayoutCoordinator             │
                         │ demand probe → 有界重解 → freeze │
                         └──────────────┬───────────────┘
                                        │
                               FrozenNodeLayout
                                        │
                         ┌──────────────▼───────────────┐
                         │ Shared Router + RoutingProfile│
                         └───────────────────────────────┘
```

## 1. 要解决的更高层问题

### 1.1 当前已经出现的两种重复

第一种是算法重复：

- `sugiyama_v2` 有 rank/order/coordinate。
- `architecture_v2/layout` 也维护 rank/order/coordinate。
- architecture 组内复杂拓扑又反过来调用 `sugiyama_v2`。
- architecture coordinate 已局部复用 BK centers，但后续仍有另一套推点链。

第二种是生命周期重复和写权竞争：

- 节点算法内部做 overlap、对齐、group bounds、space budget。
- 通用 pipeline 又做 grid snap、group frame、space budget、refine。
- route feedback 再次推节点。
- architecture 在 pipeline 中还有按算法名触发的专属重申。

这说明现在既没有真正独立，也没有真正共享，而是：

> 共享了一部分函数，同时在多个层次重复编排和补救。

### 1.2 两个极端都不合适

#### 极端 A：流程图和架构图完全独立

优点：

- 单个目录容易理解。
- 改流程图不直接进入架构图代码。

长期代价：

- rank/order、BK、约束求解、空间需求、确定性、诊断、性能优化全部复制。
- 同一个 bug 要修两次。
- 两套实现会逐步产生不同的数据结构和测试方式。
- architecture 组内仍然需要一种分层布局，最终还是会重新实现 Sugiyama。

#### 极端 B：一条万能 LayoutPipeline

典型形态：

```text
if flowchart { ... }
if architecture { ... }
profile.enable_hub_centering
hook.after_group_frame
hook.after_space_budget
hook.after_node_freeze
```

长期代价：

- 图类型语义扩散到每个公共阶段。
- profile 变成几十个布尔字段。
- hook 顺序成为隐藏契约。
- 测试必须启动整条管线才能验证局部规则。
- 新增图类型只能继续往公共管线插条件。

### 1.3 推荐的中间路线

只共享三类东西：

1. **事实模型**：稳定图索引、节点尺寸、group tree、scope、约束。
2. **纯算法能力**：FAS、rank、order、坐标求解、PAVA、组合、审计。
3. **生命周期规则**：需求反馈有界、节点冻结后不可移动、路由只消费冻结几何。

以下内容保持图类型独立：

1. 什么边参与拓扑。
2. group 是装饰框还是宏观布局本体。
3. 什么结构是主轴。
4. 生成哪些坐标目标。
5. 组内和组间按什么顺序布局。
6. 无法满足目标时如何降级。
7. 路由使用什么 profile。

## 2. 核心设计原则

### 2.1 机制共享，语义分离

共享内核只回答：

- 如何稳定建图？
- 如何给一个 DAG 分层和排序？
- 如何解一个坐标约束问题？
- 如何组合局部布局？
- 如何检查硬约束？

Recipe 回答：

- 这张图要不要先按 group 分解？
- 哪些边是 effective edge？
- 哪些节点形成 split–join、hub、client、infrastructure？
- 哪些约束是 P1，哪些只是 P3？
- group frame 是后验装饰还是一等布局对象？

### 2.2 功能核心，命令外壳

Kernel 尽量是纯函数：

```text
input model → output model + diagnostics
```

不直接读取全局环境变量，不按图名分支，不在内部启动路由，也不修改外部 `LayoutResult`。

Coordinator 是命令外壳，负责：

- 调度 Recipe。
- 管理最多几轮反馈。
- 记录阶段报告。
- 建立冻结屏障。
- 调用 router。

### 2.3 编译意图，再执行几何

图类型专属逻辑不应边识别边推节点，而应先编译为 Draft/Intent：

```text
Diagram semantics
  → Recipe Draft
  → ranks / orders / scopes / structure regions
  → coordinate intents / spacing intents
  → shared solver
```

这样可以在真正求解前测试“配方理解对不对”。

### 2.4 不建立万能布局 DSL

本文不建议把所有布局阶段抽象成：

```rust
Vec<Box<dyn Phase>>
```

也不建议设计一个可以描述所有图类型的动态阶段 DSL。

原因：

- 流程图是单个主图的控制流结构。
- 架构图是组内局部布局 + 组间宏观布局 + 组合。
- 强行把两者变成同样的 phase 列表，只会把差异藏进 callback。

Recipe 应是普通、显式的 Rust 编排代码；共享只发生在数据模型和 Kernel 调用处。

### 2.5 写权必须按生命周期收口

节点相对坐标的最终写者只有坐标/组合内核。

```text
compile / analyze：不写坐标
solve / compose：允许写候选节点坐标
feedback：只新增 intent，再重解
freeze：相对坐标封闭
route / post-route：禁止改节点
```

## 3. 推荐总体分层

### 3.1 L0：Prepared Input

所有图类型先进入一次通用准备阶段：

```rust
pub struct PreparedLayoutInput {
    pub graph: StableGraph,
    pub node_metrics: NodeMetrics,
    pub groups: GroupTree,
    pub constraints: UserConstraintSet,
    pub direction: LayoutDirection,
    pub declaration_order: DeclarationOrder,
}
```

这里保存事实，不保存 flowchart/architecture 的审美结论。

#### StableGraph

建议逐步收敛 `petgraph::DiGraph` 与 architecture 字符串邻接表的双轨：

```rust
pub struct StableGraph {
    pub nodes: Vec<StableNode>,
    pub edges: Vec<StableEdge>,
    pub out_edges: Vec<Vec<EdgeId>>,
    pub in_edges: Vec<Vec<EdgeId>>,
    pub id_to_node: HashMap<String, NodeId>,
}

pub struct StableNode {
    pub id: String,
    pub declaration_index: usize,
}

pub struct StableEdge {
    pub from: NodeId,
    pub to: NodeId,
    pub relation_index: Option<usize>,
    pub kind: EdgeSemanticKind,
}
```

原则：

- 热路径使用连续 `Vec` 和稳定整数 id。
- `HashMap` 只负责 id 查询，不驱动迭代。
- 是否过滤 passive、是否注入 constraint edge，由 Recipe 编译 effective graph 时决定，不在 `StableGraph` 建造阶段写死。

### 3.2 L1：Diagram Recipe

每个图类型有一个清晰入口：

```text
flowchart/recipe.rs
architecture_v2/recipe.rs
```

Recipe 的输出不是最终边路径，而是完整节点布局产品。

建议接口：

```rust
pub trait LayoutRecipe {
    type Draft;

    fn compile(
        &self,
        input: &PreparedLayoutInput,
        kernels: &LayoutKernels,
    ) -> Result<Self::Draft, LayoutError>;

    fn add_spacing_intents(
        &self,
        draft: &mut Self::Draft,
        demands: &[SpacingDemand],
    ) -> DemandApplyReport;

    fn solve(
        &self,
        draft: &mut Self::Draft,
        kernels: &LayoutKernels,
    ) -> Result<NodeLayoutProduct, LayoutError>;

    fn routing_profile(&self) -> RoutingProfile;
}
```

该 trait 只有四个稳定职责：

1. 编译语义。
2. 接收通用 spacing demand。
3. 使用共享 kernel 生成节点布局。
4. 声明路由 profile。

不要继续给它增加十几个阶段 hook。若某图类型需要特殊步骤，应写在该 Recipe 的 `compile/solve` 内部。

实现可以保持静态泛型：

```rust
run_recipe(diagram, FlowchartRecipe::new(config));
run_recipe(diagram, ArchitectureRecipe::new(config));
```

无需为了 registry 把 Draft 做成全局统一动态类型。

### 3.3 L2：Shared Layout Kernels

建议共享以下内核：

```rust
pub struct LayoutKernels {
    pub graph: GraphKernel,
    pub layered: LayeredKernel,
    pub coordinate: CoordinateKernel,
    pub compose: CompositionKernel,
    pub demand: DemandKernel,
    pub audit: LayoutAuditor,
}
```

实际 Rust 中可以是模块函数，不要求真的构造一个大对象。该结构只用来表达职责。

#### GraphKernel

- stable graph/view。
- effective edge view。
- cycle removal primitives。
- dominator/post-dominator。
- weak component。
- group/scope 映射。

#### LayeredKernel

- rank 分配。
- proper graph/dummy 链。
- crossing minimization。
- layer order。
- layered topology diagnostics。

输入是 Recipe 已决定的 effective graph 和 typed policy，而不是 `DiagramType`。

```rust
pub struct LayeredRequest<'a> {
    pub graph: EffectiveGraphView<'a>,
    pub constraints: &'a LayerConstraintSet,
    pub profile: LayeredProfile,
}

pub struct LayeredTopology {
    pub ranks: Vec<usize>,
    pub layers: Vec<Vec<NodeId>>,
    pub reversed_edges: Vec<EdgeId>,
    pub dummy_chains: Vec<DummyChain>,
}
```

#### CoordinateKernel

完全采用文档 11：

- `StructureModel`。
- `CoordinateIntent`。
- P0/P1/P2/P3。
- BK 初值。
- PAVA/投影优化。
- 唯一坐标写者。

文档 11 中 flowchart 的 split–join analyzer 属于 `FlowchartRecipe`，不是共享 Kernel 的固定语义；共享的是 IR 和 solver。

#### CompositionKernel

提供无业务语义的局部布局组合能力：

- local→global transform。
- scope tree。
- bottom-up 尺寸汇总。
- fragment 平移。
- group bounds 几何。
- 容器 padding。
- sibling overlap 的硬约束投影。

它不判断 architecture 的 group 是否一等公民；由 ArchitectureRecipe 决定何时调用。

#### DemandKernel

只读计算：

- label 所需间距。
- node/edge band demand。
- port clearance。
- corridor/lane pressure。

输出 `SpacingDemand`，不直接移动节点。

#### LayoutAuditor

统一检查：

- rank/order 不变量。
- 节点重叠。
- group containment。
- spacing contract。
- determinism signature。
- freeze 后节点写入。

### 3.4 L3：Layout Coordinator

Coordinator 只管理共同生命周期：

```rust
pub fn run_recipe<R: LayoutRecipe>(
    diagram: &Diagram,
    recipe: R,
    kernels: &LayoutKernels,
) -> Result<LayoutResult, LayoutError> {
    let input = prepare_layout_input(diagram)?;
    // compile 内部由 Recipe 按自身 scope/topology 调用共享 DemandKernel，
    // 并把基础需求放进对应的 CoordinateProblem。
    let mut draft = recipe.compile(&input, kernels)?;
    let mut product = recipe.solve(&mut draft, kernels)?;

    for _ in 0..MAX_DEMAND_FEEDBACK_ROUNDS {
        let delta = kernels.demand.probe_candidate(&product);
        if delta.is_empty() {
            break;
        }
        recipe.add_spacing_intents(&mut draft, &delta);
        product = recipe.solve(&mut draft, kernels)?;
    }

    kernels.audit.before_freeze(&product)?;
    freeze_nodes(product)
}
```

Coordinator 不知道：

- split–join。
- hub/client。
- infrastructure layer。
- macro group。
- flowchart end。

它只知道：

- Draft 可以接收 demand。
- Recipe 可以重新 solve。
- 反馈轮次有限。
- 冻结前必须审计。

Coordinator 不尝试读取泛型 Draft。基础需求由 Recipe 在 `compile` 中调用共享
`DemandKernel` 生成；Coordinator 只处理第一次候选几何之后的通用只读 probe。

### 3.5 L4：Frozen Geometry + Router

节点冻结后，router 只消费：

```rust
pub struct FrozenNodeLayout {
    pub nodes: FrozenNodeMap,
    pub groups: FrozenGroupMap,
    pub topology: TopologyMetadata,
    pub routing_contract: RoutingContract,
    pub diagnostics: LayoutDiagnostics,
}
```

Router 返回：

```rust
pub struct RoutedLayout {
    pub frozen_nodes: FrozenNodeLayout,
    pub edges: Vec<EdgeLayout>,
    pub annotations: RouteAnnotationSet,
}
```

类型层面不再给路由阶段 `&mut HashMap<String, NodeLayout>`。

如果短期无法改完所有签名，至少保留现有 `NodeFreeze` fingerprint 守卫；长期再切 typestate。

## 4. 流程图独立逻辑链

流程图语义：

- 节点是步骤、判断、开始/结束。
- 边表达控制流。
- group 默认只是阅读辅助，不是宏观 rank 本体。
- 主视觉目标是控制流主轴、split–join、反馈边、end 和 pendant。

推荐 Recipe：

```text
FlowchartRecipe.compile
  1. 构建 flowchart effective graph
  2. 注入不可逆用户约束
  3. 调 LayeredKernel：FAS → rank → order → proper graph
  4. FlowchartStructureAnalyzer
       ├─ linear chain
       ├─ split–join / SESE
       ├─ fan symmetry
       ├─ feedback hub
       ├─ local end
       └─ pendant
  5. FlowchartIntentBuilder
       ├─ 主轴目标
       ├─ fan-out/fan-in 目标
       ├─ end/pendant 目标
       └─ spacing demand

FlowchartRecipe.solve
  6. CoordinateKernel：BK 初值 + 统一求解
  7. flowchart group 仅按需要生成后验 frame
  8. 输出 NodeLayoutProduct
```

流程图 Recipe 不应知道：

- architecture macro block。
- group infrastructure layer。
- client→hub 语义。
- group sizing equal/uniform。
- 跨组 corridor shell。

## 5. 架构图独立逻辑链

架构图语义：

- group 是域、层或部署边界，是布局本体。
- 先决定语义舞台，再摆放内部组件。
- 组间关系决定 macro rank。
- 组内 hub/client、基础设施行、共享服务需要专属目标。
- nested group 是一等公民。

推荐 Recipe：

```text
ArchitectureRecipe.compile
  1. 构建 architecture effective graph
       ├─ passive edge 过滤策略
       ├─ 用户 constraint edge 不可反转
       └─ architecture edge semantics
  2. 构建 GroupTree / scope tree
  3. 递归编译叶子 scope
       ├─ layout hint → PatternPlacement
       └─ 普通拓扑 → LayeredKernel
  4. ArchitectureIntraIntentBuilder
       ├─ client↔hub centroid
       ├─ infrastructure row
       ├─ group-local spacing
       └─ cross-scope port tendency
  5. 每个叶子 scope 调同一个 CoordinateKernel
  6. 将叶子 fragment 封装成 macro block
  7. 构建 super graph
  8. LayeredKernel 给 macro block rank/order
  9. ArchitectureMacroIntentBuilder
       ├─ group gap
       ├─ equal/uniform sizing
       ├─ left/center row alignment
       ├─ corridor/gutter reservation
       └─ group containment

ArchitectureRecipe.solve
 10. CoordinateKernel 解 macro block 坐标
 11. CompositionKernel 回填局部 fragment
 12. 计算一等 group frame / corridor contract
 13. 输出 NodeLayoutProduct
```

这里共享的是：

- 叶子 scope 和 macro scope 都可以调用 `LayeredKernel`。
- 节点和 macro block 都可以转换成一维 `CoordinateProblem`。
- 局部和全局都使用同一 hard projection / objective solver。
- 审计和需求模型一致。

不共享的是：

- scope 如何划分。
- hub/client 如何识别。
- macro block 变量怎么构建。
- group sizing 和 corridor 目标。

### 5.1 无 group 的 architecture

无 group 时不需要维护另一套完整 rank/order/coordinate：

```text
ArchitectureRecipe
  → 单 root scope
  → LayeredKernel
  → ArchitectureIntentBuilder
  → CoordinateKernel
```

它和 flowchart 使用相同内核，但不是调用 FlowchartRecipe，因为目标语义仍不同。

## 6. 共享与独立边界

### 6.1 应共享

#### 数据与基础设施

- stable node/edge id。
- node metrics。
- group tree 基础结构。
- scope/local transform。
- determinism utilities。
- diagnostics/provenance。

#### 算法内核

- cycle removal primitive。
- rank primitive。
- crossing/order primitive。
- BK initializer。
- coordinate IR/solver。
- PAVA separation projection。
- fragment compose。
- bounds/containment geometry。
- spacing demand estimator。

#### 生命周期

- prepare。
- bounded demand feedback。
- audit。
- node freeze。
- router dispatch。
- edge finalize。

### 6.2 必须独立

#### Flowchart

- split–join / SESE 主轴。
- feedback hub。
- end 分档和局部 end。
- flowchart pendant。
- 装饰性 group 策略。

#### Architecture

- group-first scope tree。
- macro block/super graph。
- group layout hint。
- hub/client。
- infrastructure row。
- group sizing。
- EGB/side gutter/corridor reservation。
- nested group composition。

### 6.3 共享到什么粒度

判断标准：

> 如果两个图类型使用同一个数学问题和同一组不变量，就共享 Kernel；如果它们对结构含义的解释不同，就留在 Recipe。

例如：

- “相邻变量至少间隔 36px”是共同数学问题，应共享。
- “这两个变量为什么要相隔 36px”是图类型语义，应由 Recipe 决定。
- “一组孩子质心对齐某轴”是共同 objective 形式，应共享。
- “哪些孩子构成 fan，轴是谁”由 FlowchartRecipe 判断。
- “hub 对齐 clients 质心”使用同一 objective 形式，但 hub/client 识别由 ArchitectureRecipe 判断。

## 7. 关键中间数据结构

### 7.1 EffectiveGraphView

```rust
pub struct EffectiveGraphView<'a> {
    pub graph: &'a StableGraph,
    pub active_edges: Vec<EdgeId>,
    pub non_reversible_edges: Vec<EdgeId>,
    pub edge_roles: Vec<EdgeRole>,
}
```

Recipe 负责构建 view，LayeredKernel 只消费。

### 7.2 LayoutScope

```rust
pub struct LayoutScope {
    pub id: ScopeId,
    pub parent: Option<ScopeId>,
    pub members: Vec<NodeId>,
    pub children: Vec<ScopeId>,
    pub kind: ScopeKind,
}

pub enum ScopeKind {
    Root,
    DecorativeGroup,
    SemanticGroup,
    Macro,
}
```

Flowchart 常见只有 root scope；architecture 是 scope tree。

### 7.3 LayeredTopology

```rust
pub struct LayeredTopology {
    pub ranks: Vec<usize>,
    pub layers: Vec<Vec<NodeId>>,
    pub reversed_edges: Vec<EdgeId>,
    pub same_layer_edges: Vec<EdgeId>,
    pub dummy_chains: Vec<DummyChain>,
}
```

它是 rank/order 与 coordinate 之间的稳定边界。

### 7.4 LayoutDraft

Draft 是 Recipe 的可测试编译结果。

流程图：

架构图：

不必强行让两个 Draft 具有完全一样的字段。

### 7.5 NodeLayoutProduct

```rust
pub struct NodeLayoutProduct {
    pub nodes: Vec<NodeGeometry>,
    pub groups: Vec<GroupGeometry>,
    pub topology: TopologyMetadata,
    pub routing_contract: RoutingContract,
    pub diagnostics: LayoutDiagnostics,
    pub demand_state: DemandState,
}
```

它比当前 `LayoutResult` 更明确：

- 不包含最终 edge geometry。
- 明确区分 topology metadata 和 routing contract。
- 能进入 demand probe。
- 还未 freeze。

### 7.6 SpacingDemand 与 RoutingContract

```rust
pub struct SpacingDemand {
    pub scope: ScopeId,
    pub left: LayoutObjectId,
    pub right: LayoutObjectId,
    pub min_gap: f64,
    pub priority: DemandPriority,
    pub source: DemandSource,
}

pub struct RoutingContract {
    pub port_clearance: f64,
    pub corridors: Vec<Corridor>,
    pub side_gutters: Vec<SideGutter>,
    pub same_layer_edges: Vec<EdgeId>,
    pub feedback_edges: Vec<EdgeId>,
}
```

`SpacingDemand` 是布局输入；`RoutingContract` 是冻结后给路由器的输出。不要再把二者混在一个既读又写的 `SpaceBudget` 里。

## 8. SpaceBudget / Route Feedback 的新位置

### 8.1 当前职责过多

当前 `SpaceBudget` 同时扮演：

1. 需求数据。
2. layout hint。
3. 路由读取配置。
4. 节点推开执行器的输入。
5. refine 后兜底契约。

`LayoutRouteFeedback` 同时负责：

1. enrich pressure。
2. enforce 节点间距。
3. 调 router。
4. 调 refine。
5. overlap 失败后的增量重路由。

这使它们从“共享契约”逐渐变成第二套布局协调器。

### 8.2 推荐拆分

```text
旧 SpaceBudget
  ├─ 数据需求部分 ───────▶ SpacingDemand / SpacingIntent
  ├─ 路由消费部分 ───────▶ RoutingContract
  └─ enforce 推点部分 ───▶ 删除；由 Recipe + CoordinateKernel 重解

旧 RouteFeedback
  ├─ 压力读取 ───────────▶ DemandKernel / RoutingDemandProbe
  ├─ 反馈轮次调度 ───────▶ LayoutCoordinator
  ├─ 节点推开 ───────────▶ 删除
  ├─ router 调用 ────────▶ RoutingCoordinator
  └─ edge refine ────────▶ EdgeRefinePipeline
```

### 8.3 新数据流

```text
Recipe Draft
  → DemandKernel 预估 label / port / corridor 需求
  → Recipe 将 demand 编译进对应 scope 的 CoordinateProblem
  → solve
  → RoutingDemandProbe 只读检查候选几何
  → 如有新增 demand：最多重解 1–2 次
  → freeze
  → router 消费 RoutingContract
  → edge refine 只改边
```

这比当前共享补丁层更轻：

- 没有通用 `enforce_horizontal_gaps(&mut nodes)`。
- 没有布局后再猜如何推节点。
- 共享的是需求模型和求解器，而不是共享一个补丁执行器。

### 9.1 是否必须马上移动目录

## 10. 测试结构

### 10.1 Kernel 单元测试

只测试数学和不变量，不构造完整 Diagram：

```text
kernel/graph
  - stable order
  - FAS non-reversible edges
  - dominator/post-dominator

kernel/layered
  - rank constraints
  - order determinism
  - proper graph

kernel/coordinate
  - PAVA
  - hard separation
  - priority objectives
  - degraded fallback

kernel/compose
  - local/global transform
  - nested containment
```

### 10.2 Recipe 编译测试

不渲染 SVG，直接检查 Draft：

Flowchart：

- split 和 join 是否配对。
- feedback edge 是否排除出普通主轴。
- end 是否进入正确 axis。
- 生成了哪些 objective provenance。

Architecture：

- scope tree 是否正确。
- hub/client 是否识别。
- super graph 是否正确。
- group hint 是否生成 pattern placement。
- demand 是否进入正确 scope。

### 10.3 Recipe 求解契约测试

共享测试套件：

```rust
assert_hard_constraints(&product);
assert_deterministic(&recipe, fixture);
assert_no_coordinate_write_after_freeze(&pipeline);
assert_routing_contract_complete(&product);
```

图类型专属断言：

- flowchart：split–join axis、fan symmetry、feedback side。
- architecture：group containment、macro rank、hub centroid、infrastructure row。

### 10.4 Pipeline 生命周期测试

只验证状态转换：

```text
Prepared
  → Draft
  → Candidate
  → ReSolved? (≤ 2)
  → Frozen
  → Routed
  → Final
```

必须钉死：

- freeze 后节点 fingerprint 不变。
- router/refine 不能修改节点。
- feedback 不超过上限。
- 同一 demand 不重复制造振荡。

### 10.5 产品回归测试

保留现有 benchmark 和 SVG 目视，但不把具体像素快照当唯一规格。

优先检查：

- 结构不变量。
- 硬正确性。
- 诊断和降级。
- product-gate 指标。

## 11. 渐进迁移计划

### M0：画清当前写权和调用图

1. 列出 node coordinate 的全部写者。
2. 标记它属于 Recipe、Kernel、Coordinator、Router 中哪一层。
3. 对无法归类的函数暂停扩展。
4. 保留文档 11 的 M0 诊断。

完成标准：

- 每个节点写者有明确未来归属。
- route/refine 后写节点的入口全部已知。

### M1：统一 PreparedLayoutInput

1. 引入稳定 node/edge id。
2. 收敛 architecture `GraphIndex` 与 Sugiyama petgraph 的输入适配。
3. 暂不删除旧结构，先提供 view/adapter。
4. GroupTree 使用现有 `common/divide_and_conquer` 基础。

完成标准：

- 两个 Recipe 可以从同一个 prepared input 构建自己的 effective graph。
- 不依赖 HashMap 迭代顺序。

### M2：落地 CoordinateKernel

按文档 11 执行：

1. Coordinate IR。
2. hard projection。
3. objective solver。
4. flowchart StructureModel。
5. 移除 Sugiyama 坐标后多写者。

完成标准：

- FlowchartRecipe 使用统一坐标求解。
- 文档 11 的完成定义逐步满足。

### M3：建立显式 FlowchartRecipe

1. 将 flowchart facade 改成 Recipe 编排。
2. rank/order 通过 LayeredKernel 窄接口调用。
3. group divide 不再向共享内核注入 flowchart 特判。
4. 输出 NodeLayoutProduct。

完成标准：

- 流程图完整逻辑可在 `recipe/flowchart` 中顺序阅读。
- 公共 pipeline 看不到 split/end/feedback 语义。

### M4：建立显式 ArchitectureRecipe

1. 保留 architecture two-phase 的语义顺序。
2. 组内 layered path 委托 LayeredKernel。
3. 无 group 路径删除平行 rank/order。
4. hub/client/infrastructure 变为 ArchitectureIntentBuilder。
5. macro block 坐标尝试使用同一 CoordinateKernel。

完成标准：

- 架构图完整逻辑可在 `recipe/architecture` 中顺序阅读。
- 公共 Kernel 无 architecture 分支。

### M5：拆分 SpaceBudget

1. 提取 `SpacingDemand`。
2. 提取 `RoutingContract`。
3. DemandKernel 只读计算。
4. 删除冻结后的 `enforce_horizontal_gaps`。
5. demand 由各 Recipe 映射到正确 scope。

完成标准：

- `SpaceBudget` 不再同时是需求、配置和执行器。
- 所有节点推开都回到坐标求解。

### M6：引入 Coordinator 和冻结类型

1. `run_recipe` 统一生命周期。
2. 有界 feedback。
3. `NodeLayoutProduct → FrozenNodeLayout`。
4. 路由签名逐步改成只读 nodes。
5. pipeline 中 `algo == "architecture"` 清零。

完成标准：

- Coordinator 不知道图类型语义。
- freeze 后节点不可修改。

### M7：删除旧层

1. 删除 architecture 旧 post-layout direct mutations。
2. 删除重复 rank/order/coordinate。
3. 删除 space budget guard 的节点推点职责。
4. 删除只为旧时序存在的 hook、开关和回滚逻辑。
5. 更新核心手册时序图。

完成标准：

- 没有“新架构 + 旧补丁层”双轨长期共存。

## 12. 风险与防护

### 12.1 过度抽象

风险：

- 为两个 Recipe 提前设计万能 Layout DSL。
- 每个差异都变成 trait/hook。

防护：

- Recipe 使用显式 Rust 流程。
- 只有第二个真实消费者出现后才抽 Kernel。
- trait 保持少量生命周期方法。
- 图类型目标 builder 不做动态插件系统。

### 12.2 Profile 字段爆炸

风险：

- 把语义差异压成几十个 bool/weight。

防护：

- 数值参数可以进入 profile。
- 结构识别和阶段顺序留在 Recipe。
- 如果一个字段改变“执行哪条业务链”，它通常不应只是 profile bool。

### 12.3 Kernel 被图类型污染

防护：

- Kernel API 不接受 `DiagramType`。
- Kernel 不读取 entity type 判断 hub/end。
- Kernel 测试使用人工构造的小模型。
- 图类型枚举只在 registry/recipe 选择层出现。

### 12.4 Recipe 再次复制算法

防护：

- Recipe 不实现 PAVA、rank simplex、BK、overlap solver。
- 重复数学代码必须回到 Kernel。
- 代码评审必须回答“这是语义差异还是算法重复”。

### 12.5 迁移期双写

防护：

- 每迁移一个行为就删除旧写者。
- 可以双跑比较，但只能有一个结果进入产品输出。
- 每阶段记录 coordinate writer inventory。

### 12.6 Architecture 层次求解复杂

控制：

- 首期先复用组内 CoordinateKernel。
- macro block 先保持现有定位，只换数据边界。
- 等 leaf scope 稳定后再把 macro position 编译成 CoordinateProblem。
- 不要求一次性统一所有层次。

## 14. 完成定义

1. FlowchartRecipe 和 ArchitectureRecipe 拥有各自显式逻辑链。
2. 公共 pipeline/Coordinator 不包含图类型业务分支。
3. rank/order/coordinate 的数学实现位于共享 Kernel。
4. 文档 11 的 CoordinateKernel 被两个 Recipe 复用。
5. FlowchartRecipe 负责 split–join/end/feedback。
6. ArchitectureRecipe 负责 scope/macro/hub/group sizing。
7. SpaceBudget 被拆成 `SpacingDemand + RoutingContract`。
8. route feedback 只读地产生 demand，由 Coordinator 有界重解。
9. 节点 freeze 后 router/refine 不再修改节点。
10. Kernel、Recipe compiler、Recipe solver、生命周期分别可独立测试。
11. Kernel 不接受 `DiagramType`，不包含图名或节点名特判。
12. 两个图类型既没有完整 fork，也没有被塞进一条 hook-heavy 巨型管线。

## 15. 给执行 Agent 的最短规则

```text
1. 先判断改动属于 Recipe、Kernel、Coordinator 还是 Router。
2. “为什么这样摆”属于 Recipe；“如何解这个数学问题”属于 Kernel。
3. Kernel 禁止读取 DiagramType 和业务 entity type。
4. Recipe 可以不同，不要为了形式统一强行抽象。
5. 不建立万能 Phase DSL，不继续堆 hook。
6. Diagram 先编译为 Draft/Intent，再求解。
7. SpacingDemand 是数据，不是推点函数。
8. Router 消费 FrozenNodeLayout，不拥有节点写权。
9. 两个真实消费者之前不要抽新公共层。
10. 每迁移一个行为，删除一个旧写者。
11. 测试分四层：Kernel、Recipe compile、Recipe solve、lifecycle。
12. 文档 11 保持为 CoordinateKernel 的详细规格。
```
