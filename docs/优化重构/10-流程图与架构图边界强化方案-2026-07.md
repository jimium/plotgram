# 流程图与架构图边界强化方案

> 日期：2026-07-23  
> 前置：[09-布局路由算法全面技术审查与重构建议](./09-布局路由算法全面技术审查与重构建议-2026-07.md)、[布局与路由核心手册](../总结经验/布局与路由核心手册-2026-07.md)  
> 定位：回答「是否彻底分裂」之后的**可执行收敛方案**——强化边界，而非 fork 两套系统  
> 约束：AGENTS.md §2 确定性、§5 手册、禁止图名特判；门禁临时规则见 §8（正确性仍硬）

---

## 0. 结论与原则

**不要彻底分裂。** 流程图与架构图应在语义层 / 节点布局门面分开（已分开），在几何引擎与路由管线共享（应继续共享）。

当前真正的问题不是「共享太多」，而是 **四类边界模糊**：

| # | 耦合点 | 症状 | 正确方向 |
|---|--------|------|----------|
| 1 | 两套 group 语义并存 | 用户用错图种时表现怪异 | **产品边界硬化** + 弱化 flowchart group |
| 2 | architecture_v2 与 sugiyama_v2 rank/order 重复 | 改一处易漏另一处 | **更多委托** sugiyama_v2 |
| 3 | 路由层 `DiagramType` 分支扩散 | 修 flowchart 误伤 architecture | **收敛到 OrthoRoutingProfile / hook** |
| 4 | pipeline 字符串 `algo == "architecture"` | 管线图种感知、难扩展 | **PostLayoutHook / AlgoProfile** |

### 保留共享 vs 加强隔离

```text
保留共享                         加强隔离
────────────────────────────────────────────────────────
sugiyama_v2 引擎                 FlowchartLayout（仅 flowchart）
LayoutPipeline 骨架              ArchitectureV2Layout（仅 architecture）
orthogonal 路由核心              OrthoRoutingProfile（图种参数）
refine / sanitize / label        PostLayoutHook / AlgoProfile
group_frame 基础设施             废弃/弱化 flowchart group_divide
```

### 明确不做

- ❌ fork 正交路由为 `orthogonal_flowchart` + `orthogonal_architecture`
- ❌ fork `LayoutPipeline`
- ❌ fork `sugiyama_v2` 引擎
- ❌ 为压 stress 数字加图名特判分支

## 2. 问题 1：两套 group 语义 — 产品边界硬化

### 2.1 目标

让用户在写 DSL 时**几乎不可能用错图种却还不自知**；代码侧不再试图让 flowchart 的 group「赶上」architecture。

| | 流程图 | 架构图 |
|--|--------|--------|
| group 角色 | 阅读辅助（后验框） | 域边界 / macro rank 本体 |
| 布局驱动 | 全局 / 分治 Sugiyama | two_phase：组内 → 组间 |
| 推荐强度 | **弱**（有分层语义请换 architecture） | **强** |
| 嵌套 group | 不承诺完善 | 一等公民 |

### 2.2 方案

#### P1-a. 文档与选型指南（产品层，先做）

1. 在 [visual-language README](../specs/visual-language/README.md) 增加一页「流程图 vs 架构图决策树」：
   - 问：节点是**步骤**还是**组件**？
   - 问：group 是否表达**分层 / 域边界**且组间有依赖边？
   - 是 → `architecture`；否 → `flowchart`（且尽量不写嵌套 group）
2. 更新 [group-layout-and-frame.md](../guides/group-layout-and-frame.md)：flowchart 段明确标注「嵌套 group / 组内 `layout:` hint **不支持**；需要时改用 architecture」。
3. showcase 样例：凡「按层分组的流程」迁到 architecture 或在 README 标注反例。

#### P1-b. LayoutLint / validation 劝导（软引导）

新增或扩展 lint / validate 规则（**Warning，不硬失败**）：

| 规则（建议名） | 触发条件 | Advice |
|----------------|----------|--------|
| `FlowchartNestedGroup` | `diagram_type=flowchart` 且存在嵌套 group | 建议改为 `architecture`，或展平为单层 group |
| `FlowchartGroupWithCrossGroupEdges` | flowchart 中边两端分属不同 group 且拓扑像分层 | 建议改用 architecture（组驱动 macro rank） |
| `ArchitectureStepLikeChain` | architecture 无 group、节点链状且 entity type 多为 process/decision | 建议改用 flowchart |

实现落点建议：

- 几何无关的图种误用 → `validation/` 或 prepare 阶段（可给 FixAction）
- 依赖布局结果的 → `layout/lint/` + `advice.rs`

#### P1-c. 代码侧弱化 flowchart group（中期）

| 动作 | 说明 |
|------|------|
| **冻结** `group_divide` 新能力 | 不再加嵌套、不再读 group `layout:` hint |
| **默认路径收缩** | 无 group 或仅「装饰性单层 group」时走整图 `FLOWCHART_PRESET`；多 group 仍走现有 divide，但不扩展 |
| **可选废弃路径** | 评估后：多 group 流程图在 lint 强劝后，可考虑将 `group_divide` 标为 legacy，最终只保留「整图 Sugiyama + group_frame 后验框」 |

> 注意：弱化 ≠ 立刻删除。先文档 + lint，再收缩能力，避免 showcase 一次性炸掉。

### 2.3 验收

- 新用户读决策树后能正确选型（人工走查 showcase 目录）
- flowchart 嵌套 group 必出 Warning + FixAction 文案
- 不出现「为流程图补 architecture 式 two_phase」的新 PR

## 3. 问题 2：architecture_v2 与 sugiyama_v2 重复 — 委托收敛

### 3.1 目标

**无顶层 group** 的 architecture 路径尽量委托 `sugiyama_v2` + `ARCHITECTURE_PRESET`；`architecture_v2/layout/{rank,order}` 只保留 **two_phase / hint 几何模式**真正需要的差异，禁止平行演进两套完整分层引擎。

### 3.2 现状分层

```text
ArchitectureV2Layout::compute
  ├─ 有顶层 group → two_phase
  │     ├─ 组内复杂拓扑 → intra_sugiyama（已委托 ✅）
  │     ├─ 组内 hint 几何 → group_layout_hint（保留）
  │     └─ 组间 macro → macro_block（architecture 专属，保留）
  └─ 无顶层 group → layout/{rank,order,coordinate}（部分重复 ⚠️；代码注释已标注「冻结扩展」，仅服务无组路径 + hint 几何，但仍存在仅服务旧路径的死代码，需在 M2-b 清理）
```

### 3.3 方案（分步，可回滚）

#### M2-a. 无组路径整图委托（首选）

```rust
// 伪代码：ArchitectureV2Layout::compute
if !has_top_level_groups(diagram) {
    return sugiyama_v2::engine::compute_with_preset(
        diagram,
        &ARCHITECTURE_PRESET,
        /* config mapped from ArchitectureV2LayoutConfig */
    );
}
// else: two_phase ...
```

前置检查：

1. 对比当前无组 architecture showcase / product 样例的节点坐标与边质量（允许 AGENTS §8 门禁暂停下观察；正确性穿组 / det 仍硬）
2. 确认 architecture 专属 post_layout（hub 质心等）仍能在委托结果上生效
3. `ARCHITECTURE_PRESET` 与现有 `architecture_v2/layout/constants` 间距对齐（已对齐：layer_gap=72 / node_gap=32，两者完全相等）

#### M2-b. 删除死代码

委托稳定后：

- `layout/rank.rs`、`order.rs` 中仅服务「无组路径」的代码删除或降为 `#[cfg(test)]` 对照
- 模块头注释改为：「仅 two_phase / hint 路径使用；无组路径委托 sugiyama_v2」
- 保留 `coordinate` 对 sugiyama 的复用接口，或一并走 engine 出口

#### M2-c. 禁止回潮规则

在 `architecture_v2/layout/mod.rs` 与 AGENTS / 手册中约定：

> 新增分层启发（barycenter 权重、pendant、fan 对称等）优先改 `sugiyama_v2` + preset；不得在 architecture 无组路径再写一份平行实现。

### 3.4 验收

- 无顶层 group 的 architecture 样例：`det=true`，穿组 = 0
- `architecture_v2/layout/rank.rs` + `order.rs` 行数显著下降，或明确只被 two_phase 引用
- 新增分层优化只落在 `sugiyama_v2/` 或 preset

## 4. 问题 3：路由层 DiagramType 分支 — 收敛到 Profile

### 4.1 目标

正交路由热路径内 **禁止新增** `if diagram_type == Architecture` / `Flowchart`。  
图种差异只能通过：

1. `OrthoRoutingProfile` 字段（布尔 / 权重 / 枚举）
2. 已登记的阶段开关（由 profile 决定是否调用某 phase）
3. `EdgeRoutingStrategy` / 测试夹具读取 `profile.merge_policy_diagram_type()` 等**派生** API

### 4.2 迁移清单

| 当前散落点 | 收敛方式 |
|------------|----------|
| `edge_merge_policy::requires_semantic_merge(DiagramType)` | 改为读 `profile.semantic_merge`（已有字段） |
| `semantic_trunk_merge.rs` 入口 `matches!(Architecture)` | 入口只看 `profile.semantic_merge`；调用方已持有 profile 则不再传 DiagramType |
| `lane_assignment.rs` 图种判断 | 映射为 `profile.corridor_lane_offsets` / `separate_unrelated_trunks` |
| `segment_pair` 间距按图种 | 已有/扩展为 `profile.parallel_gap`（architecture 已有专用常量） |
| `label_candidate` 按 DiagramType 配参 | 抽 `LabelPlacementConfig::from_profile(&OrthoRoutingProfile)` 或并入 profile |
| 测试里直接 `DiagramType::Architecture` | 改为 `OrthoRoutingProfile::for_diagram_type(...)` 或显式构造 profile |

### 4.3 工程护栏

1. **API 收窄**：`edges_may_share_trunk(..., diagram_type)` 改为 `edges_may_share_trunk(..., &OrthoRoutingProfile)`（或只传 `semantic_merge: bool`）。破兼容可直接改（项目无向后兼容约束）。
2. **CI / 本地 grep 门禁**（建议加到 `scripts/` 或文档检查清单）：

```bash
# 允许清单：profile.rs、mod.rs（APPLICABLE_TYPES 注册表）、测试、kinds/
# 禁止：edge_routing_orthogonal/** 业务代码新增 DiagramType::Architecture|Flowchart 匹配
rg 'DiagramType::(Architecture|Flowchart)' \
  crates/plotgram-core/src/layout/edge/edge_routing_orthogonal \
  --glob '!*test*' --glob '!profile.rs' --glob '!mod.rs'
```

> 也可换更精确的模式，只匹配业务分支形态，避免误伤注册表数组：

```bash
rg '(if\s+.*DiagramType::|matches!\(.*DiagramType::|DiagramType::(Architecture|Flowchart)\s*=>)' \
  crates/plotgram-core/src/layout/edge/edge_routing_orthogonal \
  --glob '!*test*' --glob '!profile.rs'
```

3. **新功能评审句式**：PR 描述须写「本图种差异落在哪个 profile 字段 / 哪个 hook」；写不出则打回。

### 4.4 验收

- `edge_routing_orthogonal/` 业务路径无裸 `DiagramType::Architecture` 匹配（测试、`profile.rs`、`mod.rs` 的 `APPLICABLE_TYPES` 注册表除外）
- 改 flowchart 权重不触及 architecture 专用 phase 的调用条件（由 profile 布尔隔离）
- 新增路由特性默认「关」，仅 architecture profile 打开（或反之），而不是 `if Architecture { ... }`

## 5. 问题 4：pipeline `algo == "architecture"` — Hook 化

### 5.1 目标

`LayoutPipeline` **图种无关**：不出现字符串算法名分支；architecture 专属行为由策略声明的 hook 注入。

### 5.2 已有与缺口

| 已有 | 缺口 |
|------|------|
| `AlgoProfile::from_algo` → `PostRouteHook`（PRS 扩壳） | `pipeline.rs` 内仍有 hub 质心 / pendant / stub occupancy 的 `algo == "architecture"` |
| | `group_frame/spec.rs`、`pass.rs`、`padding.rs` 仍按 algo 字符串切默认 |

### 5.3 方案

#### S4-a. 扩展 `LayoutStrategy` 声明面（推荐）

在 `traits.rs` 增加可选钩子（默认空实现，不破坏现有算法）：

```rust
pub trait LayoutStrategy {
    // ... 现有方法 ...

    /// 节点布局完成后、边路由前/路由管线中的图种专属步骤。
    /// 默认 Noop；ArchitectureV2Layout 覆写。
    fn post_layout_hooks(&self) -> LayoutHooks {
        LayoutHooks::default()
    }
}

pub struct LayoutHooks {
    /// group_frame recompute 之后、space_budget 之前：hub 质心、跨 scope pendant 等。
    /// （实际管线位置：pipeline.rs group_frame recompute → 本钩子 → space_budget_guard）
    pub after_group_frame_recompute: Option<fn(&Diagram, &mut LayoutResult)>,
    /// 节点冻结 + sanitize + enforce_d_stage_separation 之后：stub occupancy 真修等。
    /// （实际管线位置：NodeFreeze → sanitize → enforce_d_stage_separation → 本钩子）
    /// 钩子契约：必须在 sanitize / d_stage 之后触发，否则会引发穿组或干线退化回归。
    pub after_node_freeze: Option<fn(&Diagram, &mut LayoutResult)>,
}
```

或更贴合现有结构：把 `AlgoProfile` 从「仅 post_route」扩展为完整 **LayoutAlgoProfile**：

```text
LayoutAlgoProfile
  ├─ post_route_hook               （已有）
  ├─ after_group_frame_recompute   （迁入 hub / pendant；注意命名与时序：group_frame 之后、space_budget 之前）
  ├─ after_node_freeze             （迁入 stub occupancy；须在 sanitize / d_stage 之后触发）
  └─ group_frame_defaults          （迁入 group_frame/spec/padding 默认）
```

`pipeline.rs` 只调用 `profile.after_group_frame_recompute(...)`，不再 `match algo`。

#### S4-b. group_frame 默认值迁移

`GroupFramePass::resolve` / `spec` / `padding.rs` 中 `algo == "architecture"` 改为：

- 读 `LayoutHooks::group_frame_defaults`，或
- 读 `DiagramProfile` / plan 上已解析的默认（图种契约进 profile，不进 pipeline 字符串）

#### S4-c. 删除散落匹配

迁移完成后 `rg 'algo == "architecture"'` 在 `layout/` 下应为 0（测试除外）；仅允许 `AlgoProfile::from_algo` / registry 一处映射。

### 5.4 验收

- `pipeline.rs` 无 `algo == "architecture"`
- 新增图种专属后处理只需实现 hook + 在 `from_algo` / `LayoutStrategy` 登记，不改 pipeline 主干
- architecture product 样例视觉与正确性不回归（穿组 / det）

## 6. 实施优先级与依赖

```text
短期（1–2 周）                         中期（2–4 周）                    产品并行
─────────────────────────────         ─────────────────────────       ────────────
S4 Hook 化 pipeline 残留               M2 无组路径委托 sugiyama_v2      P1-a 决策树文档
S3 Profile 收敛 merge/lane/trunk       M2-b 删 rank/order 死代码         P1-b Lint Warning
禁止路由层新增 DiagramType 分支         P1-c 冻结/弱化 group_divide       showcase 反例标注
grep 护栏进开发检查清单
```

**建议顺序**：先 **S4 + S3**（降低误伤面），再 **M2**（删除重复），产品文档 / lint **全程并行**。

依赖关系：

- S4 不依赖 M2；可先合
- S3 与 S4 独立，可并行 PR
- M2 依赖 architecture post_layout 仍在 hook 路径上可跑（建议 S4 先完成或至少 hub/pendant 已 hook 化）
- P1-c 弱化 group_divide 依赖 P1-a/b 已上线，避免用户无引导就丢能力

## 8. 风险与回滚

| 风险 | 缓解 |
|------|------|
| 无组 architecture 委托 sugiyama 后坐标漂移 | M2-a 先双跑 diff 节点坐标；异常则保留旧路径开关一个 release 周期 |
| Profile 字段爆炸 | 新字段必须有「默认 = flowchart 行为」；architecture 显式打开；禁止第三套隐式默认 |
| Lint 误报劝用户改图种 | Warning + 可忽略；FixAction 仅建议；不进 CI hard fail（除非后续证明误报率极低） |
| Hook 签名过重拖垮 pipeline | 钩子保持「可选 fn / 小 trait」；禁止把整段路由搬进 hook |

回滚策略：每个子项独立 PR；不合「大爆炸」；委托路径可用 `layout_options` 临时开关回退（阶段结束后删除开关）。

---

## 9. 成功标准（本方案完成定义）

1. **管线**：`LayoutPipeline` 无图种 / 算法名字字符串分支；architecture 特化全部经 Hook / AlgoProfile。
2. **路由**：正交路由业务代码无裸 `DiagramType` 匹配；差异只在 `OrthoRoutingProfile`。
3. **布局引擎**：architecture 无组路径委托 sugiyama_v2；无平行 rank/order 演进。
4. **产品**：文档决策树 + lint 劝导上线；flowchart group 能力冻结，不再追赶 two_phase。
5. **不做清单**被遵守：未 fork 路由 / pipeline / sugiyama。

### 11.2 发现的问题与修正建议

#### 问题 1（遗漏）：§1.2 漏列 `group_frame/padding.rs`

`crates/plotgram-core/src/layout/group_frame/padding.rs:12` 同样有 `if algo == "architecture"`（选 `GroupPadding::architecture_v2()` vs `uniform`）。该文件注释自称"从 mod.rs 拆分而来，无行为变更"，推测拆分晚于方案撰写。**建议补入 §5.3 S4-b 迁移清单**，与 `spec.rs` / `pass.rs` 并列。

#### 问题 2（grep 护栏误报，须修）

§4.3 提议的护栏：

```bash
rg 'DiagramType::(Architecture|Flowchart)' \
  crates/plotgram-core/src/layout/edge/edge_routing_orthogonal \
  --glob '!*test*' --glob '!profile.rs'
```

会误报 `crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/mod.rs:22-27` 的 `APPLICABLE_TYPES` 数组——这是图种注册表，不是业务分支。方案 §4.3 文字说"允许清单：profile.rs、测试、registry、kinds/"，但 grep 的 `--glob` 没排除 `mod.rs`。**建议改为**：

```bash
rg 'DiagramType::(Architecture|Flowchart)' \
  crates/plotgram-core/src/layout/edge/edge_routing_orthogonal \
  --glob '!*test*' --glob '!profile.rs' --glob '!mod.rs'
```

或换更精确的模式，只匹配业务分支形态：

```bash
rg '(if\s+.*DiagramType::|matches!\(.*DiagramType::|DiagramType::(Architecture|Flowchart)\s*=>)' \
  crates/plotgram-core/src/layout/edge/edge_routing_orthogonal \
  --glob '!*test*' --glob '!profile.rs'
```

#### 问题 3（hook 时序契约，须修）

§5.3 S4-a 提议的钩子名与实际管线时序有出入。对照 `crates/plotgram-core/src/layout/pipeline.rs`：

- **L195 hub/pendant**：实际运行在 group_frame recompute（L189-193）**之后**、space_budget_guard（L216）**之前**。提议的钩子名 `after_space_budget` 与时序相反，**应改为 `after_group_frame_recompute` 或 `before_space_budget`**。
- **L265 stub occupancy**：实际运行在 NodeFreeze（L225）之后，且依赖 sanitize（L250）+ `enforce_d_stage_separation`（L261）已执行完毕。提议的 `after_node_freeze` 大致正确，但**钩子契约须显式注明"必须在 sanitize / d_stage 之后触发"**，否则迁入 hook 后顺序错乱会引发穿组或干线退化回归。

#### 问题 4（措辞偏保守）：§3.3 "已接近" 实为 "已对齐"

`ARCHITECTURE_PRESET`（`preset.rs:87-90`）与 `architecture_v2/layout/constants.rs:7-9` 的 layer_gap=72 / node_gap=32 完全相等。方案写"已接近"略保守，可改为"已对齐"。

#### 问题 5（framing 张力）：§3.2 "部分重复 ⚠️" 与代码注释 "冻结扩展" 的措辞冲突

`crates/plotgram-core/src/layout/node/architecture_v2/layout/mod.rs:5-6` 注释明确 rank/order/coordinate 已**冻结扩展**（仅服务无组路径 + hint 几何）。方案 §3.2 用"部分重复"暗示仍在平行演进，与现状不符。**建议 §3.2 补一句**："代码注释已标注冻结扩展，但仍存在仅服务旧路径的死代码，需在 M2-b 清理"，使 §3.2 与 M2-b 删死代码的动机呼应更顺。
