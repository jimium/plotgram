# 学习工作 · Plotgram —— 让 Agent 会画图的 AI 原生图表 DSL

**标签：** #学习工作

> 一图胜千言。但当"画图的人"变成 AI Agent，现有工具却没一个为它设计。
> Plotgram 把这件事重做了一遍：一套从语法、错误模型到操作范式都为"AI 生成、人类阅读"而生的图表 DSL。

---

## 1. Demo 简介

**是什么：** 一个为 AI Agent 生成图表而设计的图表描述语言（DSL）+ 渲染引擎，Rust 核心，三端同源交付（CLI / HTTP API / WASM 浏览器），并附带一个可对话出图的 Agent Demo。

**面向谁：**
- 做 AI Agent 应用的开发者——想让 Agent 拥有"按需出图、按需改图"的能力
- 技术社区与开源用户——关心"AI 时代的图表该怎么画"
- 任何需要用图说清楚复杂系统的人（架构师、技术写作者、产品经理）

**核心功能：**

1. **对话即出图** —— Agent Demo 里用自然语言描述需求，Agent 理解语义、生成 DSL、调用 WASM 渲染出 SVG，改一行不用重画整张。
2. **一套语法，六种图** —— 流程图、时序图、架构图、状态机、ER 图、思维导图，共用同一套 DSL，引擎按图类型自动选择最优布局算法。
3. **AST 可操作，增量改图** —— DSL 不仅是文本，更是可序列化的 AST。支持语义级 Diff & Patch，Agent 可以"把节点 A 改成数据库"、"加一条从 B 到 C 的边"，而不必重新生成整张图。

## 2. Demo 创作思路

### 灵感来源

我在做 AI Agent 相关应用时反复撞到同一堵墙：**Agent 不会画图**。

让 Agent 调 Mermaid，它经常写出语法错误的图——Mermaid 有多种箭头风格、大量隐式规则，对 LLM 不友好；出错后只返回一句模糊的文本报错，Agent 没法自我修复，只能整张重画，越改越乱。让 Agent 直接生成 SVG，又丢失了语义——没有布局、没有结构、改一个节点要重画整张。

我意识到这不是"换一个画图库"能解决的，而是**语境错了**：现有工具都是为"人类手写"设计的，而我要服务的是"AI 生成"这个全新场景。

### 想解决的问题

一个真实的痛点链：

| 痛点 | 后果 |
|------|------|
| 语法变体多、隐式规则多 | Agent 一次写对的概率低 |
| 出错只返回模糊文本 | Agent 无法自修复，只能重试或放弃 |
| 文本是唯一产物 | 改一个节点要重新生成整张图，成本高、不稳定 |
| 布局要手写坐标或 hint | Agent 不擅长算坐标，图经常丑或乱 |

**目标：让 Agent 像"会画图的同事"一样——一次听懂需求、画对图、改对图。**

### 为什么做这个方向（定位取舍）

按照 April Dunford《Obviously Awesome》的定位框架，我对 Plotgram 做了明确的语境设定：

1. **替代方案是什么** —— 不是"不用 Mermaid"，而是"Agent 无法可靠地产出/修改图表"。用户今天的退路是让 Agent 调 Mermaid（常失败）或直接吐 SVG（无语义、不可改）。
2. **真实独特属性**（可验证，不编造）：
   - 固定语法——3 种箭头、显式结构、无隐式规则
   - 结构化错误诊断——JSON 返回错误码、行列位置、上下文、修复建议
   - AST 一等公民——可导出 JSON、语义 Diff & Patch
   - 三端同源——CLI / HTTP API / WASM 共享同一个 Rust 核心
   - 70+ 真实示例、6 种图表、7 种布局算法
3. **独特价值** —— Agent 一次生成对的图、增量改对已有的图；一图胜千言的能力，被 AI 放大。
4. **谁在乎** —— 做 Agent 应用的开发者、技术社区评委、需要用图说清楚复杂系统的人。
5. **品类** —— 不是"更好的 Mermaid"，而是"AI 原生图表 DSL"这个新语境。

**关键取舍：** 不去和 Mermaid 比"谁语法更全"，而是承认它们为人类手写优化、Plotgram 为 AI 生成优化——语境不同，设计不同。

## 4. TRAE 实践过程

### 协作模式：人做主干，AI 做叶子

Plotgram 是一个 30,000+ 行 Rust 核心、959 个测试用例、7 种布局算法、4 种边路由策略的项目。核心引擎约 **70% 的实现代码由 TRAE 生成**，算法迭代速度比纯人工快 **3-4 倍**。

但关键不是"让 AI 从零写一个完整项目"，而是分层协作：

- **人类负责**：产品方向、算法选型决策、架构设计、关键 API 设计、质量验收标准
- **AI 负责**：Parser 实现、数据结构编码、具体算法实现、测试用例、重构与 Bug 修复

一句话方法论：**人定义算法的骨架，AI 填充肌肉。**

### 开发全流程（五个关键阶段）

**阶段一：从概念到 DSL 设计（Day 1-2）**
没有直接写代码。先用自然语言描述目标，让 TRAE 列出 3 种语法方案并逐一评估优缺点（LLM 生成友好度、可读性、扩展性），人选定后让 TRAE 写出 EBNF 语法规范作为后续实现的 contract。

**阶段二：Parser 与基础框架（Day 3-5）**
基于 EBNF 让 TRAE 实现手写递归下降 Parser。先定义 AST 数据结构（人审稿），再按优先级逐条实现语法规则，每完成一条立即要求 AI 写对应单元测试。

**阶段三：布局算法实现与迭代（Day 6-15，最长阶段）**
人定算法选型（如 Sugiyama 分层），TRAE 调研实现细节。第一版出来后人通过视觉检查 + 量化指标（交叉数、ink 用量、边长方差）找问题，让 TRAE 分类问题并提改进方案，人选方案后让 AI 实现——两轮复盘法。

**阶段四：边路由与细节优化（Day 16-22）**
正交路由、Edge Bundling、像素量化等。小步快跑：每次给 TRAE 一个明确小目标（如"实现正交边路由通道规划"），完成后立即用 snapshot 测试验证，发现 bug 先让 TRAE 自诊断再修复。

**阶段五：前端 Playground 与部署（Day 23-25）**
用 TRAE 快速搭建 React+Vite 的 Playground、官网、7 套主题、自动化部署脚本和 Nginx 配置。

## （可选）开发心得：AI 协作的几条经验

经过整个项目，我们总结了在复杂算法项目中使用 TRAE 的几条经验：

1. **不要上来就写代码** —— 遇到设计决策，先让 AI 提多个方案、再让 AI 评价各方案优缺点，人做最终决策。AI 的"发散 + 收敛"能力极大扩展了思路。
2. **需求不清时让 AI 问你** —— 不要让 AI 猜。让 AI 列出"还需要明确的关键决策点"，人一一回答后再实现，避免走弯路。
3. **感觉好用 ≠ 真的好用** —— 每实现一个算法版本，建立量化指标（交叉数、ink 用量、边长方差），让优化有客观依据。视觉检查 + 量化指标双保险。
4. **EBNF / 类型签名 / 测试都是 Contract** —— 在让 AI 写代码前，先定义好输入输出类型、语法规范、测试预期。Contract 越清晰，AI 输出质量越高。
5. **每次一个明确的小目标** —— 不要让 AI"实现整个布局算法"，而是拆成"实现分层分配""实现同层排序""实现坐标计算"等小任务，每步验证后再继续。
6. **长任务复盘 2 次** —— 第一版实现后，人通过测试和视觉检查找出问题，和 AI 一起分类问题、讨论改进方案，第二轮迭代后效果通常大幅提升。
7. **快速模型做事，强模型检查重构** —— 落地用快速模型出活，用更强的模型做检查和重构（马后炮式 review），性价比最高。

> **关键结论：** AI 编程助手不是"替代程序员"，而是"放大程序员"。一个有清晰架构思维和算法判断力的开发者，配合 AI 可以实现远超个人产能的项目。但如果缺乏方向感和质量把控，AI 也会快速产出大量垃圾代码。Plotgram 的"让 Agent 会画图"，本身就是这种协作模式的产物——人定义了"为 AI 生成而设计"这个语境，AI 帮我把这个语境落成了 30,000 行可运行的代码。
