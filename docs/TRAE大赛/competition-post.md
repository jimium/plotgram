## 1. Demo 简介

**是什么：** FlowML（Plotgram）是一款**面向 AI Agent 原生设计的智能图表描述语言与自动布局渲染引擎**。它不是 Mermaid 的替代品，而是从语法设计、错误模型到操作范式，整套为「AI 生成、人类阅读」场景从零构建的图表基础设施。产品形态包含 Rust 核心引擎、CLI 命令行工具、HTTP API 服务、WASM 浏览器包，以及在线 Playground 编辑器。

**面向谁：**
- **AI 应用开发者**——在 LLM 应用、Agent 框架、AI 编程助手中集成可靠的图表生成能力
- **技术文档与知识管理从业者**——需要 AI 辅助生成架构图、流程图、思维导图的团队
- **算法与可视化爱好者**——关注自动布局算法、图论可视化的技术人群

**主要功能：**

### 功能一：6 种图表类型 + 7 种布局算法的智能渲染引擎
支持流程图（Flowchart）、时序图（Sequence）、架构图（Architecture）、状态机图（State）、ER 图、思维导图（Mindmap）六大类图表。内置 Sugiyama-v2（增强分层布局）、力导向布局、圆形布局、思维导图布局、时序布局、架构图双层布局等 7 种布局算法，以及正交路由、贝塞尔路由、弧形路由、直线路由 4 种边路由策略。引擎会根据图表类型自动选择最优布局算法，用户（或 AI Agent）只需表达「实体」和「关系」，无需关心坐标、弯曲、间距等视觉细节。

（此处插入产品主界面 / 多图表类型展示截图）

### 功能二：为 AI 生成优化的语法设计 + 结构化错误反馈
语法从 LLM 生成模式出发做极简设计：箭头只有 3 种（`->` 主动流向、`-->` 被动响应、`<->` 双向），实体用统一的 `entity` 关键字声明，语义通过 `type` 属性表达（如 `type: database` 自动渲染为数据库图标+圆柱形状）。错误反馈为结构化 JSON，包含错误码、行列位置、上下文信息、修复建议，AI Agent 可在 1 次重试内完成自我修正，告别「渲染空白、反复试错」的窘境。

（此处插入错误反馈示例 / 语法对比截图）

### 功能三：AST 一等公民——语义级 Diff 与 Patch
与传统图表工具的「文本即一切」不同，FlowML 的 AST 是一等公民：支持序列化为 JSON、语义级别的 Diff（不是行比较，而是「新增了哪个实体、修改了哪个属性」）、以及 AST Patch 程序化修改。Agent 可以先生成初版图表，再根据用户反馈只 patch 需要修改的部分，不需要重新生成整张图，大幅降低出错概率。

## 2. Demo 创作思路

**灵感来源：**

在使用 AI 编程助手和 LLM 应用的过程中，我们发现一个反复出现的痛点：**让 AI 生成图表时，Mermaid 的正确率总是不够高**——复杂图经常 70-80% 的成功率，语法错了就渲染空白，错误信息又是给人看的自然语言，AI 读不懂也修不好，只能反复重试，既浪费 Token 又影响体验。

深入分析后我们意识到：这不是 LLM 不够聪明，而是**Mermaid、PlantUML 这些工具从设计之初就是给「人类手写」用的**。它们的语法变体多、隐式规则多、错误静默——这些对人类来说是「灵活」，对 AI 来说就是「幻觉空间」。

于是我们产生了一个想法：**如果有一种图表语言，从第一天起就把 AI Agent 当作第一用户，会是什么样子？**

**想解决的问题：**

1. **AI 生成图表正确率低**——现有语法变体太多，LLM 容易「猜错」写法
2. **错误不可修复**——渲染失败返回空白或文本错误，Agent 无法自我修正
3. **修改只能重来**——文本级 Diff 毫无意义，Agent 改图只能整段重生成
4. **布局语义混在一起**——Agent 既要表达关系又要操心坐标，增加出错概率

**为什么做这个方向：**

我们做了三个判断：

第一，**这是一个真问题，而且会越来越痛**。AI Agent 正在从「聊天机器人」走向「能干活的助手」，生成图表是技术文档、代码解释、架构设计中几乎必经的一步。现在大家还在「能出图就行」的阶段，但很快就会进入「要稳定出图、要可控修改」的阶段。

第二，**这是一个差异化的切入点**。Mermaid、PlantUML 生态很强，但它们的「基本盘」是人类手写用户。我们不跟它们抢这个市场，而是瞄准「AI Agent 工具链」这个新增量——做 LLM 时代的图表输出格式标准。

第三，**用 TRAE 做这个项目有天然优势**。布局算法、边路由、语法解析、渲染管线……这些都是「规则明确、逻辑复杂、代码量大」的模块——正是 AI 编程最能发挥价值的地方。人来定义架构和取舍，AI 来实现算法细节和工程落地，这种协作模式效率极高。

## 4. TRAE 实践过程

### 开发流程概述

FlowML 是一个**全程用 TRAE 开发**的复杂系统项目。整体开发遵循「架构由人定义、实现由 AI 完成、质量由算法验证」的协作模式，大致分为以下阶段：

**阶段一：产品定义与核心语法设计**
- 明确「AI Agent 原生图表语言」的定位
- 设计语法规范、AST 结构、错误模型
- 用 TRAE 完成 Parser 原型和基础验证器

**阶段二：布局算法体系搭建**
- 从最简单的 Sugiyama 分层布局开始，逐步迭代出 v2 增强版
- 同步开发正交边路由、贝塞尔路由等多种路由策略
- 针对架构图、思维导图、状态图等不同图类型，开发专用布局算法
- 每一步都用基准测试（benchmark）量化效果，用 A/B 对比验证优化

**阶段三：渲染引擎与主题系统**
- 实现 SVG / PNG / JSON / ASCII 多格式输出
- 搭建主题系统，开发 clean-light、clean-dark、blueprint、neon-glow 等多套主题
- 实现图标库（覆盖云原生、数据库、服务等 50+ 语义图标）

**阶段四：工程化与多端交付**
- 封装 CLI 工具、HTTP Server、WASM 包三种交付形态
- 搭建 Playground 在线编辑器
- 建立 959 个测试用例的质量保障体系
- 持续优化布局效果：边聚合（Edge Bundling）、网格吸附（Grid Snap）、间距微调（Nudge）等高级特性

## 开发心得 / 经验总结

### 一、关于「AI 原生」产品的思考

做 FlowML 最大的体会是：**当 AI 成为第一用户时，很多设计原则都要反过来。**

人类用户喜欢「灵活」——多种写法、隐式规则、自由发挥。AI 喜欢「确定」——语法越少越好、规则越明确越好、错误越结构化越好。

我们做了一个反直觉的决定：**主动限制表达能力**。比如箭头只留 3 种，比如不支持自定义坐标（布局交给引擎）。看起来是「退步」，但对 AI 来说，选择空间越小，正确率越高。而正确率，才是 AI 场景下的核心指标。

### 二、TRAE 开发复杂算法项目的方法论

这个项目涉及大量图论算法、几何计算、布局优化，是一个非常适合验证 AI 编程能力的场景。我们总结了几条有效经验：

1. **不要外行指导内行，先让 AI 提方案，再让 AI 评方案。** 做新算法时，先让 TRAE 搜索和分析主流解法，列出 2-3 个候选方案，分析各自优缺点，形成书面方案落盘。必要时换不同模型交叉评审，最后选一个方案让 AI 执行。

2. **用好「反问机制」和「一次速通机会」。** 需求模糊时，让 AI 主动提问来收集需求、分析需求、给出方案，比人自己想需求更全面。长任务开始前，先让 AI 做一次完整的方案推演，能少走很多弯路。

3. **算法开发一定要有量化指标和基准测试。** 布局效果好不好，不能靠「感觉」，要有 ink 用量、交叉数、边长方差这些硬指标。每次优化跑一遍 benchmark，用数据说话。

4. **功能和逻辑是一棵大树，AI 做叶子部分最擅长。** 人的位置是融合和架构——定义模块边界、制定接口契约、把握取舍方向。具体算法的实现细节、代码编写、测试用例，这些「叶子节点」的工作，AI 做得又快又好。

5. **长任务要复盘 2 次。** 大的功能模块做完后，先用快速模型做一轮检查和重构（马后炮），再用强模型做一轮深度审查。这样出来的代码质量比一遍过要高很多。

### 三、项目后续方向

FlowML 目前已经完成了核心引擎的搭建，但这只是起点。后续我们计划：

- 继续优化布局算法，向 Graphviz 的成熟度看齐
- 开发 Mermaid / PlantUML 导入工具，降低迁移成本
- 探索「自然语言 → 图表」的端到端体验
- 建立自定义图表类型的扩展生态

我们相信，AI Agent 时代需要一套全新的图表基础设施。FlowML 想做的，就是成为那个「AI 生成图表的事实标准格式」。
