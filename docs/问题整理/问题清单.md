### ISS-001  跨组边出组前提前转弯，且对称路径不对称
- 状态：待修复
- 分类：路由
- 发现时间：2026-07-22
- 问题描述：
  在 `architecture/product.microservices.pgm` 中：
  - 【Web 客户端】、【移动客户端】两个节点（位于"前端层"group 内）指向【API 网关】（位于"后端层"group 内）的两条边
  - 问题1：两条边**不对称**，视觉上不平衡
  - 问题2：边在 group 内部就开始水平转弯，而不是先竖直向下延伸到 group 边界外、再转弯汇合
  - 用户期望：理想情况可以并线汇合后指向 API 网关；即使不合并，也应该**先出 group 再转弯**，且两条路径镜像对称
- 截图：
  - 基线（当前渲染结果）：[ISS-001-004-microservices-baseline.png](./归档图片/ISS-001-004-microservices-baseline.png)
  - 用户手绘红线标注：对话中可见（红线上方部分：Web/移动客户端出边应先下出前端层group再转弯汇合）
- 分析与讨论：
  **要求合理性**：完全合理，属于架构图/正交路由的行业默认共识：
  1. 跨组边必须先沿端口方向（如 Bottom）的 stub 段延伸出**源 group 的外边界**，然后才允许转弯。提前在组内转弯会导致"边看起来还没离开分组就拐弯了"，视觉分组逻辑混乱。
  2. 几何对称的两个节点（Web/移动客户端在同一 group 内、水平并排、距离目标节点水平距离对称）发出的同向边，路径必须镜像对称——这是正交路由"确定性+美观"的基本要求。
  
  **根因初步分析**：
  - 查看 [`corridor_route.rs`](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/corridor_route.rs#L209-L240)，`outer_bypass` 逻辑中虽然有 `exit_border` 计算，但 `append_stub_leg` 的 stub 长度可能只到廊心坐标，没有强制要求 stub 必须延伸到 group 外边界
  - slot 分配阶段（[`port_slot.rs`](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/phases/port_slot.rs)）没有对"同 group、同 side、对称位置"的端点进行对称锚点配对
  - 边的路由顺序（head=[0,1,3,2,...]）可能导致先路由的边占了有利位置，后路由的边被迫绕路，破坏对称性
- 关联代码：
  - [corridor_route.rs](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/corridor_route.rs) 跨组走廊路由
  - [slot.rs](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/slot.rs) slot/锚点计算
  - [port_slot.rs](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/phases/port_slot.rs) 端口与 slot 分配
- 后续动作：
  1. 检查 stub 段长度逻辑，强制跨组边的首段 stub 必须延伸到 group 外边界
  2. 对同 group 同方向出边实现对称锚点分配
  3. 验证并线（endpoint bundling）在跨组场景是否正确触发

### ISS-002  跨组/向下边箭头方向异常（"倒下来"）
- 状态：待修复
- 分类：路由
- 发现时间：2026-07-22
- 问题描述：
  在 `architecture/product.microservices.pgm` 中：
  - 【订单服务】→【PostgreSQL】的边，箭头视觉上"倒下来"了，方向不对
  - 【订单服务】→【消息队列】"发布订单事件"的边，箭头同样存在方向问题
  - 用户期望：边应该先竖直向下延伸到 group 外面，再水平弯折到目标，箭头方向应该顺着最后一段竖直向下（或接近目标的方向），而不是出现"倒悬"感
- 截图：
  - 基线（当前渲染结果）：[ISS-001-004-microservices-baseline.png](./归档图片/ISS-001-004-microservices-baseline.png)
  - 用户手绘红线标注：对话中可见（红线下方部分：订单服务出边应先下出后端层group再弯折，箭头方向应朝下而非朝左）
- 分析与讨论：
  **要求合理性**：完全合理。箭头方向是边的"语义方向"的视觉表达：
  1. 从 Bottom 端口出来的边，首段必须竖直向下（保持端口方向的 stub）
  2. 进入目标节点前的最后一段，方向必须与目标端口方向一致（如进入 Top 端口则最后一段必须竖直向上）
  3. 箭头必须沿最后一段方向绘制，不能出现"看起来箭头是倒着指向节点"的视觉错觉
  
  **根因初步分析**：
  - 可能与 ISS-001 是同一类问题：边在 group 内就开始水平转弯，导致到达 PostgreSQL 时最后一段的方向不对
  - 或者是 `fix_reverse_stub_ports`（端口修正）逻辑没有正确处理这类场景，选了错误的目标端口（比如应该进 Top/Left 但选了其他方向）
  - 日志显示 `4b_port_correction: flipped 1 edges`，说明有1条边被翻转了端口，可能就是问题边，但翻转后结果仍不正确
- 关联代码：
  - 端口选择：[port_solver.rs](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/port_solver.rs)
  - 反向 stub 修复：（待定位，日志中 `x2_flip_stub`）
  - 走廊路由出/入组逻辑：[corridor_route.rs](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/corridor_route.rs)
- 后续动作：
  1. 复现问题边，打印实际路径点坐标，确认弯折位置和端口选择
  2. 检查首段 stub 是否被强制保持端口方向直到出组
  3. 验证最后一段 approach 段是否与目标端口方向一致

### ISS-003  非矩形特殊形状（菱形/六边形等）的边端点未接触形状轮廓
- 状态：待修复
- 分类：路由/渲染
- 发现时间：2026-07-22
- 问题描述：
  【API 网关】节点是 gateway 类型，渲染为菱形（Diamond）或六边形（Hexagon）特殊形状，但：
  - 连接到它的边（来自 Web/移动客户端，以及指向用户/订单服务的边）的端点，并没有接触到形状的实际边线
  - 边终止在形状的矩形包围盒（bbox）位置，与菱形轮廓之间有明显的空隙或穿透
  - 这是所有非矩形形状的通病（圆形、圆柱体、数据库、队列等都会有这个问题）
- 截图：
  - 基线（当前渲染结果）：[ISS-001-004-microservices-baseline.png](./归档图片/ISS-001-004-microservices-baseline.png)
  - 用户手绘红线标注：对话中可见（API网关节点为菱形，箭头停在bbox边缘，未接触菱形实际轮廓）
- 分析与讨论：
  **要求合理性**：完全合理，这是所有专业绘图工具的基本要求——边的端点必须精确落在形状的**实际可见轮廓**上，不能落在包围盒上留下空隙，也不能穿透形状内部。
  
  **根因明确**：
  - 当前所有正交路由的锚点计算都基于**矩形 bbox**：
    - [`slot.rs:slot_anchor()`](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/slot.rs#L363-L372) 直接返回 bbox 边上的点
    - [`spline_fallback.rs:port_anchor()`](../../crates/plotgram-core/src/layout/refine/spline_fallback.rs#L320-L328) 同样按矩形计算
  - organic 路由中 [`snap_to_side()`](../../crates/plotgram-core/src/layout/edge/edge_routing_organic.rs#L516-L553) 已经对圆形做了椭圆边界 snap，但正交路由完全缺失这个逻辑
  - 不同形状需要不同的边界交点计算：
    - Diamond：四条边组成的菱形，需求边与菱形边的交点
    - Hexagon：六条边组成的六边形
    - Circle：圆形/椭圆，射线与圆的交点
    - Cylinder（数据库）：顶部椭圆+竖边+底部椭圆
    - 其他形状（Person、Cloud、Parallelogram 等）各有自己的轮廓
- 关联代码：
  - 锚点计算：[slot.rs](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/slot.rs#L363-L372)
  - 形状定义：[spatial_clarity.rs](../../crates/plotgram-core/src/graphic_style/spatial_clarity.rs#L122-L179) 有所有形状的顶点生成
  - 形状点生成：[common.rs:diamond_points()](../../crates/plotgram-core/src/graphic_style/common.rs#L604-L617)
  - organic 路由参考：[edge_routing_organic.rs:snap_to_side()](../../crates/plotgram-core/src/layout/edge/edge_routing_organic.rs#L516-L553)
- 后续动作：
  1. 新增通用的 `shape_anchor_point(nl, shape, side, frac) -> Point` 函数，根据 NodeShape 计算真实轮廓上的锚点
  2. 替换所有 slot_anchor/port_anchor 调用点
  3. 路径最后一段 approach 也需要 snap 到真实形状边界，而不是 bbox
  4. 对圆柱体、数据库等"伪3D"形状，需要明确边应该接在哪个可见面上

### ISS-004  边标签应使用不透明背景色遮蔽底层边线
- 状态：待修复
- 分类：渲染
- 发现时间：2026-07-22
- 问题描述：
  边线上的标签（如"发布订单事件"、"消费事件"）当前视觉效果不够干净：
  - 标签文字直接放在边线上，边线从文字下方穿过，影响可读性
  - 用户期望：行业标准做法是——标签使用与画布背景完全相同的不透明背景，z-index 压在边线上方，在视觉上"打断"边线，让文字清晰可读；就像道路地图上的路名标签覆盖在道路上一样
- 截图：
  - 基线（当前渲染结果）：[ISS-001-004-microservices-baseline.png](./归档图片/ISS-001-004-microservices-baseline.png)
  - 用户手绘红线标注：对话中可见（"发布订单事件"、"消费事件"标签处，边线从文字下方穿过）
- 分析与讨论：
  **要求合理性**：完全合理，这是 draw.io、Mermaid、Excalidraw、Figma、Lucidchart 等所有主流图表/绘图工具的默认做法：
  - 标签渲染在最上层（z-index 最高）
  - 标签背景色 = 画布背景色（纯白色或浅灰色，取决于主题）
  - 背景不透明（opacity=1.0，不是半透明），完全遮盖下方的边线段
  - 背景有 4-8px 的 padding，比文字区域稍大
  - 可以选择性加细边框或不加
  - 这个做法比"把标签推到边线旁边"更美观、更节省空间，尤其是在线条密集时
  
  **当前现状分析**：
  - 查看 [`visual.rs:EdgeLabelStyle::default()`](../../crates/plotgram-core/src/render/visual.rs#L146-L163)，当前默认是：
    - `bg_color: Some("#ffffff")` （白色）
    - `bg_opacity: 0.85` （85%不透明——这是问题所在，半透明会让边线透出来）
    - `padding: (6.0, 3.0)` （上下6px、左右3px，可能偏小）
  - 查看 [`svg_utils.rs:render_edge_label()`](../../crates/plotgram-core/src/render/paint/svg_utils.rs#L556-L670)，渲染顺序已经是 edges→nodes→labels，标签确实在最上层，但半透明白色在浅色画布上还好，在有 group 背景色（灰色）的区域就会透出底下的线和背景
  - 问题：背景色是硬编码白色，没有取画布实际背景色；且透明度不对
- 关联代码：
  - 默认标签样式：[visual.rs](../../crates/plotgram-core/src/render/visual.rs#L146-L163)
  - 标签渲染：[svg_utils.rs:render_edge_label()](../../crates/plotgram-core/src/render/paint/svg_utils.rs#L556-L670)
  - 三层渲染顺序：[standard.rs:paint_export_edge_label()](../../crates/plotgram-core/src/render/paint/standard.rs#L54-L75)
- 后续动作：
  1. 把 `bg_opacity` 从 0.85 改为 1.0（完全不透明）
  2. `bg_color` 不硬编码白色，改为从主题/画布背景色读取
  3. 适当增大 padding（建议至少 4px 垂直、8px 水平，或统一 6px）
  4. 验证在 group 背景色区域（如后端层的灰色背景），标签背景色是否正确匹配
  5. 可选：对沿边旋转的标签，背景矩形也要跟着旋转，避免边角露出线段

### ISS-005  共线边的 label 重叠，无法区分归属
- 状态：待修复
- 分类：路由/渲染
- 发现时间：2026-07-22
- 问题描述：
  在 `flowchart/product.order-approval.pgm` 中：
  - 边 `check -> approved "否"`（金额是否超限→审批通过）和边 `finance -> rejected "驳回"`（财务复核→驳回修改）共线（共享同一段路径线段）
  - 两条边的 label（"否" 和 "驳回"）落在共线段的同一位置，从视觉上无法判断哪个 label 属于哪条边
  - 逻辑上这两条边共线是合理的（它们恰好走同一段通道），但 label 的摆放没有做差异化的偏移处理
- 截图：[w2.png](./归档图片/w2.png)
- 分析与讨论：
  **核心矛盾**：边共线/并线（edge bundling）是正交路由中常见且合理的行为（多条边共享同一段通道），但当前 label 放置逻辑没有处理共线段的 label 去冲突：
  - 多条边共享同一段路径时，label 应该在沿路径方向（或垂直方向）错开摆放，或采用"每边一个 label 偏移"策略
  - 与 ISS-004（label 背景不透明）相关但不相同——ISS-004 解决的是"边线从文字下方穿过"的问题，而本问题解决的是"两个 label 堆在一起无法区分"的问题
  - 可能的方案：
    1. **沿路径分散**：在共线段上，将不同边的 label 沿路径方向错开一定距离
    2. **垂直偏移**：在共线段上，将不同边的 label 向路径两侧偏移（一个在路径上方，一个在下方）
    3. **label 碰撞检测**：通用的 label 碰撞检测 + 排斥力，自动将重叠的 label 推开
  - 当前代码中 label 位置计算可能仅基于边的中点或固定比例，没有考虑与同一路径段上其他 label 的冲突
- 关联代码：
  - label 位置计算：待定位（可能在 `svg_utils.rs` 或 label 分配阶段）
  - edge bundling / 共线段检测：`edge_routing_orthogonal` 相关模块
- 后续动作：
  1. 定位 label 在边上的位置计算逻辑
  2. 确认是否有共线段感知的 label 去冲突机制
  3. 评估方案 1（沿路径分散）和方案 2（垂直偏移）的可行性，优先方案 1（不占用额外空间）

### ISS-006  【驳回修改】布局位置应放在【财务审核】左侧
- 状态：待修复
- 分类：布局
- 发现时间：2026-07-22
- 问题描述：
  在 `flowchart/product.order-approval.pgm` 中：
  - PGM 源中节点声明顺序为 `rejected`（驳回修改）在 `finance`（财务复核）之前，但布局结果中 `rejected` 的位置不在 `finance` 左侧
  - 用户期望：【驳回修改】应放在【财务审核】的左侧，逻辑上更顺——审批流程中"驳回"是左分支（回到流程起点），"通过"是右分支（继续往下走），左驳回、右通过符合直觉
  - 从边连接角度看：`finance -> rejected` 和 `rejected -> submit` 构成一个"左回环"（驳回后重新提交），放在左侧相比放在右侧或下方，边的正交路由更简洁、不会横跨整个图
- 截图：[w2.png](./归档图片/w2.png)
- 分析与讨论：
  **要求合理性**：合理，属于流程图分支语义的行业惯例（左否/左回、右是/右进），且能改善回环边的路由简洁度。

  **当前实际布局**（`cargo run -p plotgram-cli -- render` 实测坐标）：

  | 节点 | x | y | 说明 |
  |------|---|---|------|
  | submit / review / check / finance / approved / rejected | 228 | 49→607 | 几乎全部叠在同一竖列 |
  | done | 384 | 607 | 仅终点偏右，与 rejected 同层 |

  `rejected` 在 `approved` **正下方**（同 x=228），而非 `finance` 左侧；`finance` 也在 x=228 中轴上。用户期望的「左驳回」结构未出现。

  **根因分析**（比「声明顺序」更深）：
  1. **Sugiyama 只做 rank + 层内 order**，不读边标签语义（"驳回"/"通过"）；`decl_order` 仅是同层排序的软偏置，会被交叉最小化覆盖。
  2. **回环边 `rejected -> submit`** 经 `greedy_cycle_reversal` 反转破环后，`rejected` 的 rank 被推到图的下部（近 sink），与 `done` 落在同一底层，而非 finance 的左邻。
  3. **`apply_sink_rank_constraints`** 把 `type=end` 的 `done` 强制压到 `max_rank`，进一步把底层挤成「rejected + done」横排，与 finance 层无关。
  4. **层内排序**走 weighted-median + barycenter（[`order.rs`](../../crates/plotgram-core/src/layout/node/sugiyama_v2/order.rs)），天然倾向把节点收拢到中轴列，不会主动展开「左回环 / 右前进」对称结构。

  **文档原判断需修正**：「调整 PGM 声明顺序即可影响布局」——对此图**基本无效**；`rejected` 虽声明在 `finance` 前，但拓扑 rank 与 median 排序才是主因。

  **可行修复方向**：
  1. **算法层（推荐）**：FAS 反转后，对 feedback 目标节点（此处 `rejected`）施加层内「回环侧」偏置——相对其源节点 `finance` 尽量靠左（TB 布局下 x 更小）。
  2. **决策分支展开**：`check`、`finance` 等多出边节点，层内按出边稳定序展开左右（"是/通过" 右，"否/驳回" 左），类似 BPMN 习惯。
  3. **DSL 层（短期兜底）**：现有 `constrain A -> B` 只约束 **rank**（纵向），**不能**指定同层左右；若需精确控制，需新增 `order` / `align` 类 hint（当前 flowchart 未暴露）。

- 关联代码：
  - Sugiyama 主流程：[sugiyama_v2/engine.rs](../../crates/plotgram-core/src/layout/node/sugiyama_v2/engine.rs)
  - FAS 去环：[graph.rs:greedy_cycle_reversal](../../crates/plotgram-core/src/layout/node/sugiyama_v2/graph.rs)
  - 层内排序：[order.rs](../../crates/plotgram-core/src/layout/node/sugiyama_v2/order.rs)
  - 声明序软偏置：[decl_order.rs](../../crates/plotgram-core/src/layout/decl_order.rs)
  - sink/end 沉底：[engine.rs:apply_sink_rank_constraints](../../crates/plotgram-core/src/layout/node/sugiyama_v2/engine.rs)

  1. 在 sugiyama order 阶段增加 feedback 目标节点的「回环侧」偏置（相对源节点靠左）

### ISS-007  【完成】应放在【审批通过】右侧
- 状态：待修复
- 分类：布局
- 发现时间：2026-07-22
- 问题描述：
  在 `flowchart/product.order-approval.pgm` 中：
  - `done`（完成）节点是流程的终点，`approved -> done` 是最后一条边
  - 用户期望：【完成】节点放在【审批通过】的右侧，让流程图从左到右展开，视觉上更平衡、更好看
  - 这是一个纯审美偏好，不涉及逻辑正确性
- 截图：[w2.png](./归档图片/w2.png)
- 分析与讨论：
  **要求合理性**：合理，优先级低于 ISS-005/006。终点右置是常见流程图审美，与 ISS-006「左驳回」形成对称。

  **当前实际布局**：
  - `approved`：(228, 495) — 中轴列
  - `done`：(384, 607) — **在 approved 的右下方**，而非右侧邻接

  当前 `done` 确实偏右（x 大 156px），但被 **`apply_sink_rank_constraints` 压到最底层**（y=607），与 `approved` 相差一整层（≈112px）。用户要的是「approved 右侧、大致同高」，不是「右下角」。

  **根因分析**：
  1. `type=end` 节点被强制 `rank = max_rank`（[`apply_sink_rank_constraints`](../../crates/plotgram-core/src/layout/node/sugiyama_v2/engine.rs)），`approved -> done` 的业务边要求 `rank(approved) < rank(done)`，在 TB Sugiyama 下 **done 必须在 approved 下方**——与「水平右置」存在结构性冲突。
  2. 底层仅 `rejected` + `done` 两个节点，median 排序把 `done` 放到右侧空位，这是「沉底 + 层内右偏」的副产品，并非「终点跟随 approved」的语义。
  3. **与 ISS-006 联动有限**：修 ISS-006 只会让 `rejected` 左移，不会自动让 `done` 升到 `approved` 同层右侧。

  **可行修复方向**：
  1. **终点同层右置模式**：对 `approved -> done`（process/end 直连）允许「伪同层」——`done` 与 `approved` 共享 rank 但在坐标阶段水平右偏移（类似 BPMN 终点图标贴邻最后一环）。
  2. **放宽 end 沉底**：仅对无前置 process 的孤立 end 沉底；有唯一前驱 process 时跟在前驱同层右侧。
  3. **PGM 层 workaround（有限）**：`constrain` 无法让 done 与 approved 同层（会违反 `approved -> done` 的 rank 单调性）。

- 关联代码：
  - 同 ISS-006，另见 sink 约束：[engine.rs:apply_sink_rank_constraints](../../crates/plotgram-core/src/layout/node/sugiyama_v2/engine.rs)
  - 坐标映射：[coordinate.rs](../../crates/plotgram-core/src/layout/node/sugiyama_v2/coordinate.rs)
- 后续动作：
  1. 与 ISS-006 一并设计「分支展开 + 终点邻接」坐标策略
  2. 明确 end 节点沉底规则的例外（唯一前驱 process 时同层右置）
  3. order-approval 回归：done 在 approved 右侧、垂直中心大致对齐

### ISS-008  回环边路径折点过多且端口选择不智能
- 状态：待修复
- 分类：路由
- 发现时间：2026-07-22
- 问题描述：
  在 `flowchart/product.refund-process.pgm` 中，边 `revise -> submit "重新提交"`（【修改申请】→【提交退款申请】）：
  - 当前路径折点过多：从【修改申请】顶部出发后先向左折，沿图左侧长竖廊上升，再折向右，最终从【提交退款申请】**底部**进入
  - 用户期望（红线示意）：从【修改申请】**径直向上**，到达合适高度后**右拐**，从【提交退款申请】**左侧**端口进入——理想路径为 1 次转弯的 L 形（┐），而非多段 Z 形绕行
  - 用户判断：目标端口（side）选择不够智能，未根据源/目标相对位置选择最自然的入边侧
- 截图：[ISS-008-refund-process-baseline.png](./归档图片/ISS-008-refund-process-baseline.png)
- 分析与讨论：
  **要求合理性**：完全合理。回环/重提边在流程图中极为常见，行业默认是「从源节点朝目标方向最短正交折线」，而非绕到图外缘长廊。与 ISS-001/002 同属「端口 + 走廊路由」语义问题，但场景是 **feedback 回环边**。

  **当前实际路径**（`cargo run -p plotgram-cli -- render` 实测）：
  - `revise`（修改申请）：bbox (128, 692)–(240, 742)，中心 x≈184
  - `submit`（提交退款申请）：bbox (240, 128)–(352, 178)，中心 x≈296
  - 边 `revise→submit`（edge[8]）路径要点：Top(revise) → 左折至 x≈199 → 长竖直上升至 y≈194 → 右折 → **Bottom(submit)** 进入
  - 路由日志：`35 candidates`（候选极多，说明搜索空间大）、`4b_port_correction: flipped 2 edges`

  **期望路径**（几何上更优）：
  - 源在目标左下方，`revise.x_max ≈ submit.x_min`（水平几乎邻接）
  - 自然端口对：**Top(revise) → Left(submit)**，路径 `(184, 692) ↑ (184, ~153) → (240, ~153)`，仅 1 个折点

  **根因初步分析**：
  1. **长跨度回环边被强制侧通道**：`revise→submit` 跨多层（rank_span ≫ 2），[`feedback_side.rs`](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/feedback_side.rs) 的 `LONG_SPAN_SIDE_THRESHOLD` 逻辑在「正对路径不干净」时将其打入 Left/Right 桶，走外廊绕行；但 revise 与 submit 在 x 轴已近乎对齐，**不需要外廊**。
  2. **侧通道端口语义不匹配**：侧通道桶分配 `same_side_ports`（Left→Left 或 Right→Right），与本案最优 **Top→Left** 正交组合不一致；后续 `port_solver` / `port_correction` 又可能翻转端口（本图 flipped 2 条），最终落到底部入边。
  3. **缺少「相对象限」端口启发**：未根据 `(dx, dy)` 符号选择最短路端口对——源在左下、目标在右上时应优先 Top+Left，而非 Bottom 或纯侧廊。
  4. **A* 候选过多不等于更优**：35 个候选说明评分未有效偏好「最少折点 + 最短曼哈顿距离」的 L 形路径。

  **与已有问题的关系**：
  - 与 ISS-002（箭头方向异常）同类：错误入边端口导致最后一段方向违反直觉
  - 与 ISS-006 同类：回环边布局语义（重提应沿最短回路）未进入路由评分

- 关联代码：
  - 回环侧通道分配：[feedback_side.rs](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/feedback_side.rs)
  - 端口求解：[port_solver.rs](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/port_solver.rs)
  - 端口修正（flipped）：[phases/port_correction.rs](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/phases/port_correction.rs)
  - 回环延后重路由：[phases/trunk.rs:phase_reroute_feedback_after_trunk](../../crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/phases/trunk.rs)
  - PGM 源：[product.refund-process.pgm](../../showcase/flowchart/product.refund-process.pgm)
- 后续动作：
  1. 打印 `revise→submit` 的 `from_port`/`to_port` 及各阶段候选折点，定位端口被改写的步骤
  2. 长跨度回环边增加「近对齐 L 形」快捷路径：x 投影重叠或间隙 < 阈值时，强制 Top→Left（或相应象限）并跳过外廊
  3. 路由评分加入折点数量惩罚，避免 Z 形绕远
  4. 以 refund-process 为 product 回归样例
