1这 9 行代码是什么

先看本体。这是整个独立边路由机制的"接口合同"。

/// 独立边路由器：节点已冻结，负责写出最终边路径。
///
/// 消费一个 [`RouteScene`]（障碍 + 端子 + 参数），为 `scene.edge_order` 中的
/// 每条边产出一个 [`EdgePlacement`]。不得修改节点、端口，也不得发明端子——只写 `path`。
pub trait EdgeRouter: Send + Sync {
    /// 注册表键（例如 `"orthogonal"`）。
    fn name(&self) -> &'static str;

    /// 路由 `scene` 中描述的全部边。
    ///
    /// 输出顺序与 `scene.edge_order` 一致。
    fn route(&self, scene: &RouteScene) -> Result<Vec<EdgePlacement>, LayoutError>;
}

它属于 tautcore-engine-api crate——契约层。 这个 crate 只有 trait 和数据结构，没有任何算法。真正的路由算法 （OVG 搜索图 + A*）住在 tautcore-router crate 里的 OrthogonalEdgeRouter，它 impl EdgeRouter。 引擎（tautcore-engine）通过注册表按名字拿到 Arc<dyn EdgeRouter> 来调用——引擎不认识具体算法，只认识这个 trait。

一句话定位 EdgeRouter 是"布局"与"路由"两个自由度之间的解耦边界： 布局把节点摆好、把端口定死，然后把这个自包含的 RouteScene 交给路由器， 路由器只管把边画出来。

2全景：它在管线中的位置

先看数据从 .taut 源文件到 SVG 的完整旅程， 再看 engine::run 内部布局与路由的交接。

为什么布局不顺手把边也画了？ 布局算法（hierarchical）内置了一个简单的正交 ink，但那是"顺手的占位"。 把路由抽成独立 trait 后：① 路由可以独立开发、独立测试（夹具化，R6）； ② 同一个布局可以搭配不同的路由器；③ 路由器看不到 Graph，天然无法越权改节点。 这正是 EdgeGeometryMode::DeferToRouter 这个开关的意义。

3RouteScene 结构解剖

route() 唯一的输入。它被刻意设计成 自包含——路由器拿到它就够了，永远不需要回头去看 Graph 或节点框。

为什么是 BTreeMap？

BTreeMap 按键有序，迭代顺序确定。若用 HashMap，边的处理顺序会随哈希漂移， 破坏确定性（R3）。配合显式的 edge_order， 路由优先级与平局取舍完全可复现。

为什么要单独的 edge_order？

BTreeMap 的键序是字典序，但路由优先级未必想按字典序。 edge_order 把"处理顺序"从存储结构中解耦出来， 由上游显式决定，输出顺序也按它对齐。

为什么自包含？

路由器看不到 Graph / NodePlacement，就不可能越权改节点。 同时场景可以整体 JSON 序列化，直接做成测试夹具（R6）—— tests/scenes/*.json 就是这么来的。

为什么 point 是投影好的？

"节点框 + 端口 → 绝对锚点"的翻译只发生在 facade 的 project_route_scene。路由器拿到的是纯几何点， 不需要知道节点框长什么样，天然 frame-agnostic。

5组边界与穿越许可（M2）

group_boundaries 和 boundary_permissions 是 RouteScene 里最绕的两个字段。其实它们合起来只建模一件事：一条边能不能穿过组的边框、从哪里穿。

先理解"两种墙"

RouteScene 里有两类"挡路"的东西，规则截然不同：

obstacles —— 挡所有边的墙

普通障碍（通常是节点框）。每条边都必须绕开，唯一例外是"自身节点豁免"。 规则一句话：挡住一切边。

group_boundaries —— 有条件的墙

组的边框。它只挡住没有持有穿越许可的边：某条边若在 boundary_permissions 里有该组的许可，这面墙对它就成了"门框"； 否则就是一堵真墙。本质是一批"挡不挡"取决于边身份的墙。

boundary_permissions 就是"通行证"

它以 edge_id 为键，为每条边列出按 source→target 顺序要穿越的组、每次的方向与位置：

// 边 e0：从 group a 内的 a1 → group b 内的 b1
boundary_permissions["e0"] = [
    BoundaryCrossing { group_id: "a", direction: Leave, gate_region: Some(gate_a) }, // 先离开 a
    BoundaryCrossing { group_id: "b", direction: Enter, gate_region: Some(gate_b) }, // 再进入 b
]
字段含义约束
group_id要穿越哪个组的边界必须存在于 group_boundaries
directionEnter / Leave —— 进入还是离开该组消除"边在组哪一侧"的歧义
gate_regionOption<Rect> —— 穿越必须发生的"门"区域M2 必填，且须贴在组边界上

为什么这样设计？

为什么"墙在哪"和"谁能过"分开？

group_boundaries 是几何（墙的位置）， boundary_permissions 是许可（谁能过）。 同一面墙被多条边的许可经 group_id 引用，几何只需描述一次； 路由器把组框当成"对该边是否豁免的障碍"，复用既有碰撞模型。

为什么 gate_region 必填？

组框不是哪里都能穿——"门"的位置由上游（布局/作者）决定。 必填 gate 防止路由器自选穿越点，画出破坏组视觉结构的线。

为什么有 Enter/Leave 和顺序？

按 source→target 列出穿越序列："先离开 a、再进入 b"。 方向消除"边当前在组哪一侧"的歧义，顺序保证穿墙次序正确。

为什么用"条件障碍"而不是新概念？

组的本质就是"对某些边是墙、对另一些边不是"。 建模成"按边身份决定豁免的障碍"，豁免集从"自身节点"扩展到"持许可的组"，概念上最小。

M2 的诚实承诺（R5） 当前路由器（M0/M1）尚未实现组路由。validate() 发现 group_boundaries 非空会直接报错，路由器返回 UnsupportedRouteScene——绝不静默忽略组、画出一条穿越组框的线。 画不出来（或不支持）就明说，而不是给个看起来对的结果。

validate() 的组规则

规则原因
group_id 不得重复一个组只能有一面"墙"
组与组不得嵌套/重叠（正面积重叠即错，边贴边可以）M2 只支持单层组
许可的 key 必须存在于 terminals不许给不存在的边发许可
crossing 的 group_id 必须存在于 group_boundaries不许引用不存在的组
gate_region 必填，且须接触组边界（不能严格在组内部）门必须开在墙上

6输出：EdgePlacement 与写权纪律

route() 返回 Vec<EdgePlacement>。 关键在于路由器能写什么、不能写什么——这是写权纪律（R1/R2）的落点。

判断句（来自写权纪律手册） 如果一个修法变成"在路由器里再加一个特判去挪端口或障碍"， 先问：这个自由度的写者应该是谁？——答案几乎总是"上游布局"， 而不是给路由器开后门。

7签名逐行拆解

把 9 行签名里的每个设计选择摊开看。

: Send + Sync

路由器以 Arc<dyn EdgeRouter> 存放在注册表里， 可能被多线程共享调用。OrthogonalEdgeRouter 是零大小无状态结构体， 天然满足。

registry: BTreeMap<&str, Arc<dyn EdgeRouter>>

fn name()

注册表键。DSL 里写 edge_routing: orthogonal， 引擎就用这个名字到 BTreeMap 里查实现。名字即契约，与算法解耦。

"orthogonal" → OrthogonalEdgeRouter

&RouteScene

不可变借用。路由器只读场景、不拥有场景，调用方（facade 或测试） 保留所有权。自包含结构让"借用"足够——不需要任何外部上下文。

scene 可 JSON 序列化 → 夹具化测试

Vec<EdgePlacement>

每条边一个 placement，顺序与 edge_order 一致。 调用方无需按 id 重新查找，顺序本身就是契约的一部分（确定性，R3）。

out[i].id == scene.edge_order[i]

Result<_, LayoutError>

诚实失败（R5）。画不出来就返回错误，绝不退化成穿障的单肘连线。 无法处理的场景特性用 UnsupportedRouteScene 明确拒绝。

Err 优于"看起来画出来了"

&self（无 &mut）

路由是纯函数：相同输入必产生位级相同的输出。 没有内部可变状态，就没有跨调用的隐式依赖，确定性可证。

double_run_is_bit_identical 测试锁定

LayoutError 的"路由相关"变体

变体何时产生语义
UnsupportedRouteScene { reason } 场景含路由器不支持的特性（如有 group、M1+ 参数被设为非默认值） 诚实拒绝，不静默忽略
UnknownRouter { name } DSL 指定的路由器名字在注册表里不存在 facade 层报错
Message(String) stub 被堵死、无碰撞自由路径等具体失败 携带 edge_id 上下文，便于定位

9设计决策问答

把"为什么这样设计"整理成 Q&A。

Q1：为什么路由是独立 trait，而不是布局的一个方法？

因为"摆节点"和"画边"是两个正交的自由度。独立 trait 让两者可以各自演进、 各自测试、自由组合。布局只需声明 DeferToRouter， 把边的几何责任完全交出去——这就是写权纪律里的"每个自由度有且只有一个写者"。

Q2：为什么路由器不直接拿 Graph / NodePlacement？

两个理由。① 防越权：拿不到就不可能改，编译器替纪律站岗。 ② 可测试：自包含场景能整体 JSON 化，测试无需构造整张图， 直接喂 tests/scenes/*.json 夹具即可（R6）。

Q3：为什么投影只发生在 project_route_scene 一个地方？

"端口 → 绝对锚点"是一个决策展开。如果每个路由器各自从节点框算锚点， 就会出现"两个路由器对同一个端口算出不同锚点"的灾难。收敛到唯一翻译点， 保证所有下游看到的几何一致——落笔相零新决策。

Q4：输出顺序为什么必须等于 edge_order？

确定性（R3）。边的处理顺序影响路由优先级和平局取舍；如果输出顺序漂移， 上层（渲染、快照测试、diff）就无法稳定对齐。把顺序写进契约， 调用方可以无脑按序消费。

Q5：画不出来时为什么宁可报错？

诚实（R5）。一条"看起来画出来了但穿过了障碍"的边，比一个明确的错误危害大得多—— 前者会污染渲染、误导用户、还可能被快照测试悄悄固化。所以 stub 被堵、 无碰撞自由路径、不支持的场景特性，一律返回 LayoutError。
