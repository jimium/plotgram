1这个 mod 是什么

一句话：plotgram 的主布局核，把任意有向图（含环、长边、自环、组） 排成"主流方向同向、层内少交叉、边走正交"的可读图。

算法骨架

Sugiyama 五段式：去环 → 分层 → properify → 定序 → 坐标。在此基础上落 yFiles 经验沉淀的四相写权纪律。

实现位置

单独 crate：plotgram-layout 下的 layout/hierarchical/。 通过 LayoutAlgorithm trait 接入 engine。

crates/plotgram-layout/src/layout/hierarchical/

注册名

"hierarchical" 是 Registry::standard() 里唯一注册的 layout 名（HierarchicalLayout::name() 自报）。"architecture" 不是 layout 别名，而是 profile 原子（diagram type）—— profile: architecture 经 Profile::for_type 展开成 layout: hierarchical。直接写 layout: architecture 会 UnknownLayout 硬失败（parse 层不归一化）。引擎按 map 查找，不按名字分支。

方向支持

核心只实现 canonical TB（自上而下）；LR/RL/BT 通过 plotgram_algo::orientation 在入/出口做坐标变换。

它不是 yFiles 的全量复刻 AGENTS.md §1 明确："轻量 DSL 画图引擎……不复刻全量复杂布局栈"。 本模块在 Network Simplex、Brandes–Köpf、Channel rip-up 等子问题上做了 有记录的简化（见 §10），目标是"够用且可读"，而不是"和 yFiles 像素一致"。

2全景：四相 + Orient 边界

整个模块按 Compose / Channel / Metric / Ink 四相切分，外加一个 Orientation 边界把"canonical TB 内核"和"四方向物理输出"隔开。

为什么要把方向"挡在门外"？ Sugiyama 的 rank / order / median / VPSC 全部以"层 + 层内序"为输入，方向只是 把 (main, cross) 映射到 (x, y) 的旋钮。若让算法内部到处出现 if lr { ... } 分支，每个子问题都要写四遍。把方向收敛到 orient.rs 一个文件，是 每个几何自由度有且只有一个写者（AGENTS.md §1）的最具体落地。

3数据结构谱系

从一个 plotgram_model::Graph 进来， 最终吐出 LayoutOutput。中间跨四相（Compose / Channel / Metric / Ink）的内部 IR，每个都有明确的"什么时候被填满、什么时候只读"。 Channel 与 Metric 之间通过 DemandBoard 单向握手——这是写权纪律（§10） 的具体落地之一。

为什么 ElemKey 同时有 Real 和 Virtual？ properify 把跨多 rank 的长边拆成一串"rank-相邻的小段"，中间插入 dummy 节点。 把 real 和 dummy 用同一个 ElemKey 枚举表达，后续 order / metric / ink 就可以不区分地处理它们——dummy 只是"宽度=0、无 group 的节点"。 这是 Sugiyama 框架的核心简化。

4执行流程总览

HierarchicalLayout::compute 是 Compose → Channel → Metric → Ink 四相流水，外加入口的参数绑定 / 方向变换和出口的 orient-out / normalize。 下面把它的关键步骤和源文件一一对应（精简了诊断、错误处理和 captures 装配）。

// crates/plotgram-layout/src/layout/hierarchical/mod.rs
fn compute(input: LayoutInput<'_>) -> Result<(LayoutOutput, Captures), LayoutError> {
    let bound      = HierarchicalParams::bind(input.options)?;            // params.rs
    let params     = &bound.params;
    let mut diags  = LayoutDiagnostics { warnings, relaxations: [], params_hash }; // bind warnings 落地
    let orientation = orient::to_algo_orientation(params.orientation);  // orient.rs

    // --- Compose ---------------------------------------------------
    let mut real_graph = compose::graph_index::build_real_graph(input.graph); // graph_index.rs
    compose::cycle::remove_cycles(&mut real_graph);                  // cycle.rs (Greedy-FAS)
    let ranks = compose::rank::assign_ranks(&real_graph)?;                // rank.rs (Network Simplex)
    let mut plan  = compose::properify::properify(&real_graph, &ranks);  // properify.rs
    let critical_edges: BTreeSet<String> = real_graph.edges.iter()
        .filter(|e| e.critical).map(|e| e.edge_id.clone()).collect();
    compose::order::order_layers(&mut plan, &critical_edges);           // order.rs (median+transpose)
    let canonical_size = real_graph.ids.iter().map(|id|           // 入口方向 → TB size
        orientation.to_tb_size(to_algo_size(node_sizes[id]))).collect();
    let PortAssignment { ports, bundles: end_bundles } =
        compose::ports::assign_ports(&real_graph, &plan, orientation,
                              &canonical_size, params.auto_edge_grouping)?;     // ports.rs (五档 + bundle)

    // --- Channel ---------------------------------------------------
    let route_plan =
        channel::route_edges_channel(&plan, &real_graph, &ports,
                                     &end_bundles, params)?;                    // channel/route_all.rs
    diags.relaxations.extend(route_plan.relaxations.iter().cloned());
    compose::verify::verify_plan(&plan, &real_graph, &ports, &route_plan)?; // compose/verify.rs

    // --- Metric (prelim → Demand → final) --------------------------
    let prelim_gaps = vec![params.layer_gap; plan.layers.len() - 1];
    let main_prelim = metric::main_axis::assign_main_axis(&plan, &size_of, &prelim_gaps);
    let cross = metric::cross_axis::assign_cross_axis(
        &plan, &real_graph, &ports, &size_of, &main_prelim, params.node_gap)?;   // cross_axis.rs (BK + 两遍 VPSC)
    let prelim_frames = (0..plan.elems.len()).map(zip(cross, main_prelim)).collect();

    let track_order = compose::track_order::assign_track_order(
        &plan, &real_graph, &ports, &prelim_frames,
        &route_plan.bundles, &route_plan);                                       // compose/track_order.rs (L3 着色)
    let mut demand = demand::DemandBoard::new();
    demand::publish_channel_layer_gap_demand(&mut demand, &track_order,
                                       params.layer_gap, params.edge_gap);      // demand.rs (Channel → LayerGap)
    demand.freeze();                                                  // 写权 H3：freeze 后禁写
    let layer_gaps = demand::resolved_layer_gaps(plan.layers.len(),
                                              params.layer_gap, &demand);
    let main = metric::main_axis::assign_main_axis(&plan, &size_of, &layer_gaps); // final main
    let canonical_frames = (0..plan.elems.len()).map(zip(cross, main)).collect();
    let track_coords = metric::track::assign_track_coords(
        &plan, &main, &cross, &size_of, &track_order, &route_plan, params.edge_gap); // track.rs
    let bus_levels = metric::bus::assign_bus_levels(
        &route_plan.bundles, &ports, &real_graph, &plan,
        &canonical_frames, params.layer_gap);                                   // bus.rs (BundlePlan 主轴)

    // --- Ink -------------------------------------------------------
    let mut canonical_edges = ink::route::route_edges(
        &real_graph, &plan, &ports, &canonical_frames, &bus_levels,
        &route_plan, &track_order, &track_coords,
        params.routing_style, params.layer_gap, params.node_gap)?;              // route.rs
    ink::verify::verify_no_illegal_overlap(&canonical_edges, &route_plan.bundles)?; // verify.rs
    ink::verify::verify_no_node_penetration(&canonical_edges, &real_frames)?;
    canonical_edges.extend(ink::selfloop::self_loop_edges(..));          // selfloop.rs

    // --- Orientation-out + normalize -------------------------------
    let nodes = real_graph.ids.iter().map(|id|
        NodePlacement { id, frame: canonical_rect_to_physical(orientation, frames[..]) });
    let edges = canonical_edges.iter().map(|ce| EdgePlacement {
        id, source, target,
        path: match ce.path { Polyline(p) ⇒ EdgePath::polyline(p.map(transform)),
                       Cubic {..} ⇒ EdgePath::cubic(.., .., [.., ..]) },
        from_port, to_port });
    let shift = normalize_to_origin(&mut nodes, &mut edges);

    Ok((LayoutOutput { nodes, edges, diagnostics: diags }, Captures { .. }))
}

5Compose 相：拓扑决定

这一相只决定"谁在第几层、层内什么顺序、从哪一侧出入"—— 完全不碰像素。所有几何自由度（坐标、间距、折点）都留给下游 Metric / Ink。

5.1 graph_index — 索引与自环提取 Compose

把 Graph 翻译成 dense-indexed 的 RealGraph。两件关键事：抽自环、记 group_path。

自环抽离

source == target 的边不进 edges 列表，只记到 self_loops: Vec<(edge_id, node_idx)>。理由：自环没有 rank 差， 参与 rank/order 没意义；Ink 阶段单独画。

group_path 记录

每个节点存 root..leaf 的 group id 路径（Vec<String>）。 这是后续 order 相"组内连续"约束的唯一输入。

声明序 = 稳定 tie-break

ids: Vec<String> 严格按 Graph::all_node_ids() 的声明序，index_of 是 BTreeMap。所有后续 sort 的最终 tie-break 都回退到这里——确定性（AGENTS.md §2）的根基。

RealEdge 双向字段 每条边同时存 original_source/target（DSL 写的方向，永不改）和 working_source/target（去环后的工作方向）。下游所有 arrow / label / port 决策都只读 original_*；working_* 只供 rank/order 用。这是 cycle 相不 "污染"语义的关键。

5.2 cycle — Greedy-FAS 去环 Compose

Sugiyama 框架要求 DAG，所以有环图必须先反转一部分边。 实现直接复用 plotgram_algo::fas::greedy_fas。

为什么用 Greedy-FAS 而不是精确 FAS？ 精确 FAS 是 NP-hard。Greedy-FAS（Eades 1993）在实践中给出非常接近最优的反转集， 且实现简单、确定。plotgram_algo::fas 已经提供，本模块直接复用。

5.3 rank — 简化 Network Simplex Compose

给每个节点一个 rank: u32（层号）， 使每条 working 边满足 rank(target) - rank(source) ≥ 1，并尽量短。 目标是最小化 总边长加权和。

为什么是"简化版"？ 生产级 NS 用 low/lim/lim1 三个数组把 cut value 计算做到 O(V+E) 增量。 本实现每次 pivot 都重新线性扫描所有边算 cut value，复杂度 O(V·(V+E))。 这是有意的取舍（见 MVP scope §2.1）：layout fixture 规模下（≤几十节点）， 简化版的代码可读性远胜增量簿记的复杂度，性能完全够用。
测试里的反例 network_simplex_balances_beyond_longest_path 构造了"3 条出边 + 1 入边" 的图，longest-path 会把 b 放在 rank 1（最早可行），但总长度目标 3*(3-b) + b = 9-2b 在 b=2 时更小——NS 必须把 b 拉到 rank 2 才算正确。 这是验证 NS 真的在优化的最小反例。

5.4 properify — dummy 链展开 Compose

Network Simplex 后会有"跨多 rank 的长边"。Sugiyama 框架要求 每条边只跨 1 个 rank，所以中间插入 dummy 节点，把它拆成 rank-相邻的小段。

Segment 的定义 Segment { edge_id, ordinal, from, to } 是"rank-相邻的一跳"。 span=1 的短边有 1 个 segment；span=N 的长边有 N 个 segment、N-1 个 dummy。 所有 segment 存储为 working 方向（rank 升序），Ink 相在画路径时会按 reversed 标志把它翻回 original 方向。

5.5 order — median + transpose + 组块 Compose

每层内重排元素，最小化相邻层之间的边交叉数。 核心：median barycenter 启发式 + adjacent transpose 局部优化 + best-snapshot。

组连续性：递归块排序

同组节点在层内必须连续。本实现没有用"边界 dummy 节点"机制 （architecture.md 设想的），而是用等价的递归块排序。

edge_weight：dummy 链权重更高 median 计算时给邻接边加权：real-real=1, real-virtual=2, virtual-virtual=8。 这样长边的 dummy 链更"努力"地对齐，避免长边在中间层被无关节点挤歪。
critical_edges 加权（edge-parameters §2.5） 作者标记 critical: true 的边，其 dummy 链段在 median/barycenter 计算时权重 翻倍（real-real / real-virtual × 2； virtual-virtual 不动——保 corridor 整形不被压制）。效果：关键路径在定序中 被更努力地拉直，减少不必要的折弯。order_layers(plan, &critical_edges) 只在 Compose 这一步消费 critical 标志；下游 Channel / Metric 也各自读一次（Channel 排序优先级、 Metric VPSC 权重 ×2）。

5.6 ports — 五档端口 + BundlePlan Compose

每条边的两端各解析成一个 ResolvedPort { side, along: AlongSpec }。 side（N/S/E/W，canonical TB 空间）由作者约束或图形态推断； along（沿 side 的位置）只是序号 / ratio / 像素点——展开成像素锚点是 Metric 的事， 这里绝不碰像素。作者约束分五档 + Candidates（ports-and-channel §2）。

写权纪律（H1：along 只能由 Metric 展开） ResolvedPort.along: AlongSpec 是序号或比例，不是像素。 Ordered { order, count } 由 Metric 的 anchor.rs::port_anchor 在 canonical_frames 建好之后展成像素锚点；Ratio(r) / LocalOffset(p) 同理。 Compose 在这里零像素决策——这是写权纪律（§10）的最具体落地之一。
auto_edge_grouping 与 routing_style 的冲突检查 params.rs::bind 会拒绝 auto_edge_grouping + routing_style=octilinear 组合（bus 几何只在 orthogonal 主路径上定义，edge-parameters §2.4）。这是硬失败， 不是 warning——已知不支持的组合不允许静默 bind。

6Channel 相：走廊搜索 + rip-up Channel

Compose 把"拓扑层 + 端口 side"决定完之后，每条非 bus 边还需要一条 离散走廊。Channel 在 Substrate 上为每条边跑一次 lex Dijkstra，把走廊占用 commit 到 Occupancy， 再用 bounded rip-up 把峰值占用压下来——最多 4 轮、每轮最多 8 条边。 产物 ChannelRoutePlan 只含 track 序列，零像素。

6.1 substrate — 离散走廊骨架 Channel

channel/substrate.rs 把 PlanGraph 的 rank/order 网格翻译成 一组 Main（沿 rank 轴，TB 下竖直）和 Cross（沿 order 轴，TB 下水平层间） 离散 track。奇偶编码： 2j = gap j，2j+1 = node body j—— track 的 ext 闭区间直接表达"我覆盖哪些 gap / body"。

root-scope vs group-cut

derive_substrate 优先用 group-cut Substrate（每条 track 带 scope: GroupId， 跨 scope 由 Gate 衔接）；DSL 没有 group 时退化为 root-scope 单层 Substrate。

GateCapacity

组穿越许可 Gate { group, side, line, crossings }。当前实现里 used_gates 反映是否走了 group-cut IR；root-scope fallback 时为 false。

BlueprintIndex

line → 有序 SegmentRef，给端口定位 host track： resolve_host_track(rank, order, side) 把 ResolvedPort.side 翻成 host TrackId（出/入端口各一个）。

host track = 边的起止

每条非 bus 边的 search 起点和终点就是它两端端口的 host track—— side 已经在 Compose 里定死，Channel 不能改。

6.2 RouteOrderWriter — 确定提交序 Channel

多边竞争同一走廊时，谁先 commit 谁就拿到直走廊。提交序必须确定， 否则同样输入两次跑出不同路径。compute_route_order 的 key：

// channel/route_all.rs
fn cmp_priority(&self, other: &Self) -> Ordering {
    other.critical    .cmp(&self.critical)     // critical ↓（关键边优先拿直走廊）
        .then_with(|| other.span     .cmp(&self.span))      // span ↓（长边优先）
        .then_with(|| other.reversed .cmp(&self.reversed))   // reversed ↓（FAS 反转过的更难让）
        .then_with(|| other.dummy_len.cmp(&self.dummy_len))  // dummy 链长的优先
        .then_with(||  self.decl_index.cmp(&other.decl_index)) // 声明序 ↑（最后 tie-break）
        .then_with(||  self.edge_id  .cmp(&other.edge_id))    // EdgeId ↑（终极 tie-break）
}
decl_index 不是"声明序就是路由序" decl_index 只是最后一道 tie-break。前面的 critical / span / reversed / dummy_len 决定绝大多数顺序——这意味着同样的拓扑两次声明会得到同样的路由序 （测试 route_order_ignores_declaration_shuffle 守住这条性质）。 这是确定性（AGENTS.md §2）在 Channel 相的具体落地。

6.3 search — lex Dijkstra + ScopeMask Channel

每条边在 ChannelGraph 上跑一次 lex Dijkstra（channel/search.rs）。 cost 是字典序元组，不是标量加权和——这样 bends 严格压倒 length，length 严格压倒 affinity， 拥塞严格压倒 span，不会出现"多绕两个折点换 1 像素长度"这种讨厌的权衡。

6.4 bounded_ripup — 拥塞缓解 Channel

初始 commit 后某些 track 的 lane demand 可能 > 1（多条边挤同一走廊）。 bounded_ripup 把峰值压低——最多 4 轮 （MAX_RIPUP_ROUNDS），每轮最多重路由 8 条边（MAX_RIPUP_EDGES）。

牺牲序

挑峰值 track 上的边，按 non-critical 优先 / span 短优先 / failure 多优先 排序后重路由。critical 边尽量不动。

接受准则

重路由后必须满足下列之一才接受： peak ↓、 (peak, sum) 字典 ↓、或 path_load ↓ 且路径变了。 否则回滚到原路径。

relaxations 上报

每次接受的重路由记一条 Relaxation { rule: "channel-rip-up" }； 4 轮后峰值仍 > 1 记一条 "channel-rip-up-budget"。 全部进 LayoutDiagnostics.relaxations。

不是"必须压到 1"

预算耗尽后仍可能 peak > 1——这时下游 TrackOrder + DemandBoard 会把该 track 的 lane 数展开成多 lane，并抬高对应 LayerGap（见 §7）。 rip-up 是"尽量优化"，不是"必须无冲突"。

写权纪律（H2：Channel 只写走廊，不写像素） ChannelRoutePlan 里只有 TrackId 序列和 lane 索引——没有任何 f64 坐标。像素 lane 由 Metric 的 track.rs::assign_track_coords 展开， Ink 只是把 track 序列机械连成折线。Channel 想"避让一条边"也不能，因为 它不知道 track 的像素位置——这正是 AGENTS.md §1 的"下游不得推翻上游，只得展开上游"。
scope verify 是硬失败 路由完成后 channel/verify::verify_route_scope 检查每条 path 是否离开了它的 ScopeMask 允许的 group 范围。任何"跨 scope 但没走 Gate"的路径直接 LayoutError—— 不是 warning，因为这意味着 Substrate 构造或 search 出了 bug。

7Metric 相：BK 理想位 + 全局 VPSC + TrackOrder + DemandBoard Metric

Channel 把走廊序定下来之后，Metric 把"序"展开成像素坐标。 它分四个子步：(1) main prelim 用基础 layer_gap 排出层栈初稿； (2) cross 用 Brandes–Köpf 理想位 + 全局 VPSC 两遍解次轴； (3) TrackOrder 用 interval-colouring 给每条边在每个 substrate track 上分 lane； (4) DemandBoard + main final + TrackCoords + BusLevels 把走廊需求 反馈到 layer_gap，最终展开 main 坐标、track lane 像素、bus 主轴坐标。

7.1 main_axis prelim — 层栈初稿 Metric

metric/main_axis.rs::assign_main_axis 用基础 layer_gap（不含走廊 demand）累加每层最大 node 高度，得到 main 轴初稿 main_prelim。这一步的目的是给 cross_axis 的 VPSC 提供 port anchor 展开所需的 main 坐标——不是最终 main 坐标。最终 main 在 DemandBoard freeze 之后重算（见 §7.4）。

7.2 cross_axis — Brandes–Köpf 理想位 + 两遍全局 VPSC Metric

metric/cross_axis.rs::assign_cross_axis 是本相最复杂的子步。 它把每条 real/dummy 元素放到一个 cross 轴坐标，使同层不重叠、长边直、 fan 居中、端口锚点对齐。两遍 VPSC，全局（跨层）解。

primary block（硬共线）

同类型邻居对（virtual-virtual / 1:1 real-real）走 equality 约束—— 长边 dummy 链保持直走廊、脊链不zigzag。fan-out ≥2 的 real 邻居不硬约束， 留给 pass 2 居中。

soft desired + weight

其余元素的 desired = BK ideal；权重 real=1.0、virtual=4.0， critical 边的 dummy 权重再翻倍——走廊更用力拉向 port anchor。

fan center

odd fan → 单中位数邻居位置；even fan → 中间两邻居中点。 BK left-bias 把 fan-out hub 焊到最左子，所以 odd fan 也得显式定中心。

无 packed fallback

VPSC 失败 = bug，不是 layout contingency（architecture.md §3.4）。 primary block 是 BK 同一 alignment 的子集，块不会交叉——可行性由构造保证。

7.3 TrackOrder — lane 上色 Metric

compose/track_order.rs::assign_track_order 把每条边在每个 substrate track 上的占用区间当 interval-colouring 问题： 重叠区间分到不同 lane。产物 TrackOrderPlan 只含 (edge_id, track_id) → lane_index 和 track_id → lane_count， 零像素。end-bus 成员跳过（bus 自带共线豁免，ink-verify §5）。

Cross track：按 rank 占用

Main 走廊按 [min_rank, max_rank+1) 半开区间上色—— 同一段 track 上 rank 不重叠的边可共享 lane。

Main track：按 cross 像素 span

水平走廊按 cross 轴像素 span 上色：port anchor 算出每条边在该 Main track 上的 X 占用区间，重叠者分 lane。这一步读了 cross_axis 的产物， 所以 TrackOrder 必须在 cross_axis 之后。

rank_gap_track_counts → Demand

每条 Cross line r+1 上的最大 lane 数被记到 rank_gap_track_counts[r]——这是 Channel → Metric 的 demand 信号， 直接喂给 DemandBoard 抬高对应 layer_gap。

7.4 DemandBoard — Channel → Metric 单向握手 Metric

demand.rs::DemandBoard 是 Channel 和 Metric 之间的唯一合法握手。 Channel 通过 publish_channel_layer_gap_demand 把 Cross line 的 lane 数 转成 LayerGap 下界（公式 layer_gap + (count-1) × edge_gap），max-merge 进 board； freeze 之后 Metric 才能 resolved_layer_gaps 读取。freeze 后再 publish 直接 panic。

// demand.rs（精简）
pub fn publish_channel_layer_gap_demand(
    board: &mut DemandBoard,
    track_order: &TrackOrderPlan,
    base_layer_gap: f64,
    edge_gap: f64,
) {
    for (&corridor, &count) in &track_order.rank_gap_track_counts {
        if count == 0 { continue; }
        let demand = base_layer_gap + (count.saturating_sub(1) as f64) * edge_gap;
        board.publish(DemandKey::LayerGap(corridor), demand);  // max-merge
    }
}

pub fn resolved_layer_gaps(n_layers: usize, base: f64, board: &DemandBoard) -> Vec<f64> {
    assert!(board.is_frozen(), "requires freeze");
    let mut gaps = vec![base; n_layers - 1];
    for r in 0..n_layers-1 {
        if let Some(d) = board.get(DemandKey::LayerGap(r as u32)) {
            gaps[r] = gaps[r].max(d);
        }
    }
    gaps
}
写权纪律（H3：DemandBoard 是单向、一次性握手） Channel 只能 publish，Metric 只能 read after freeze。 没有 Metric → Channel 的回调，没有 freeze 后的 publish。 这条纪律的硬约束是 assert!——违反就 panic，不是 warning。 Channel 想"再调一次 layer_gap"也不行，只能等下一轮 layout。

7.5 main final + TrackCoords + BusLevels — 像素展开 Metric

DemandBoard freeze 之后，Metric 把走廊需求展开成像素：

子步函数产物展开什么

TrackCoordsmetric/track.rs::assign_track_coordsTrackCoords每个 substrate track 的 lane 像素坐标（Cross=Y 中心、Main=X 主轴）
BusLevelsmetric/bus.rs::assign_bus_levelsBusLevels每个 end-bus 成员的共享 trunk 主轴 Y（trunk_length = clamp(layer_gap×0.35, 12, 32)）
TrackCoords 的 Main lane 避障 Main track 的 X 主轴若落在某 real node 的 X 投影内，clear_main_x 会把它 推到节点外侧——否则一条全高 Main rail 会贯穿中间节点（InkVerifier §7.3 会硬失败）。 重叠 X 投影先合并，避免在两节点面之间反复震荡。
写权纪律（H4：Metric 是像素的唯一写者） 整个 layout 里，只有 Metric 写 f64 坐标。Compose 写拓扑序、Channel 写 track 序、 Ink 写路径展开——都不发明像素。这意味着任何"看起来需要避让"的几何调整都必须在 Metric （或上游 Channel 的 track 序）里做完，Ink 没有避让能力。

8Ink 相：Channel 展开 + cubic + bus + verify Ink

Ink 把 Channel 的 ChannelPath 序列 + Metric 的 TrackCoords / BusLevels / port_anchor 机械展开成像素折线或三次贝塞尔。零新决策：不发明端口、不发明折点、不发明 track Y。 三种 routing_style 走同一入口 ink/route.rs::route_edges， 最后由 ink/verify.rs 硬校验。

8.1 orthogonal — ChannelPath → TrackOrder 折线 Ink

主路径。每条非 bus 边的 ChannelPath { tracks: Vec<TrackId> } 被 expand_channel_path 逐 track 展开：

track 朝向lane coord 来源展开动作
Cross（水平层间）track_coords.lane(tid, idx).y插入 (start.x, lane_y) → (end.x, lane_y) 双折
Main（竖直 rank 轴）track_coords.lane(tid, idx).xleave_to_main + arrive_from_main，含 cross-axis stub 检查
写权纪律（H5：Ink 零猜测） port anchor 只来自 metric::anchor::port_anchor——Ink 无 default-side fallback， 也不重新推导 anchor。需要 jog 但 TrackOrder 没分到 track → InternalInvariant 硬失败（说明 Channel / TrackOrder 出 bug）。

8.2 bus — SharedPort → Trunk → Bus → Stub Ink

end-bus BundlePlan 成员不跑 ChannelPath，直接走 yFiles AutomaticEdgeGrouping 风格的 四段式：SharedPort（簇共享锚点，无成员间距）→ Trunk（共享短桩， 长度由 trunk_length 决定）→ Bus（共享 trunk 主轴 Y， 由 BusLevels 给出）→ Stub（成员各自连到自己的目标端口）。 bus 共线由 BundlePlan 显式豁免，InkVerifier §5 不报。

8.3 cubic — 三次贝塞尔 Ink

RoutingStyle::Curved 时，每条边只生成一条三次贝塞尔曲线 （InkPath::Cubic { start, end, controls }）。控制点由两端 port 的 side 法向偏移得出。 只支持 main-axis（North/South）端口对——cross-axis 端口（East/West）的曲线展开 等 Channel D₁ 路线图（G3）。curved 不进 InkVerifier 的折线校验。

8.4 polyline — 直连 waypoint Ink

RoutingStyle::Polyline 时，waypoint 之间用直线段直接相连， 不走 orthogonal 的 track jog 也不走 cubic。无 normalize_orthogonal 清理。 主要用于"看着像手画"的展示场景。

8.5 selfloop — East 侧小回路桩 Ink

自环在 graph_index 阶段就被抽离，不参与 rank/order/coord。 Ink 阶段单独画：节点 East 侧伸出一个固定尺寸的小矩形回路，多个自环按 OUT_STEP=10 像素错开。无严格防碰撞证明（已知局限，见 §11）。

8.6 verify — 硬校验 Ink

ink/verify.rs 在折线生成完后跑两个硬校验， 任一失败 → LayoutError，不是 warning：

verify_no_illegal_overlap

两条非 bundle 边的折线完全相同 → 硬失败。 bundle 共谋成员（edges_share_bundle）是唯一豁免。 防 Channel rip-up 没压下去时两条边走完全同一条走廊却没分 lane。

verify_no_node_penetration

折线段进入非端点 real node 的开内部 → 硬失败。 仅检查正交段（非正交段跳过）；obstacle 用 OBSTACLE_INSET=1e-3 避免端口贴边 grazing 误报。这条校验守住 TrackCoords 的 clear_main_x 没漏掉节点。

Ink 的写权纪律 Ink 不发明端口、不发明折点、不发明 track 像素。它只展开 Channel 的 track 序 + Metric 的 lane 像素 + port anchor。如果发现 Ink 想"再加一个特判"（比如避让某条边）， 正确问题是：这个自由度的写者应该是谁？——答案永远是上游 Channel 或 Metric， 而 Ink 只能展开。这是 AGENTS.md §1 在本相的最具体落地。

9Orientation 转换 Orient

核心（Compose / Channel / Metric / Ink）只在 canonical TB 空间工作—— main=y↓、cross=x→、rank 0 在最顶。物理方向（LR/RL/BT）通过 plotgram_algo::orientation 在入口/出口做一次性变换， 内核代码完全感知不到方向。orient.rs 是 model 几何类型和 algo orientation 类型之间的薄桥。

为什么 rect 要用 4 角 bbox？ canonical_rect_to_physical 不直接变换 (x, y, w, h)，而是取 4 个角分别变换、 再取外接 bbox。原因：Bt/Rl 变换会翻转坐标轴符号，"左上角"经过变换后不一定是 min 角。 直接搬 (x, y) 会导致 rect 跑到负坐标或方向错乱。4 角 bbox 是唯一安全做法。
orient.rs 是薄桥 to_algo_orientation / to_algo_size / to_algo_point / to_algo_side 把 model 的 Orientation / Size / Point / Side 翻成 algo 的同名类型， from_algo_point / from_algo_side 反向。内核代码不直接 import algo， 只通过 orient.rs 调用——这样 model 类型可以独立演进，algo 变化也不会污染内核。
