## 0. 一句话方案

> **在 Recipe-Kernel 架构的语义边界开窄接口，不做万能 hook DSL；编译期 Rust trait 注册为一期目标，WASM 沙箱插件为远期方向；插件默认权力受限，不能绕过 hard constraint 或越过 Materializer 直接写几何。**

---

## 1. 设计原则

### 1.1 新架构天然适合插件，但必须在正确的边界开放

旧架构接口 `route(&Diagram, LayoutResult) → LayoutResult` 让插件拿到整个可变产品，可以随便修改 nodes/groups/edges，隔离性差、容易破坏不变量。新架构的分层（PreparedInput → Contract → Problem → Solution → MaterializedGeometry → FrozenGeometry → LabeledProduct）天然提供了**清晰的窄接口**，每层可以独立扩展，插件不能越权。

### 1.2 核心原则：安全默认，窄接口，能力可复用

1. **插件默认权力受限**：不开放任意修改的 hook，只在明确的语义边界开扩展点
2. **窄 IR 通信**：插件消费/产出结构化 IR，不接触整个可变 `LayoutResult`
3. **复用内置能力**：插件可以调用所有内置 Kernel 和 Solver，不需要从头写
4. **hard constraint 不可绕过**：GeometryMaterializer 唯一写权、typestate 冻结、auditor 硬检查对插件同样生效
5. **确定性兼容**：所有插件配置必须进入 `RoutingPlan` 的 typed config，禁止环境变量控制插件行为
6. **不做万能 hook DSL**：禁止 `before("port_assignment")` / `after("lane_assignment")` 这种任意插桩模式
7. **Kernel 不读 DiagramType**：插件如果需要图类型信息，必须通过 SemanticExtension 编译成 Contract，不能让 Kernel/Solver 读取图类型分支

## 2. 五类插件扩展点

### 2.1 自定义 RoutingRecipe（最常用、最推荐）

一个 Recipe 就是一个完整的路由家族，定义"如何编译语义、如何求解、如何物化几何"。第三方可以通过实现 `RoutingRecipe` trait 添加新的路由风格。

**Trait 设计：**

```rust
pub trait RoutingRecipe: Send + Sync {
    type Draft;

    fn name(&self) -> &'static str;

    fn capabilities(&self) -> RecipeCapabilities;

    fn compile(
        &self,
        input: &PreparedRoutingInput,
        kernels: &RoutingKernels,
    ) -> Result<Self::Draft, RoutingError>;

    fn solve(
        &self,
        draft: &mut Self::Draft,
        kernels: &RoutingKernels,
    ) -> Result<RouteSolution, RoutingError>;

    fn materialize(
        &self,
        solution: &RouteSolution,
        kernels: &RoutingKernels,
    ) -> Result<MaterializedRouteGeometry, RoutingError>;
}

pub struct RecipeCapabilities {
    pub supported_geometry_families: &'static [GeometryFamily],
    pub supports_self_loop: bool,
    pub supports_parallel_group: bool,
    pub supports_bundle: bool,
    pub supports_curve: bool,
    pub produces_annotation: bool,
}
```

**可以做什么：**
- 添加新的几何家族，如 MetroMap（地铁路线图45度对角）、CableHarness（工程线束）、Sankey（桑基流图）、HandDrawn（手绘扰动曲线）、PcbRoute（PCB布线）
- 完全自定义 solve 顺序（比如某类图不需要 LaneSolver）
- 自定义 materialize 产出特殊路径形状

**不可以做什么：**
- 不能绕过 GeometryMaterializer 直接写最终 points（必须通过自己的 materialize 产出 MaterializedRouteGeometry）
- 不能修改 FrozenNodeProduct 中的节点坐标
- 不能在 materialize 之后继续改几何

**示例用法：**

```rust
// 第三方 crate: plotgram-metro
pub struct MetroMapRecipe;

impl RoutingRecipe for MetroMapRecipe {
    type Draft = MetroDraft;

    fn name(&self) -> &'static str { "metro" }

    fn capabilities(&self) -> RecipeCapabilities {
        RecipeCapabilities {
            supported_geometry_families: &[GeometryFamily::Diagonal45],
            supports_self_loop: false,
            supports_parallel_group: true,
            supports_bundle: true,
            supports_curve: false,
            produces_annotation: true,
        }
    }

    fn compile(&self, input: &PreparedRoutingInput, kernels: &RoutingKernels) -> Result<MetroDraft> {
        // 复用 EndpointKernel 处理端点
        let endpoints = kernels.endpoint.prepare(input);
        // 复用 ObstacleKernel 构建障碍
        let obstacles = kernels.obstacle.build(input, &endpoints);
        // 自己编译地铁线路的交换站、线路颜色等
        MetroDraft::compile(input, endpoints, obstacles)
    }

    fn solve(&self, draft: &mut MetroDraft, kernels: &RoutingKernels) -> Result<RouteSolution> {
        // 复用 LaneSolver 分配轨道
        let lanes = kernels.lane.solve(&draft.track_intervals, LaneConfig { symmetric: true })?;
        // 自己写45度路径搜索
        draft.solve_diagonal_paths(lanes)
    }

    fn materialize(&self, solution: &RouteSolution, kernels: &RoutingKernels) -> Result<MaterializedRouteGeometry> {
        kernels.geometry.materialize_diagonal(solution, 45.0)
    }
}
```

### 2.2 自定义 SemanticExtension（语义扩展）

新的图类型或领域语义通过 SemanticExtension 在 compile 阶段添加 EdgeRole、PortIntent、MergeIntent 等语义事实，Kernel 和 Recipe 消费这些事实来决定路由行为。

**Trait 设计：**

```rust
pub trait SemanticExtension: Send + Sync {
    fn name(&self) -> &'static str;

    fn compile_edge_roles(
        &self,
        input: &PreparedRoutingInput,
    ) -> Result<Vec<Option<EdgeRole>>, RoutingError>;

    fn compile_port_intents(
        &self,
        input: &PreparedRoutingInput,
    ) -> Result<Vec<Option<PortIntent>>, RoutingError>;

    fn compile_merge_intents(
        &self,
        input: &PreparedRoutingInput,
    ) -> Result<Vec<Option<MergeIntent>>, RoutingError>;

    fn compile_transit_intents(
        &self,
        input: &PreparedRoutingInput,
    ) -> Result<Vec<Option<TransitIntent>>, RoutingError>;

    fn label_policy(&self) -> Option<LabelPolicy>;
}
```

**可以做什么：**
- 添加领域特定的 EdgeRole，如 UML 的 `Generalization`/`Implementation`、网络的 `Trunk`/`Uplink`、甘特的 `DependencyFs`/`DependencyFf`
- 添加端口约束（如 UML 继承箭头必须指向父类的 Top/Bottom 侧）
- 添加合流语义（如数据库 ER 图的多对多菱形连接）
- 添加标签策略（如电路图标签必须在水平段上方）

**不可以做什么：**
- 不能直接改路径或坐标
- 不能读 DiagramType 来判断自己要不要生效（应该在 input.contract 中已包含 diagram_type 信息，通过编译条件判断）
- 不能产生和内置语义冲突的 intent（冲突时由 Coordinator 按优先级裁决）

**示例用法：**

```rust
// UML 语义扩展
pub struct UmlSemantics;

impl SemanticExtension for UmlSemantics {
    fn name(&self) -> &'static str { "uml" }

    fn compile_edge_roles(&self, input: &PreparedRoutingInput) -> Result<Vec<Option<EdgeRole>>> {
        let mut roles = vec![None; input.edges.len()];
        for (i, edge) in input.edges.iter().enumerate() {
            match edge.attr("arrow_style") {
                Some("generalization") => roles[i] = Some(EdgeRole::UmlGeneralization),
                Some("implementation") => roles[i] = Some(EdgeRole::UmlImplementation),
                Some("association_class") => roles[i] = Some(EdgeRole::UmlAssociationClass),
                _ => {}
            }
        }
        Ok(roles)
    }

    fn compile_port_intents(&self, input: &PreparedRoutingInput) -> Result<Vec<Option<PortIntent>>> {
        // UML 继承：父类侧强制 Top/Bottom 端口
        // ...
    }

    // ...
}
```

### 2.3 自定义 Solver（替换求解阶段）

内置的 6 个 Solver（Port/Path/Repair/Lane/Bundle/Curve）都有明确的窄接口，插件可以替换某个 Solver 的实现。

**Trait 设计（以 PathSolver 为例）：**

```rust
pub trait PathSolver: Send + Sync {
    fn name(&self) -> &'static str;

    fn solve_initial(
        &self,
        problem: &RoutingProblem,
    ) -> Result<Vec<RoutePath>, RoutingError>;

    fn solve_repair(
        &self,
        problem: &RoutingProblem,
        previous: &RouteSolution,
        intent: &RouteRepairIntent,
    ) -> Result<RouteSolution, RoutingError>;
}

pub trait LaneSolver: Send + Sync {
    fn name(&self) -> &'static str;
    fn solve(
        &self,
        intervals: &[LaneInterval],
        config: &LaneConfig,
    ) -> Result<Vec<LaneAssignment>, RoutingError>;
}

// PortSolver / BundleSolver / CurveSolver / RepairSolver 同理
```

**可以做什么：**
- 替换 PathSolver 为 ILP 精确求解器（小图全局最优）
- 替换 LaneSolver 为并行版本或 GPU 加速版本
- 添加新的 RepairSolver 策略（如模拟退火、禁忌搜索）
- 为特定领域优化 ShortestPathKernel 的启发函数

**不可以做什么：**
- 不能绕过 hard constraint（H0-H5 必须满足）
- 不能直接改 MaterializedGeometry（必须输出 RouteSolution 子集，由 Materializer 统一物化）
- 不能修改 Contract 中已有的 hard 约束
- 不能使用随机数或 wall-clock 时间作为停机条件

### 2.4 自定义 LabelPlacementStrategy（标签策略）

标签放置是天然的插件口，不同领域有截然不同的标签规则。

**Trait 设计：**

```rust
pub trait LabelPlacementStrategy: Send + Sync {
    fn name(&self) -> &'static str;

    fn generate_candidates(
        &self,
        edge: &EdgeDemand,
        path: &RoutePath,
        geometry: &FrozenRouteGeometry,
    ) -> Vec<LabelCandidate>;

    fn hard_constraints(&self) -> Vec<LabelHardConstraint>;

    fn objective(&self) -> LabelObjective;

    fn merge_policy(&self) -> LabelMergePolicy;
}

pub struct LabelCandidate {
    pub t: f64,                     // 路径参数
    pub anchor: LabelAnchor,        // 段/径向锚点
    pub offset: (f64, f64),         // 切向/法向偏移
    pub side: LabelSide,            // 左侧/右侧
    pub bbox: Rect,
    pub owner: Option<MergeGroupId>,
    pub cost: f64,
}
```

**可以做什么：**
- 电路图：标签必须放在水平段上方，不允许在垂直段
- UML 类图：关联端名称靠近对应端点，多重度标签固定位置
- 思维导图：标签只在外侧，不翻转到边内侧
- 架构图：monitor 边标签小字号，business 边标签正常

**不可以做什么：**
- 不能改 route geometry（geometry 已冻结）
- 不能盖 node 或 arrowhead（hard constraint 由 auditor 检查）

### 2.5 自定义 AuditRule（审计规则）

在通用 hard audit 之外，添加领域特定的审计规则。

**Trait 设计：**

```rust
pub trait AuditRule: Send + Sync {
    fn name(&self) -> &'static str;
    fn severity(&self) -> AuditSeverity;

    fn audit(
        &self,
        geometry: &FrozenRouteGeometry,
        contract: &RoutingContract,
    ) -> Vec<AuditFinding>;
}

pub struct AuditFinding {
    pub rule: &'static str,
    pub severity: AuditSeverity,
    pub edges: Vec<EdgeId>,
    pub message: String,
    pub suggestion: Option<String>,
}

pub enum AuditSeverity {
    Error,   // hard violation，阻止结果产出
    Warning, // 质量问题，报告但允许产出
    Info,    // 建议
}
```

**可以做什么：**
- 架构图规则："monitor 边必须从组件的 Top/Bottom 侧出"
- PCB 规则："差分对两条边长度差 < 2mm"
- UML 规则："generalization 箭头必须指向父类"
- 视觉规则："同一节点出发的边不允许全部集中在一侧"

**不可以做什么：**
- 不能修改几何，只能产出 finding
- Error 级别的 finding 会阻止产出，Warning 级别只记录

## 3. 插件注册与发现

### 3.1 编译期注册（一期目标，优先）

利用 Rust 类型系统，通过 `RoutingRegistry` 编译期注册：

```rust
pub struct RoutingRegistry {
    recipes: HashMap<&'static str, Box<dyn RoutingRecipe>>,
    semantic_extensions: Vec<Box<dyn SemanticExtension>>,
    path_solvers: HashMap<&'static str, Box<dyn PathSolver>>,
    lane_solvers: HashMap<&'static str, Box<dyn LaneSolver>>,
    label_strategies: HashMap<&'static str, Box<dyn LabelPlacementStrategy>>,
    audit_rules: Vec<Box<dyn AuditRule>>,
}

impl RoutingRegistry {
    pub fn builtin() -> Self {
        let mut reg = Self::empty();

        // 内置 Recipes
        reg.register_recipe(StraightRecipe);
        reg.register_recipe(BezierRecipe);
        reg.register_recipe(SplineRecipe);
        reg.register_recipe(CircularRecipe);
        reg.register_recipe(OrganicRecipe);
        reg.register_recipe(OrthogonalRecipe);

        // 内置语义扩展
        reg.register_semantic_extension(FlowchartSemantics);
        reg.register_semantic_extension(ArchitectureSemantics);
        reg.register_semantic_extension(StateSemantics);
        reg.register_semantic_extension(ErSemantics);
        reg.register_semantic_extension(MindmapSemantics);

        // 内置 Solvers
        reg.register_path_solver("default", LexicographicDijkstraSolver);
        reg.register_lane_solver("default", GreedyColoringLaneSolver);

        // 内置标签策略
        reg.register_label_strategy("default", DefaultLabelStrategy);

        // 内置审计规则
        reg.register_audit_rule(ContinuityAudit);
        reg.register_audit_rule(EndpointBoundaryAudit);
        reg.register_audit_rule(NodeInteriorAudit);
        reg.register_audit_rule(GroupInteriorAudit);
        reg.register_audit_rule(OrthogonalityAudit);

        reg
    }

    pub fn register_recipe<R: RoutingRecipe + 'static>(&mut self, recipe: R) {
        let name = recipe.name();
        assert!(!self.recipes.contains_key(name), "duplicate recipe: {name}");
        self.recipes.insert(name, Box::new(recipe));
    }

    pub fn register_semantic_extension<E: SemanticExtension + 'static>(&mut self, ext: E) {
        self.semantic_extensions.push(Box::new(ext));
    }

    // register_path_solver / register_lane_solver / ... 同理
}
```

**第三方接入方式：**

```rust
// 用户代码
use plotgram::prelude::*;
use plotgram_metro::MetroMapRecipe;
use plotgram_uml::UmlSemantics;

fn main() {
    let mut registry = RoutingRegistry::builtin();
    registry.register_recipe(MetroMapRecipe);
    registry.register_semantic_extension(UmlSemantics);

    let engine = PlotgramEngine::new(registry);
    let result = engine.render(dsl_code, RenderOptions {
        routing_family: "metro",
        enable_semantics: &["uml"],
        ..Default::default()
    })?;
}
```

**优势：**
- 类型安全，编译期错误检查
- 零运行时开销
- 插件可以无缝调用所有内置 Kernel/Solver
- 确定性保证

### 3.2 能力声明与检查

每个插件必须声明自己的能力，Coordinator 在运行前检查兼容性：

```rust
pub struct PluginCapabilities {
    pub name: &'static str,
    pub version: &'static str,
    pub provides_recipes: &'static [&'static str],
    pub provides_semantics: bool,
    pub provides_solvers: &'static [&'static str],
    pub provides_labels: bool,
    pub provides_audit: bool,
    pub requires_features: &'static [&'static str], // 依赖的内置能力
    pub conflicts: &'static [&'static str],         // 冲突的其他插件
}

pub enum PluginCompatibility {
    Compatible,
    MissingFeature { feature: String },
    Conflict { other: String },
}
```

在 compile 前做 `check_feature_support()`，如果用户使用了 Recipe 不支持的硬约束（如 Metro 45度路由不支持self-loop），给出明确错误：

```
Error: Recipe "metro" does not support self-loop edges
  Edge: "node_a" → "node_a" (line 15)
  Suggestion: Remove the self-loop, or use routing_family: "orthogonal"
```

### 3.3 动态加载（远期目标，WASM 沙箱）

编译期插件稳定后，可以考虑增加 WASM 插件运行时，支持非 Rust 语言编写的插件：

```rust
// 远期：WASM 插件宿主
pub struct WasmPlugin {
    module: wasmtime::Module,
    name: String,
    capabilities: PluginCapabilities,
}

impl WasmPlugin {
    pub fn load(bytes: &[u8]) -> Result<Self, PluginError> {
        // 用 wasmtime 加载，验证导出符号
        // 沙箱：无文件系统、无网络、固定内存上限 (128MB)、
        //       固定执行轮次 (不能无限循环)
    }
}

// 插件 ABI（宿主提供给插件的函数）
// - kernel.endpoint.prepare()
// - kernel.obstacle.build()
// - kernel.shortest_path.find()
// - kernel.lane.solve()
// - kernel.audit.check()
```

**选择 WASM 而不是 native dylib 的原因：**
1. 跨平台一致（不需要为 macOS/Linux/Windows 各编一份）
2. 沙箱安全（插件不能访问文件系统/网络，不能崩溃主进程）
3. 和 Plotgram 的 WASM playground 目标一致
4. 支持多种语言（Rust/C/C++/Zig/Go 都能编译到 WASM）
5. 版本隔离：不同插件用不同 WASM 实例，不会符号冲突

**WASM 插件约束（比编译期插件更严）：**
- 固定内存上限（默认 128MB）
- 固定执行时间上限（默认 500ms，超时终止）
- 只能通过宿主 ABI 调用 Kernel，不能直接访问内存
- 不能修改宿主提供的只读 IR（必须通过返回值传递结果）
- 禁止随机数（必须使用宿主提供的确定性 RNG）

**不要在架构初期做动态插件**：先把编译期接口设计稳定，验证边界正确，动态插件是 v2 之后的事。

## 4. 禁止开放的边界

以下是插件系统的红线，任何插件都不能突破：

### 4.1 绝对禁止

1. **禁止绕过 GeometryMaterializer 直接改 points**
   - 自定义几何必须在自己的 `Recipe.materialize()` 中产出 `MaterializedRouteGeometry`
   - 不能在 materialize 之后追加修改

2. **禁止修改 FrozenNodeProduct 中的节点坐标**
   - Router 只消费冻结节点，类型上无 mutable API
   - 需要更多空间时只能产出 `UnresolvedRoutingDemand`，不能自己推节点

3. **禁止在 geometry freeze 后改路径几何**
   - freeze 后只有 LabelSolver 可以运行（产出 label，不改路径）
   - 任何路径修改必须回到 RepairSolver，在完整 contract 下重新求解

4. **禁止 Kernel/Solver 读取 DiagramType 或图名**
   - 图类型差异必须通过 SemanticExtension 编译成 RoutingContract
   - 不能出现 `if diagram_type == Architecture { ... }` 在 Kernel 中

5. **禁止万能 hook 插桩**
   - 不提供 `before("phase_name")` / `after("phase_name")` 接口
   - 不提供事件总线让插件监听任意阶段
   - 扩展必须通过五类标准 trait

6. **禁止环境变量控制插件正式行为**
   - 插件所有配置必须进入 RoutingPlan 的 typed config
   - 环境变量只用于日志/trace/debug
   - problem signature 必须包含所有影响结果的配置

7. **禁止用随机数或 wall-clock 时间作为停机条件**
   - 所有启发式必须固定轮次、固定 tie-break
   - 时间测量只用于性能日志，不控制算法流程
   - 插件违反确定性规则时，auditor 产生 Error

8. **禁止图名/节点名特判**
   - 不能根据具体图的名字或节点名字改变算法行为
   - 领域规则通过 SemanticExtension + Contract 表达，不写死在代码里

### 4.2 可以做但有约束

| 操作 | 约束 |
|------|------|
| 添加新的 EdgeRole | 不能和内置 EdgeRole 语义冲突，必须文档化 |
| 替换内置 Solver | 必须通过所有内置 hard audit |
| 自定义几何 | 必须支持 annotation 同源生成，translate_all 正确 |
| 添加 AuditRule | Error 级规则必须可关闭（用户可选择降级为 Warning） |
| 配置 recipe 参数 | 所有参数必须可序列化，进入 problem signature |

## 5. 插件配置与 DSL 集成

### 5.1 DSL 中声明使用插件

```plotgram
diagram flowchart {
    plugin uml
    plugin metro {
        line_spacing: 12
        diagonal_angle: 45
    }

    entity user "用户"
    entity auth "认证服务" { type: service }

    user -> auth : 登录
}
```

### 5.2 RoutingPlan 中通过 typed config 配置

```rust
pub struct RoutingPlan {
    pub family: RoutingFamily,            // 内置或插件 recipe 名
    pub config: RoutingConfig,
    pub semantics: SemanticsConfig,       // 启用哪些语义扩展
    pub plugins: PluginConfig,            // 插件特定配置
    pub incremental: IncrementalPolicy,
    pub trace: TracePolicy,
}

pub struct PluginConfig {
    pub enabled: Vec<String>,
    pub params: HashMap<String, serde_json::Value>, // 插件参数可序列化
}
```

### 5.3 problem signature 必须包含插件配置

为了保证确定性和可复现性，`problem_signature` 必须包含：
- 启用的插件列表（name + version）
- 每个插件的配置参数
- 插件的 capabilities hash

这样同一份输入 + 同一份插件配置，在任何环境（CLI/Server/WASM）下产出完全相同的结果。

## 6. 与 Layout 侧插件的统一

插件体系不仅限于路由，布局侧也应该一致：

| 扩展点 | 路由侧 | 布局侧 |
|--------|-------|-------|
| 核心算法 | RoutingRecipe | LayoutRecipe |
| 语义编译 | SemanticExtension | StructureExtension |
| 求解器替换 | PathSolver/LaneSolver | CoordinateSolver/RankSolver/OrderSolver |
| 审计 | AuditRule | LayoutAuditRule |
| 后处理 | LabelStrategy | CompositionStrategy |
| 注册 | RoutingRegistry | LayoutRegistry |

统一的顶层注册：

```rust
pub struct PlotgramRegistry {
    pub layout: LayoutRegistry,
    pub routing: RoutingRegistry,
    pub rendering: RenderingRegistry,
}

impl PlotgramRegistry {
    pub fn builtin() -> Self { /* 内置所有 */ }
    pub fn register_plugin<P: PlotgramPlugin>(&mut self, plugin: P);
}

pub trait PlotgramPlugin {
    fn name(&self) -> &'static str;
    fn register(&self, registry: &mut PlotgramRegistry);
}
```

## 7. 分阶段实施路线

### P0：预留插件 trait，只注册内置（R0-R4 期间）

**目标**：在路由架构重构时就用插件 trait 组织内置实现，验证接口设计正确性。

任务：
1. 定义 `RoutingRecipe` trait，6 个内置 Recipe 都通过它接入
2. 定义 `AuditRule` trait，内置 hard audit 通过它注册
3. 定义 `RoutingRegistry::builtin()`，注册所有内置实现
4. 不暴露 `register_*` 外部 API，外部还不能注册插件
5. 验证：移除一个内置 Recipe 再通过 trait 加回来，行为一致

退出判据：
- 所有内置路由家族都通过统一 trait 接入
- 不需要任何 hack 或特殊通道

### P1：开放编译期插件注册（R5-R8 完成后）

**目标**：第三方 Rust crate 可以实现 trait 并注册。

任务：
1. 暴露 `RoutingRegistry` 的 `register_recipe`、`register_semantic_extension` 等公共 API
2. 完成 `RecipeCapabilities` 和 `PluginCapabilities` 声明与检查
3. 完成 `check_feature_support()` 兼容性验证
4. 添加插件配置序列化到 RoutingPlan
5. 写一个示例插件（如 `plotgram-metro` 或 `plotgram-uml`）验证接口

退出判据：
- 第三方 crate 可以成功添加新 Recipe，复用内置 Kernel/Solver
- 插件配置可序列化，problem signature 包含插件配置
- 错误配置产生明确诊断信息

### P2：语义扩展和 Solver 插件稳定

**目标**：五类插件口全部开放，文档和示例齐全。

任务：
1. 稳定 SemanticExtension trait
2. 稳定 PathSolver/LaneSolver/LabelStrategy trait
3. 插件开发者文档 + 多个示例插件
4. 插件版本管理 + 冲突检测
5. 性能基准：插件不能显著拖慢内置路径

退出判据：
- 至少 2-3 个外部插件成功接入（如 UML、电路图、甘特图）
- 插件 API 稳定一个版本不 break

### P3：WASM 插件宿主（远期，生态成熟后）

**目标**：支持非 Rust 语言编写的沙箱插件。

任务：
1. 基于 wasmtime 设计 WASM ABI
2. 实现插件沙箱（内存/时间/系统调用限制）
3. 宿主 Kernel 函数通过 ABI 暴露给 WASM
4. 插件市场/分发机制（可选）

退出判据：
- 非 Rust 插件（如 C/Zig 编写）能加载运行
- 沙箱边界验证通过（插件崩溃不影响宿主）
- 性能开销 < 20%（相比编译期插件）

## 8. 与竞品插件体系对比

| 维度 | D2 插件 | ELK 扩展 | yFiles | Plotgram 插件 |
|------|--------|---------|--------|--------------|
| 插件接口 | `Layout(ctx, *Graph)` 拿到整个图随便改 | `ILayoutPhase` 阶段链 | 模块化 Router + 配置 API | 五类窄 trait，按层扩展 |
| 隔离性 | 差（插件可破坏任何不变量） | 中（phase 有约定但可变 ElkNode） | 中（封装较好但闭源） | 强（窄 IR + typestate 冻结） |
| 复用内置能力 | 弱（插件基本自己写） | 中（可复用部分 phase） | 中（API 调用） | 强（15个Kernel + 6个Solver全部可复用） |
| 能力声明 | PluginFeature 检查 | Layout Options 元数据 | License + Feature 枚举 | RecipeCapabilities + PluginCapabilities |
| 动态加载 | Binary 插件（stdin/stdout JSON） | OSGi（Java） | 无（闭源） | 一期编译期 Rust trait，远期 WASM 沙箱 |
| 插件破坏 hard constraint | 可以 | 可以（配置错误时） | 不可以（商业保证） | 类型上不可以（唯一写权 + auditor） |
| 配置可复现 | 依赖插件实现 | 140+ 选项难复现 | 商业保证 | typed config 进入 problem signature |
| 确定性 | 依赖插件实现 | 依赖实现 | 较好 | 强制规则（固定轮次、禁随机、tie-break） |
| 万能 hook | 支持（Plugin 可任意改） | 通过 phase 链 | 配置驱动 | **不支持**（故意不提供） |
| 沙箱安全 | Binary 插件无隔离 | JVM 安全模型 | 无（闭源） | 编译期内存安全 + WASM 沙箱 |

**核心差异**：D2/ELK 的插件默认权力很大，需要开发者自觉不破坏不变量；Plotgram 插件默认只能做窄范围的事情，想绕过架构卫生需要刻意突破多层防护。

## 9. 风险与控制

| 风险 | 控制措施 |
|------|---------|
| 插件接口过早冻结导致后期难改 | P0 阶段只用 trait 组织内置实现，不对外暴露，经过 R0-R11 完整验证后再开放 |
| 万能 hook 需求压力（用户想要 before/after） | 明确拒绝，先收集真实需求，用新的标准扩展点满足，不做通用 hook |
| 插件质量参差不齐影响体验 | Error 级 audit 不通过不产出；内置 plugin lint 检查常见问题；插件评分/标记"官方认证" |
| WASM 插件性能差 | 编译期插件优先；WASM 作为可选扩展，不替代编译期插件；性能基准持续监控 |
| 插件生态碎片化 | 内置能力保持强大，插件只做领域扩展，不把核心能力下放到插件 |
| 版本兼容 break | 插件 trait 遵循 Rust semver；P2 稳定后至少一个版本不 break；capabilities 声明版本要求 |

---

## 10. 不做的事

1. **不做可视化插件编排 UI**：一期不提供拖拽式插件管线编辑器
2. **不做插件市场/商店**：远期考虑，P3 之前不做
3. **不支持 hot reload**：插件注册在引擎初始化时完成，不支持运行时动态加载/卸载
4. **不做 Python/JS 语言绑定作为一期目标**：先稳定 Rust 接口，其他语言绑定通过 WASM 或 FFI 后期提供
5. **不让插件控制渲染样式**：一期插件只影响布局/路由几何，颜色/笔触/图标等视觉属性仍由主题系统控制（渲染插件是另一个独立话题，本方案不覆盖）
6. **不做插件依赖管理**：P0-P2 由用户手工确保插件版本兼容，类似 Rust crate 依赖
7. **不把核心算法下放到插件**：正交路由、Bezier、Organic 等核心 Recipe 保持内置一等地位

## 11. 完成定义

本插件体系完成时，应满足：

1. 五类插件扩展点（Recipe/SemanticExtension/Solver/LabelStrategy/AuditRule）都有稳定的 Rust trait
2. 所有内置实现都通过插件 trait 接入，无特殊通道
3. 第三方 Rust crate 可以注册新 Recipe 和语义扩展，复用内置 Kernel/Solver
4. 插件配置全部可序列化，problem signature 包含插件配置
5. 能力声明和兼容性检查在 compile 前自动执行
6. hard constraint 不可被插件绕过（auditor 对插件产出同样生效）
7. 确定性对插件同样生效（禁随机、禁时间停机、固定 tie-break）
8. 不提供万能 hook DSL
9. 有至少 2 个示例插件验证接口正确性
10. 插件开发者文档完整
