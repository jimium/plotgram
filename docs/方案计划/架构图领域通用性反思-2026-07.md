# 架构图领域通用性反思

> 状态：已定案（待实施）
> 日期：2026-07-18（2026-07-21 修订）
> 作者：讨论纪要

## 1. 核心问题

当前 `architecture` 图表类型的 entity type **过度绑定软件开发领域**，限制了架构图作为通用图形范式的表达能力。

### 1.1 现状：9 种 type 全是 IT 领域概念

见 [`profile/mod.rs`](../../crates/plotgram-core/src/profile/mod.rs#L108-L118)：

```
frontend, backend, service, database, gateway, cache, queue, storage, external
```

这些 type 全部指向软件/互联网行业的特定组件。

### 1.2 问题：换个行业就没法用了

| 行业/场景 | 需要表达的节点类型 | 当前 type 够用吗 |
|-----------|-------------------|-----------------|
| 组织架构 | 部门、团队、岗位、人员 | ❌ 完全不匹配 |
| 硬件架构 | CPU、内存、主板、外设 | ❌ 不匹配 |
| 建筑/平面 | 房间、走廊、电梯、楼梯 | ❌ 不匹配 |
| 工艺流程 | 工位、物料、检测、包装 | ❌ 不匹配 |
| 生态系统 | 生产者、消费者、分解者 | ❌ 不匹配 |

但这些场景从**图形结构特征**上看，都是「架构图」：
- 节点是并存的实体（不是过程步骤）
- 有分组/分层/分区的概念
- 边表达连接/依赖/流动关系
- 没有明确的「开始/结束」

## 2. 三层结构分析

当前的 type 体系分为三层，问题主要出在第二层与第三层的错配：

### 2.1 第一层：基础形状（通用，没问题）

见 [`render/visual.rs`](../../crates/plotgram-core/src/render/visual.rs#L60-L77) 的 `NodeShape` 枚举：

```
Rect           矩形
RoundedRect    圆角矩形
Circle         圆形
Diamond        菱形
Cylinder       圆柱体
Hexagon        六边形
Person         人形
Stadium        体育场形
Parallelogram  平行四边形
Document       文档形
Cloud          云形
Subprocess     子流程（双边框）
```

共 12 种基础形状，**领域无关**，任何行业都能用。

### 2.2 第二层：主题映射（命名偏 IT，但机制通用）

在主题 JSON 的 `entity_types` 中，用**领域语义**命名 type，然后映射到形状 + 颜色：

```json
"entity_types": {
  "service":   { "shape": "rounded_rect", "fill": "蓝色系" },
  "database":  { "shape": "cylinder",     "fill": "橙色系" },
  "gateway":   { "shape": "diamond",      "fill": "青色系" },
  ...
}
```

**问题**：推荐清单的 type 名偏 IT 语义（`service`, `database`...），非软件用户缺少开箱即用的中性词汇；但主题层对未知 type 已能兜底到 `node_default`，机制本身无缺陷。

### 2.3 第三层：图表类型闭集（真正的闸门）

见 [`profile/mod.rs`](../../crates/plotgram-core/src/profile/mod.rs#L108-L118)，每种图表类型有自己的 type 白名单：

```rust
const ARCHITECTURE_ENTITY_TYPES: &[&str] = &[
    "frontend", "backend", "service", "database",
    "gateway", "cache", "queue", "storage", "external",
];
```

校验层把「推荐清单」等同于「合法边界」，进一步把「架构图」限定在了软件架构的范畴内。

## 3. 产品定位（已定案）

### 3.1 architecture 是什么

> **architecture = 结构关系图（开放画布）+ 软件领域内置推荐样式**

- DSL 关键字**暂不改名**，继续用 `diagram architecture`。
- 文档称呼调整为「结构图」：强调结构范式，而非软件架构专用。
- **不新增** `graph` / `topology` 等平行图种——与 flowchart 边界模糊，且与现有 architecture 布局（`architecture_v2` + 正交路由 + 显式 `group`）高度重复。

与 flowchart 的分工：

| 图种 | 结构特征 | 核心问题 |
|------|----------|----------|
| `flowchart` | 有步骤顺序、start/end | *先做什么、再做什么？* |
| `architecture` | 并存实体、分组/分层、连接关系 | *由什么组成、如何连接？* |

### 3.2 与 Mermaid `graph` 的对比

Mermaid 用通用 `graph` + 形状语法，灵活但布局单一、无场景优化。Plotgram 选择保留 `architecture` 作为**带分组布局的结构画布**，通过开放 type + 通用结构 type 补齐通用性，而非退化为万能 `graph`。

## 4. 核心共识

1. **架构图是图形结构范式，不是领域分类** — 应能表达任何行业的结构关系。
2. **当前 type 闭集过于绑定软件领域** — 限制了适用范围；根因是校验策略错配，不是布局算法缺陷。
3. **形状是通用的，领域语义是用户的** — `label` 承载「财务部」「CPU」等领域含义；`type` 承载结构角色与视觉预设。
4. **推荐 type 与合法边界解耦** — 内置 type = 推荐 + 主题映射，不再作为拒绝用户的依据。
5. **闭合记法与开放画布分治** — state/sequence/mindmap/flowchart 保持闭集；architecture 全面开放。

## 5. 选定方案：开放扩展 + 三层 type 词汇

设计目标：

- **推荐 type 与合法边界解耦**；未知 type 优雅降级而非报错。
- **保留 IT type** 作为软件开箱即用预设包，不删除、不替换。
- **新增通用结构 type** 作为跨行业预设包，降低非 IT 用户上手成本。
- **任意自定义 type** 作为第三层扩展，配合 `shape`/`fill`、`node_style`、主题扩展自定义外观。

### 5.1 三层 type 词汇

```
┌─────────────────────────────────────────────────┐
│  Layer 1：通用结构 type（内置推荐，跨行业）          │
│  component / endpoint / storage / hub / ...     │  → 形状 + 配色
├─────────────────────────────────────────────────┤
│  Layer 2：IT 行业 type（内置推荐，软件开箱即用）     │
│  service / database / frontend / queue / ...      │  → 复用 Layer 1 视觉
├─────────────────────────────────────────────────┤
│  Layer 3：用户自定义 type（开放后任意 atom）         │
│  部门 / CPU / 工位 / ...                           │  → node_default 或用户样式
└─────────────────────────────────────────────────┘

  semantic（mysql / browser / user）  →  图标推断，与 type 正交
  shape / fill（内联覆盖）             →  最终外观兜底
```

**正交分工**：

| 字段 | 职责 |
|------|------|
| `type` | 结构角色 + 视觉预设（形状、配色） |
| `label` | 领域语义（「财务部」「订单库」「CPU」） |
| `semantic` | 技术/图标语义（可选，偏 IT 图标库） |
| `shape` / `fill` | 覆盖 type 默认外观 |

### 5.2 通用结构 type（新增，7 个）

按**结构角色**命名，不按行业、也不用 shape 名当 type（避免与 `shape` 属性重复）：

| 通用 type | 视觉 | 对应现有 IT type | 跨行业示例 |
|-----------|------|------------------|------------|
| `component` | 圆角矩形 | `service`, `backend` | 部门、模块、工位、CPU |
| `endpoint` | 矩形 | `frontend` | 入口、客户、接口 |
| `storage` | 圆柱体 | `database` | 仓库、档案、内存 |
| `hub` | 菱形/六边形 | `gateway`, `cache` | 枢纽、交换机、检测点 |
| `channel` | 平行四边形 | `queue` | 通道、传送带、管道 |
| `external` | 虚线矩形 | `external` | 外部系统、第三方 |
| `person` | 人形 | flowchart 已有 | 人员、岗位、角色 |

IT type **全部保留**，主题层让 IT type **复用**通用 type 的视觉定义（同 shape + 同配色），避免维护两套主题资产。

`default_entity_type` **暂保持 `service`**（软件场景仍是主路径）；文档引导非软件用户显式写 `component`。

### 5.3 自定义 type 的三条通道

开放后 `type: 部门` 默认落到 `node_default`（圆角矩形 + 中性色）。用户可通过：

1. **内联属性**：`entity dept "财务部" { type: 部门, shape: hexagon, fill: "#..." }`
2. **DSL 声明**：`node_style 部门 { shape: hexagon, fill: "..." }`
3. **主题扩展**：项目主题 JSON 的 `entity_types: { "部门": {...} }`

### 5.4 明确不做

- **不用 shape 当 type**（`rect`/`cylinder`）——与 `shape` 属性语义重复。
- **不为每个行业加 type**——`部门`/`CPU`/`房间` 交给 Layer 3 开放 type。
- **不把 IT type 删掉或改名**——现有 showcase 与主题资产继续有效。
- **不新增 `graph` 图种**——architecture 即结构画布。
- **暂不改 DSL 关键字**——`architecture` 保留；远期可视需要加 `structure` 别名。

## 7. 代码核对：`type` 到底被谁消费

> 结论先行：整条渲染管线里，**唯一把架构图 type 锁死的就是「校验闭集」这一处**；主题层本就对未知 type 兜底，架构图布局根本不读 type 语义。

| 消费点 | 代码位置 | 对未知 type 的行为 |
|--------|---------|-------------------|
| **校验闭集** | [`validation/attrs.rs` L44-53](../../crates/plotgram-core/src/validation/attrs.rs#L44-L53) | **硬报错** `invalid_enum_value` ← 唯一真正的闸门 |
| 主题级联 | [`theme/schema.rs` node_block L478-485](../../crates/plotgram-core/src/theme/schema.rs#L478-L485) | 已优雅兜底：`unwrap_or(&d.node_default)` |
| DSL 样式声明 | [`prepare/styles.rs` L40-47](../../crates/plotgram-core/src/prepare/styles.rs#L40-L47) | 仅 warning（unknown_style_selector） |
| 布局语义 | sugiyama_v2 / circular / mindmap | 仅 flowchart/state/mindmap 用 type 判定 initial/final/start/end/root |
| **架构图布局** | architecture_v2（全目录） | **完全不消费 type 语义**，分组靠显式 group 语法 |

**关键发现**：对架构图而言，`type` 纯粹是渲染（形状 + 颜色）属性，布局不读它；且主题层对未知 type 已兜底为 `node_default`。因此开放架构图 type 的风险面极小。

## 8. 定性：抽象层次错配

是设计缺陷，但不是「考虑不周」式的模糊问题，而是一个**抽象层次错配（category error）**：

> **把「开放结构画布」当成「闭合记法语言」来建模了。**

系统里混着两类本质不同的图：

- **闭合记法（bounded notation）**：state、sequence、mindmap、flowchart。`initial/final`、`actor/lifeline`、`root/branch` 不只是样式，而是**布局算法的语义输入**。对这些图，type 闭集校验是**正确的**。
- **开放画布（open canvas）**：architecture。布局**不消费 type 语义**，type 只驱动形状与颜色。对这类图，闭集校验没有任何算法上的必要性。

缺陷根因在 [`profile/mod.rs` L61-63](../../crates/plotgram-core/src/profile/mod.rs#L61-L63)：

```rust
pub fn restricts_entity_type_values(&self) -> bool {
    !self.entity_types.is_empty()   // ← 把「有推荐清单」等同于「必须闭集校验」
}
```

两个**正交**的概念被绑成了一个：

1. 这个图有哪些**推荐/内置** type（补全、主题映射、文档提示）
2. 这个图是否**只允许**这些 type（合法性边界）

ER（`entity_types` 为空 → `restricts=false`）已证明「有推荐清单 ≠ 必须闭集」；architecture 只是没享受同样待遇。

后续方案的本质不是「加功能」，而是**修正这个错配**——让 architecture 回到「开放画布」类别。

## 9. 实施路线

### 阶段 0：分治原则（决策，不改码）

- **保持闭集**：state、sequence、mindmap、flowchart。
- **改为开放**：architecture——type 不参与布局，全面开放。

### 阶段 1：profile 层解耦「推荐清单」与「校验策略」

在 [`DiagramProfile`](../../crates/plotgram-core/src/profile/mod.rs#L16-L45) 引入显式开关：

```rust
pub struct DiagramProfile {
    ...
    pub entity_types: &'static [&'static str],   // 语义变为「推荐/内置」，不再等于「合法边界」
    pub entity_types_open: bool,                 // true=开放画布，false=闭合记法
}
```

改写判定：

```rust
pub fn restricts_entity_type_values(&self) -> bool {
    !self.entity_types.is_empty() && !self.entity_types_open
}
```

- architecture profile 设 `entity_types_open: true`，**保留并扩展** `ARCHITECTURE_ENTITY_TYPES`（通用结构 type + IT type）。
- state/sequence/mindmap/flowchart 设 `entity_types_open: false`。
- ER 不变（本就空集）。

### 阶段 2：校验层——未知 type 降级为 warning

[`validation/attrs.rs`](../../crates/plotgram-core/src/validation/attrs.rs#L44-L53) 对开放 profile 不再进入 error 分支。为保留引导价值：

- 开放 profile 且 type 不在推荐清单内 → **warning**（如 `custom_entity_type_hint`：「`部门` 不是内置 type，将使用默认形状；可用 `shape`/`fill` 自定义外观」）。
- 闭合 profile 行为不变（继续 error）。

### 阶段 3：通用结构 type + 主题映射

1. 在 `attr_constants.rs` 新增 7 个通用结构 type 常量。
2. 扩展 `ARCHITECTURE_ENTITY_TYPES`：通用 type 在前，IT type 在后。
3. 主题 `entity_types`（`common.clean-light` / `common.clean-dark` 等）：
   - 为 7 个通用 type 定义视觉；
   - IT type 复用对应通用 type 的 shape + 配色（内容复制即可，不必引入 inherit 机制）。
4. 不进布局算法——通用 type 仅影响渲染与补全提示。

### 阶段 4：自定义外观通道验收

验证三条通道通畅（多数已存在）：

1. 内联 `shape` / `fill` 覆盖 cascade。
2. `node_style <自定义type> { ... }` 按 type 字符串匹配。
3. 主题 JSON `entity_types` 扩展。

产出主要是**验证 + 补齐 `shape` 作为可覆盖键**，非大改。

### 阶段 5：文档与示例

- 更新 [`entity-types.md`](../specs/visual-language/entity-types.md)：区分闭集图种与开放图种；列出通用结构 type 与 IT type 对照。
- 更新 [`architecture.md`](../specs/visual-language/diagrams/architecture.md)：定位改为「结构关系图」；补充组织架构等跨行业示例。
- 反思文档状态改为「已实施」。

### 阶段 6：确定性调色兜底（可选增强）

多种自定义 type 视觉难区分时，可按 type 名稳定哈希映射到主题调色板 role 色。

- **必须确定性**（AGENTS.md §2）：用 type 名稳定 hash，不依赖 HashMap 迭代序。
- 非必需，优先保证「能用」与通用 type 预设。

### 阶段 7：测试

- profile：`architecture` 接受任意 type 不报错；内置 type 仍走主题映射；`state` 仍拒绝非法 type。
- 校验：`type: 部门` 在 architecture 下产出 warning 而非 error。
- 主题：通用 type 与 IT type 视觉符合 §5.2 对照表。

## 10. 风险与边界

- **绝不动 state/sequence/mindmap/flowchart 的闭集**——type 是布局文法输入，开放会静默破坏布局。
- **主题层机制不用改**——`node_block` 兜底已就绪；阶段 3 仅扩展 `entity_types` 条目。
- **无向后兼容负担**（AGENTS.md §1）：直接改 `restricts_entity_type_values` 语义，IT type 保留，不留兼容层。
- **改动面集中**：profile（加字段 + 改一方法）+ validation（error 降 warning）+ 主题/type 常量扩展 + 文档。
- **与布局/路由全局优化正交**：`docs/优化重构/` 管几何质量；本方案管类型系统与产品模型，可并行推进。

## 11. 跨行业示例（目标态）

### 软件架构（IT type，Layer 2）

```plotgram
diagram architecture {
    entity user "用户" { type: frontend }
    entity api "API 服务" { type: service }
    entity db "主库" { type: database }
    user -> api -> db
}
```

### 组织架构（通用 type，Layer 1）

```plotgram
diagram architecture {
    entity hq "总部" { type: component }
    entity rd "研发部" { type: component }
    entity alice "张三" { type: person }
    hq -> rd
    rd -> alice
}
```

### 自定义 type（Layer 3）

```plotgram
diagram architecture {
    entity room "会议室 A" {
        type: 房间
        shape: rect
        fill: "#F5F3FF"
    }
}
```
