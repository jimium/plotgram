### 3.2 第二阶段：合并冗余阶段（预计减少 ~5,000 行）

**目标**：将职责重叠的模块合并，减少管线步骤数。

#### 3.2.1 边段分离统一化（详细设计 v2，2026-07-20 据实修订）

> **修订说明**：原方案（合并 `conflict_reroute` + `lane_assignment` + `stub_fix` → 600 行）
> 经代码调研判定**不可行**。这 7 个步骤是**两类本质不同的职责**，强行合并会造成
> 巨型函数并丢失重路由能力。下为据实重写的设计。

##### 现状分类（基于 run.rs / pipeline.rs / phases/refine.rs 调研）

七个「分离」实为两类：

| 类别 | 步骤 | 本质 | 依赖 | 处置 |
|------|------|------|------|------|
| **A 重路由** | `reroute_conflicting_edges` (X-1, 316行) | 多轮 path-selection 重选路 | scorer/corridor/obstacles/grid | **保持独立，不并入** |
| **A 重路由** | `fix_reverse_stub_ports` (X-2, 839行) | 端口翻转 + 重路由 | 同上 + endpoint_map | **保持独立，不并入** |
| **B 微平移** | `enforce_reverse_pair_min_gap` | 正反向对干线间距 | 无（纯几何） | 并入引擎 |
| **B 微平移** | `enforce_reverse_pair_dock_separation` | 同侧 dock 落点 | nodes/sides | 并入引擎 |
| **B 微平移** | `resolve_stub_occupancy_conflicts` / `..._post_route` | 同侧 stub 柱 | nodes/sides | 并入引擎 |
| **B 微平移** | `assign_lanes` (Union-Find) | interior 段车道 | nodes/grid | 检测+平移抽出，分组逻辑保留 |
| **B 微平移** | `separate_unrelated_trunk_overlaps[_post_route]` | 非语义 trunk | merge_policy/lint | 并入引擎 |

B 类**全部遵循同一模式**：`检测(近距同轴对) → 沿 cross-axis/切向平移拉开 → 验证(不穿节点/不反向/不退化/不新增交叉) → 回退`。共享 `undirected_pair_key` 分组、BTreeMap 确定性、shift+validate+rollback、grid 重建、stats 汇总。

##### 统一方案评估 → **否决建引擎**（2026-07-20 执行后修订）

进入实施前先读了 B 类各 pass 的实际 shift/validate 原语，得出与「建引擎」相反的结论：

- `validate_shift` / `commit_shifted_path` / `segment_hits_node` / `direction_sign` / `force_shift_trunk_coord` **早已是 lane_assignment.rs 内的共享函数**——真正的重复（几何原语）已经被抽出来了。
- 各 pass 的差异只在**上层编排**：`assign_lanes` 是 Union-Find 分组 + 对称偏移；`stub_occupancy` 是贪心 live-recompute；`min_gap`/`dock_sep` 是无条件拉开；`trunk_sep_post_route` 是 crossing-neutral 逐对回退。这些控制流**本质不同**。
- 强套 `Detector/Guard` trait 引擎，只会把这些异构控制流塞进带大量 per-detector 特判的「统一」接口——**增加**抽象复杂度，与「简化」目标相悖。这与第一阶段 Step 7 的教训同源：方案文档对实际结构过于乐观。

**结论**：不建 `SeparationEngine`。B 类的真实可得收益不是「合并成引擎」，而是**去掉冗余的重复调用**（下）。

##### 实测：C/D 双调用去重（本阶段实际执行，每步跑门禁）

`min_gap` / `dock_sep` 在 C 期（phase_lane、run.rs 末）与 D 期（pipeline 末）重复调用。逐一移除 C 期预修、对比 `s2-before` 基线（= phase1-final，零漂移）：

| 实验 | 移除对象 | 门禁 | 处置 |
|------|----------|------|------|
| A | `run.rs` C 末 `enforce_reverse_pair_dock_separation` | **PASS** | ✅ 删除（D 末最终写者覆盖，纯冗余） |
| B | `phase_lane` C 期 `enforce_reverse_pair_dock_separation` | **FAIL**（`product.user-auth` node_fp 变化） | ⛔ 回滚（C 期未冻结，dock 改动经反馈移节点，承重） |
| C | `phase_lane` C 期 `enforce_reverse_pair_min_gap` | **PASS** | ✅ 删除（2 点直连对不触发节点反馈，D 末覆盖） |

**净结果**：`dock_sep` 调用 3→2、`min_gap` 调用 2→1；管线减少 2 次冗余分离调用 + `gap_fixed` 死代码。全量门禁 product/stress 全 PASS，单测无新增失败（既有 19 项基线失败经 `git stash` 核实早于本工作，与改动无关）。

**关键认知（写入手册）**：C 期（节点未冻结）的边几何改动会经 space-budget/refine 反馈**移动节点**，因此 C 期分离 pass **不是纯冗余**——只有「D 期已覆盖且不参与 C 期后续反馈」的调用才可安全删除。这正是 B 与 A/C 结果分野的原因。

#### 3.2.2 Scoring 精简

**现状**：10+ 惩罚因子，权重按图种/边类型分叉。

**方案**：合并为 4 个核心惩罚项：

      + bend_weight * bend_count
      + obstacle_weight * obstacle_penalty    // 合并：node_crossing + group_transit + near_miss + pierce_depth
      + congestion_weight * overlap_penalty   // 合并：edge_overlap + channel_load + protected_trunk

**执行结论（2026-07-20，删除实验 → FAIL 回滚，S4 判定为非冗余）**：

按预案做了完整的「门禁保护删除实验」：

1. **调研**：S4 门控 `s4_monitor_corridor = profile.semantic_merge && diagram.groups.is_empty()` + 监控枢纽（某目标 ≥3 条被动 `-->` 入边）。24 样本中**仅 `typical-microservice-architecture` 一个触发**（6 条被动入边全指向 prometheus，groups=0），门禁全覆盖该样本。

   - `typical-microservice-architecture`：`node_fp` 变化（`48226cfc76f310eb → 4e0debccdf96de3f`）
   - `tight_sev` **1048 → 3044（约 3 倍恶化）**

5. **后续**：S4 保留现状。若要精简，需先提供「监控枢纽外环」的通用替代（非图名特判），在 `typical-microservice-architecture` 上 `tight_sev` 不劣于 1048 方可再评估——这属于 §7 算法级重写范畴，不走日常棘轮。

**保留：** S3 `semantic_trunk_merge` 核心 FanIn 合流不动；本节不再做删除。

## 5. 风险与回退方案

### 5.1 风险识别

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 合并分离 pass 后密集图退化严重 | 中 | 中 | 保留分离逻辑核心算法，仅合并调用入口 |
| 移除 S4 后特定架构图退化 | 低 | 低 | S4 仅服务无组+监控枢纽，可用普通回环边替代 |
| Scoring 精简后路径质量下降 | 中 | 中 | 保留 4 核心项的权重可调，用 showcase 回归验证 |
| 移除样条降级后穿障边无法修复 | 低 | 中 | dogleg 已覆盖 90%+ 场景，残余可保留原路径 |
| 管线步骤减少后写权冲突 | 低 | 高 | 每步合并后跑全量 showcase 验证 |

### 5.2 回退策略

- 每个阶段独立提交，可单独 revert
- 第一阶段（死代码清理）几乎零风险，可直接合入
- 第二、三阶段按子模块拆分 PR，每个 PR 附带 showcase 回归对比
- 使用 `benchmarks/compare.sh` 量化退化程度
- 若某子模块退化超过 20%（严重度加权），暂停该模块简化，分析原因

### 5.3 不可触碰的红线

以下约束在简化过程中**不得违反**（AGENTS.md 硬红线）：

1. **确定性**（§2）：禁止依赖 HashMap 迭代序
2. **禁止图名特判**（§5）：不为特定图引入分支
3. **WASM 兼容**（§6）：不使用 `std::time::{Instant, SystemTime}`
4. **验真**（§5）：用 `cargo run -p plotgram-cli` 验证
5. **Annotation 语义**（手册 §1.7）：渲染消费 annotation，不猜路径点数

## 8. 总结

本方案通过三阶段渐进式简化，将布局与路由模块从 ~69,700 行降至 ~57,700 行（-17%），管线步骤从 25 步降至 13 步（-48%），同时保持核心路由质量不变。

**核心原则**：
1. 移除实验性/诊断性代码（零风险）
2. 合并职责重叠的阶段（低风险，可量化）
3. 精简过度特化的策略（中风险，抬基线）

**不简化的部分**：
- 走廊路由（有组场景核心）
- 端口/Slot 选择（路由基础）
- Sanitize 不变量（几何正确性）
- 标签避让（可读性核心）
- 确定性排序（AGENTS.md 红线）
