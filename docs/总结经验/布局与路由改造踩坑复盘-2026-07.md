# 会话复盘：Label 碰撞与正交路由问题为何一度未解

> 日期：2026-07-12  
> 位置：`docs/总结经验/`（由 `docs/architecture/重构方案/` 迁入并重命名）  
> 会话：[路由问题为何一度未解](6f1586f2-fa83-4456-9f49-81c9e6171181)  
> 范围：`n.user-auth` label 碰撞 → `c.supply-chain-control-tower` / `c.layout-stress-nested` 弯折、入出边重合、overshoot Z 折、近距 label 省略引线  
> 目的：记录**先前模型最终如何解决问题**，以及**为何中间长时间未能收敛**，供后续 agent / 协作者避免重复踩坑。

---

## 0. 一句话结论

最终修对的不是「某个图的特例参数」，而是三类**管线时序 / 后处理死锁 / 端口翻转无去冲突**的系统缺陷。  
中间失败的主因也不是「不会改代码」，而是：**过早局部猜因 + 陈旧二进制误导调试 + 改动放在节点布局仍可变的阶段导致假回归**。  
一句话：**先冻结几何再改标签/折点，先用 `cargo run` 验真再信 stderr，先量化全量 showcase 再谈「无退化」。**

## 1. 会话里实际解决了什么

### 1.1 第一轮：`n.user-auth` label 碰撞

| 表象 | 真正根因 | 最终修复 |
|------|----------|----------|
| 双向边 label 完全叠在一起 | 路由 step-5 算完避让后，管线末尾 `sanitize_orthogonal_edges` **按平行边规则重建全部 label**，避让结果被丢弃；且 snap/repulse 又动了路径 | `pipeline.rs`：最终 sanitize 之后再跑一次 `resolve_label_overlaps_with_config` |
| 密集走廊仍残留重叠 | label-label 只沿最小穿透轴推一次，被节点夹住就放弃 | `label_avoidance.rs`：不安全时回退正交轴再推 |

### 1.2 第二轮：架构图弯折 / 扭曲 / 引线

| 表象 | 真正根因 | 最终修复 |
|------|----------|----------|
| 边线「冲过再折回」的 Z 扭曲 | `lane_assignment` 平移 interior 段产生 overshoot；`collapse_micro_jogs` 按「离 curr 最近」选角点，`cand_b == curr` 时**死锁** | `sanitize.rs`：按「与相邻段共线合并分数」选角；**仅管线末尾** `merge_overshoot=true` |
| 入边与出边端口重合 | `stub_fix` 翻转端口硬编码 `frac=0.5`，与同侧已有边撞锚 | `stub_fix.rs`：`deconflict_flip_anchor` 沿切线错开 |
| 两 label 很近却省略引线 | 引线只看「离路径可见长度」，不感知邻近其它边的 label | `label_avoidance.rs`：Pass 2 邻近感知强制保留引线 |

## 2. 先前模型是如何最终解决问题的（可复用方法）

成功收敛时，路径大致是：

```text
截图问题
  → 渲染 JSON，抽出节点 bbox / 边折点 / label center / leader
  → 用坐标把「视觉抱怨」翻译成可证伪命题
  → 沿管线阶段（Step1 端口 → … → sanitize → label）对照 dump
  → 定位「谁在几何冻结之后又改了结果」或「谁本该修却修不动」
  → 改通用规则（时序 / 死锁启发 / 去冲突），禁止硬编码图名
  → 全量 showcase 重叠脚本 + 节点坐标前后对比 + 测试基线对照
```

关键动作（值得固化为习惯）：

1. **数值化视觉问题**  
   例如入出边共锚写成「两端点同为 `(225,981)`」；overshoot 写成「竖段 x=508，端口 x=498」。没有坐标就无法排除「只是看起来密」。

2. **追管线时序，不追单函数观感**  
   Label 轮真正突破点是发现：router 内部避让 → pipeline sanitize **重建 label** → 避让被丢。这是架构时序 bug，不是候选打分微调能根治的。

3. **改动放在「几何已冻结」之后**  
   overshoot 合并若在 router 内部 sanitize（4g）启用，会反馈进 space-budget / 节点重定位，节点整体平移 → 其它图 label 指标假回归。最终方案：router 保守，pipeline 末尾激进。

4. **用「严重度」而不是「计数」谈退化**  
   label-node 数量 +1 但总穿透下降，判定为重排而非恶化；避免为消除一个 warning 引入更大逻辑。

5. **基线失败单独钉死**  
   全量测试 3 个失败经 stash 对照确认为仓库既有问题，避免把无关失败当成自己引入的回归。

## 3. 为什么中间一度没能解决（失败模式）

下面按「浪费时间的数量级」排序。这些不是「模型不会写 Rust」，而是**调试闭环断了**。

### 3.1 陈旧二进制（最大时间黑洞）

现象链：

- 已改 `pipeline.rs`，加了 `eprintln!`
- `perf_log!`（同一函数稍后）能打出 `[perf] post-process`
- 自己的 `eprintln!` 完全没有
- 于是误判：「这段代码没跑到」「`edge_routing_style != orthogonal`」「走了另一条 layout 入口」

真相：

- `target/release/plotgram` 时间戳不更新；Cargo release + LTO / fingerprint 有时**重编库却不重链可执行文件**
- 脚本直接跑 `./target/release/plotgram` → 永远在测旧逻辑
- 正确做法：验证用 `cargo run --release -p plotgram-cli -- …`；或强制 touch/清 fingerprint 后再确认 binary mtime

教训：**stderr 与源码不一致时，先怀疑产物，再怀疑控制流。**

### 3.2 过早局部猜因，推迟管线对照

Label 轮早期大量时间花在：

- 平行边偏移是否够大
- 法向量是否同侧
- Phase1 候选分数是否选错

这些都可能是次因，但**主因是 sanitize 丢弃避让**。  
在没有「最终输出里的 label 是否等于 router step-5 输出」的对照之前，局部调参无法闭环。

教训：**先回答「最终输出是谁写的」，再回答「算法算得对不对」。**

### 3.3 把「节点动了」当成路由修好了

第二轮把 `collapse_micro_jogs` 直接接到 router 内部后：

- overshoot 消失，图看起来更干净
- 但 nested 图节点坐标相对基线整体偏移（例如 `biz_svc` x 从 284→144）
- 全量 label-label 在个别架构图上升

若停在「视觉更好」，会把**节点重排副作用**当成成功，违反「已有效果不能退化」。

教训：**sanitize/后处理改路径形状时，必须对比节点坐标是否不变；变了就要把激进逻辑挪到几何冻结之后。**

### 3.4 对「高风险模块」犹豫过久，却未先读调用上下文

`stub_fix` 一度被认为「改签名太侵入、需要感知其它边锚点」，差点改成 sanitize 末端几何 nudge。  
实际上 `fix_reverse_stub_ports` **已有** `endpoint_map`，在翻转赋锚时做去冲突是自然落点。

教训：**先读函数已有参数与调用阶段，再决定「侵入性」。**

### 3.5 启发式死锁被当成「阈值不够」

`collapse_micro_jogs` 的 overshoot 案例：两段长度都已小于 `MICRO_JOG_LEN`，却因「选离 curr 最近的候选角」选中恒等变换。  
若只加长阈值或只加更多迭代，**死锁逻辑不变**，问题仍在。

教训：**修后处理时先构造「候选是否恒等 / 是否可共线合并」的最小例子，再动阈值。**

### 3.6 工具与环境噪音

- 对 `target/` 盲目 `rg` 可卡住
- 临时 Python 依赖 `numpy` 缺失导致检查脚本中断
- 把「探索失败」和「算法失败」混在同一时间线，干扰判断

教训：回归脚本尽量零第三方依赖；探索命令失败要显式标为无关。

## 4. 「之前模型」vs「中间卡住」的对照

| 维度 | 卡住时 | 最终解法 |
|------|--------|----------|
| 证据 | 看图 + 猜模块 | JSON 坐标 + 阶段 dump |
| 假设 | 单点算法不够好 | 时序 / 死锁 / 缺去冲突 |
| 验证 | 直接跑旧 binary | `cargo run` + mtime 核对 |
| 改动位置 | 哪里看起来相关改哪里 | 几何冻结后 / 翻转赋锚点 |
| 退化判定 | 单图好看就算过 | 节点坐标不变 + 全量严重度表 |
| 范围 | 容易滑向特例参数 | 规则通用、不绑图名 |

## 5. 给后续 Agent 的操作清单（短）

1. 改布局/路由后，**禁止**默认信任 `./target/release/plotgram`；优先 `cargo run -p plotgram-cli`。  
2. 任何「我加了日志却看不到」：先 `ls -l` binary / `touch` 入口 / 清 fingerprint，再怀疑分支条件。  
3. Label / 折点类问题：画出  
   `router 输出 → snap/repulse → sanitize →（是否）resolve/assign`  
   谁最后写结果。  
4. 路由内部 sanitize 保持保守；激进几何清理放在 pipeline 末尾。  
5. 回归至少三件套：节点坐标 diff、label 重叠严重度、相关单元测试；仓库既有失败先 stash 钉死。  
6. 用户要求「全盘提高、不能退化」时：**不做图名特判**；可接受「合法单调台阶暂留」，不可接受「为消 warning 引入穿模」。

## 7. 未收尾项（诚实边界）

- `analytics → control_tower` 一类**合法单调多段台阶**：sanitize 无障碍物信息，强行拉直有穿模风险，本会话按「不退化」保留。  
- 全量 showcase 仍可能残留极少量 label 重叠（严重度已下降）；彻底消除需避让搜索空间/走廊宽度层面的继续投入，而非再加特判。  
- Release 产物陈旧属于工具链痛点，本会话用 `cargo run` 绕过，未改 Cargo profile；若团队频繁踩坑，可另开「强制 relink / 校验 mtime」的工程项。

---

## 8. 总结给人类读者

先前模型**最终能解**，是因为把问题从「这个图画得难看」升级成「管线里哪一步写坏了最终几何」，并用坐标与全量回归约束住改动面。  

中间**一度解不了**，主要是因为：

1. 用陈旧二进制验证，把自己绕进「代码没执行」的假说；  
2. 在局部算法上打转，晚于发现「结果被后一步丢掉 / 启发式死锁」；  
3. 把激进清理放在节点仍可变的阶段，制造假回归，差点导致正确方向被回滚。

这些经验与具体图无关；下次再做布局/路由质量工作时，应默认按第 5 节清单执行。
