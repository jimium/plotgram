## 0. 一句话结论

这次提交的四处改动，本质是**四类后处理缺陷的通用化修复**，而不是「调某个图的参数」。

### 3.2 我相对擅长的部分（可放大的优势）

- **按 AGENTS.md 的硬约束行事**：不做图名特判、HashMap 不驱动迭代顺序、lint 不必 100% 清零——这些我能在改代码时主动遵守。

## 4. GLM5.2 的工作流（针对布局/路由后处理问题）

把上面的优缺点翻译成可执行流程。**任何一步跳过，都对应一个已知的失败模式。**

```text
Step 0  先确认产物可信
        ├─ 不默认信任 ./target/release/plotgram
        ├─ 优先 cargo run -p plotgram-cli -- …
        └─ 「我加了日志却看不到」→ 先怀疑 binary mtime / fingerprint，再怀疑分支

Step 1  把视觉抱怨翻译成坐标命题
        ├─ 渲染 JSON，抽节点 bbox / 边折点 / label center / leader
        ├─ 「label 叠在一起」→ 写成「两 label center 距离 = (x,y)」
        └─ 「边冲过再折回」→ 写成「竖段 x=508，端口 x=498，overshoot=10」
        （没有坐标，后面所有判断都是猜）

Step 2  画管线写时序图（谁最后写结果）
        router step-5 避让 → snap/repulse → sanitize（重建 label?）→ resolve/assign
        ├─ 找出「几何冻结点」在哪一步之后
        └─ 找出「最终输出是谁写的」——若避让被后一步丢弃，先改时序，别改算法

Step 3  构造最小可证伪例
        ├─ 死锁类：候选是否恒等？（cand==curr）
        ├─ 阈值类：调大 2x 是否动？（不动 = 不是阈值问题）
        └─ 时序类：在「最终几何」上手动跑一次目标函数，看是否生效

Step 4  改通用规则，禁止图名特判
        ├─ 优先复用函数已有参数（如 endpoint_map）
        ├─ 优先打分 + 平局回退，而非纯启发式
        └─ 激进几何清理只放管线末尾（merge_overshoot=true 只在几何冻结后）

Step 5  回归三件套（缺一不可）
        ├─ 节点坐标 diff（必须不变，除非本就该动节点）
        ├─ label 重叠严重度（用穿透面积，不只是计数）
        └─ 相关单元测试（既有失败先 stash 钉死，避免混谈）

Step 6  用注释固化「为什么」，防止回滚
        └─ 写清「保守 vs 激进」「为何在此阶段启用」
```

## 8. 错误来源的母题分析

> 「母题」= 把表面不同的具体错误归约到的**原型模式**。每个具体 bug 都是母题在特定场景下的变体。母题分析的价值不在于"归类"，而在于**能预测未来还可能出现哪些同类 bug**——下次看到某个新 bug 时，先认出它属于哪个母题，就能直接复用该母题的防御方法。

本次提交的四类错误 + 复盘里的失败模式，可归约为五个母题。

### 母题一：多写者无最终所有者（写权时序）

- **定义**：同一份数据（label 位置、路径折点、节点坐标）被管线中多个阶段写入，没有明确"谁的写入是最终输出"。后一个写者会无声覆盖前一个写者的结果。
- **本次表现**：router step-5 算完 label 避让 → pipeline 末尾 `sanitize_orthogonal_edges` 按平行边规则**重建全部 label** → 避让结果被丢弃。
- **变体预测**（未来可能出现的同类 bug）：
  - `snap_and_repulse_edges` 移动路径后，又有人重建折点 → snap 结果被覆盖
  - `group_frame` 重排节点后，router 缓存的端点信息过时 → 端口锚定到旧坐标
  - 任何"先算 X，后算 Y，Y 内部又重算 X"的管线结构
- **防御**：为每个字段明确"最终写者"；中间阶段写后，要么被最终阶段显式保留（如 pipeline.rs 末尾再跑一次 label resolve），要么文档化"此阶段结果会被覆盖"。

### 母题二：假设独占的共享资源（独占假设）

- **定义**：代码假设某个资源（端口、锚点、slot、切线坐标）只被当前对象使用，实际被多个对象共享，导致分配冲突。
- **本次表现**：`stub_fix` 翻转端口时硬编码 `frac=0.5`，与同侧已有边的锚点重合 → 入出边共锚。
- **变体预测**：
  - slot 分配假设单边独占某一侧，实际同侧已有多条边
  - label 锚点选择假设路径唯一，实际 shared trunk 上挂了多条边的 label
  - group_frame 假设某条 track 只放本组，实际相邻组已占用该 y-band
- **防御**：凡是"给一个对象分配位置"的逻辑，都要查"该位置是否已被占用"。`deconflict_flip_anchor` 就是这个母题的标准修法：复用 `endpoint_map` 查占用 → 沿切线错开 → clamp 到合法范围。

### 母题三：贪心选择撞上不动点（对称死锁）

- **定义**：基于局部贪心的选择策略（"选最近的""选最小的"），在某些对称构型下选中**恒等变换**（`cand == curr`），无论迭代多少次、阈值调多大都不动。
- **本次表现**：`collapse_micro_jogs` 按"离 curr 最近"选对齐角，overshoot 场景下 `cand_b == curr`，死锁 → Z 折永不消除。
- **变体预测**：
  - 任何"从候选集选最优"的启发式，若候选集含恒等项且打分平局，都可能死锁
  - reroute 选路径时若"当前路径"总在候选集里且打分不差，永远不换
  - label 避让推挤时若"推回原位"总是候选，永远推不动
- **防御**：打分函数必须能区分"维持现状"与"改进"；平局时引入打破对称的偏好（如共线合并分数）；**修死锁要改选择逻辑，不要调阈值**——阈值加大只是把死锁区间扩大，不改变死锁本身。

### 母题四：无群体上下文的个体决策（孤立决策）

- **定义**：单个对象的决策只看自身状态（自己的可见长度、自己的端点几何），不看同类对象的状态，导致视觉歧义或群体冲突。
- **本次表现**：`assign_leader_lines` 只看"自己离路径多远"决定是否挂引线，不感知邻近其他边的 label → 两个不同边的 label 很近时都省了引线，归属歧义。
- **变体预测**：
  - side selection 只看端点 dx/dy 比例，不看其他边已占用哪些侧 → 端口拥堵
  - reroute 只看自己路径的冲突数，不看整体通道负载 → 多条边挤同一通道
  - 单条边 label 避让推挤时只看自己与节点的穿透，不看其他 label 被推到哪 → 推开一个撞到另一个
- **防御**：视觉歧义类问题**必然是群体问题**——"这条边的 label 属于谁"只有在有其他边 label 邻近时才有歧义。决策时引入"邻居状态"作为输入（Pass 2 的 `labels_confusingly_close` 检查就是标准范式）。

### 母题五：验证对象与改动对象错位（验证错位）

- **定义**：你以为在验证改动 X 的效果，实际跑的是旧产物 / 旧逻辑 / 旧缓存，导致"加了日志看不到""改了代码没效果"，进而误判控制流。
- **本次表现**：`target/release/plotgram` 时间戳不更新，脚本跑旧 binary，`eprintln!` 不打印 → 误判"代码没跑到""走了另一条入口"。
- **变体预测**：
  - WASM / 浏览器缓存导致前端跑旧逻辑
  - Cargo fingerprint 命中导致库重编但可执行文件不重链
  - 多入口（CLI vs Studio vs eval）跑的是不同版本
  - 测试跑的是旧 baseline，把既有失败当成自己引入的回归
- **防御**：验证前先确认"产物 mtime > 源码 mtime"；日志是最便宜的探针——加了日志看不到，**先怀疑产物，再怀疑控制流**。这条在 AGENTS.md §5 已固化为硬约束。

| 母题 | 一句话识别 | 一句话防御 |
|------|-----------|-----------|
| 一·多写者无最终所有者 | "我改了 X 但结果没变" | 画写时序图，明确每个字段的最终写者 |
| 二·假设独占的共享资源 | "分配位置时没查占用" | 分配前查 `*_map`，沿切线/法线错开 |
| 三·贪心撞上不动点 | "调阈值没用，候选里有恒等项" | 改打分函数区分现状与改进，平局打破对称 |
| 四·无群体上下文的个体决策 | "只看自己，没看邻居" | 视觉歧义必然是群体问题，加 Pass 2 邻近感知 |
| 五·验证对象错位 | "加了日志看不到" | 先核产物 mtime，再怀疑控制流 |

### 母题的用法

母题不是用来"归类"的，是用来**预测和加速定位**的：

1. **遇到新 bug 时**：先用一句话描述现象，尝试归入某个母题。归不进去说明可能是新母题，值得单独记录。
2. **归入后**：直接复用该母题的防御方法，跳过"从头分析"的环节。例如看到"分配位置类"bug，直接去查有没有 `endpoint_map` 式的占用查询——大概率没有。
3. **写新代码时**：对照五个母题自检——这个字段有多个写者吗？这个资源是独占的吗？这个选择会撞恒等项吗？这个决策需要邻居状态吗？验证产物可信吗？

本次提交的四类错误，没有一个逃出这五个母题。下次做布局/路由工作时的最大风险，不是遇到新母题，而是**在旧母题上重复踩坑**。
