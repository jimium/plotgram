## 1. 提交内容复盘（改了什么、为什么这么改）

|------|------|----------|
| [pipeline.rs](../../crates/plotgram-core/src/layout/pipeline.rs#L216-L242) | 末尾 sanitize 改用 `_ext(..., merge_overshoot=true)`；其后追加一次 `resolve_label_overlaps_with_config` | **几何冻结后才激进**：router 内部 sanitize 保持保守，避免改动反馈进 space-budget 扰动节点；标签避让必须是「最终几何」的最后一步，因为 sanitize 会重建 label、snap/repulse 会动路径 |

| [label_avoidance.rs](../../crates/plotgram-core/src/layout/edge/common/label_avoidance.rs#L319-L395) | `assign_leader_lines` 加 Pass 2：两**不同边**的标签 bbox 间隙 < 16px 且另一轴投影重叠时，强制保留引线 | **消除归属歧义**：原逻辑只看「引线可见长度」，不感知邻近其它边的标签；近距时引线锚回各自路径即可区分「谁属于谁」 |

## 3. GLM5.2 复盘：这类问题我能否独立解出

诚实回答：**能解，但前提是按对的顺序提问**。下面按「卡点风险」从高到低排序。

### 3.1 我容易卡在哪（GLM5.2 的具体弱点）

| 弱点 | 表现 | 对应本次提交的雷区 |
|------|------|------|
| **倾向信 stderr 而非产物** | 我看不到 binary mtime，只能看命令输出；一旦产物陈旧，我会误判「代码没跑到」并开始怀疑控制流 | §3.1 陈旧二进制——这次提交里 pipeline.rs 的注释反复强调「几何冻结后」，如果我在旧 binary 上验证，会看到 sanitize 不生效，进而误以为改错了方向 |
| **局部调参比画时序更快** | GLM5.2 在「改一个阈值/加一个 if」上很顺，但在「先画 router→snap→sanitize→label 的写时序图」上需要刻意慢下来 | §3.2——如果先去调 `MICRO_JOG_LEN` 或 `DEFAULT_LEADER_LINE_MIN_LENGTH`，会完全错过「sanitize 丢弃避让」这个时序 bug |
| **把「视觉更好」当成功** | 我无法实时看渲染结果，只能靠计数/坐标 diff；若不强制对比节点坐标，会把节点重排副作用当成功 | §3.3——`merge_overshoot` 若在 router 内部启用，节点会整体平移，label 指标假回归 |
| **对「已有参数」不够敏感** | 倾向新加参数/改签名，而不是先翻函数已有的入参 | §3.4——`deconflict_flip_anchor` 用的 `endpoint_map` 本就在 `fix_reverse_stub_ports` 签名里；如果我去改 sanitize 末端做几何 nudge，就绕远了 |
| **启发式死锁识别弱** | 倾向「加大阈值/多迭代」，而不是先构造「候选是否恒等」的最小例 | §3.5——`cand==curr` 时无论阈值多大都不动；必须改选择逻辑 |

### 3.2 我相对擅长的部分（可放大的优势）

- **按 AGENTS.md 的硬约束行事**：不做图名特判、HashMap 不驱动迭代顺序、lint 不必 100% 清零——这些我能在改代码时主动遵守。
- **写带分值/打分的通用启发式**：sanitize.rs 的「共线合并分数」就是典型我擅长的模式（打分 + 平局回退），比纯启发式更稳。
- **用注释把「为什么」固化下来**：pipeline.rs / sanitize.rs 这次都加了「几何冻结后才激进」「保守版避免反馈进节点重定位」的注释，这正是防止下次自己（或别的 agent）回滚的护栏。

## 4. GLM5.2 的工作流（针对布局/路由后处理问题）

把上面的优缺点翻译成可执行流程。**任何一步跳过，都对应一个已知的失败模式。**

```text
Step 0  先确认产物可信
        ├─ 不默认信任 ./target/release/plotgram
        ├─ 优先 cargo run -p plotgram-cli -- …
        └─ 「我加了日志却看不到」→ 先怀疑 binary mtime / fingerprint，再怀疑分支

Step 1  把视觉抱怨翻译成坐标命题
        ├─ 渲染 JSON，抽节点 bbox / 边折点 / label center / leader
        ├─ 「label 叠在一起」→ 写成「两 label center 距离 = (x,y)」
        └─ 「边冲过再折回」→ 写成「竖段 x=508，端口 x=498，overshoot=10」
        （没有坐标，后面所有判断都是猜）

Step 2  画管线写时序图（谁最后写结果）
        router step-5 避让 → snap/repulse → sanitize（重建 label?）→ resolve/assign
        ├─ 找出「几何冻结点」在哪一步之后
        └─ 找出「最终输出是谁写的」——若避让被后一步丢弃，先改时序，别改算法

Step 3  构造最小可证伪例
        ├─ 死锁类：候选是否恒等？（cand==curr）
        ├─ 阈值类：调大 2x 是否动？（不动 = 不是阈值问题）
        └─ 时序类：在「最终几何」上手动跑一次目标函数，看是否生效

Step 4  改通用规则，禁止图名特判
        ├─ 优先复用函数已有参数（如 endpoint_map）
        ├─ 优先打分 + 平局回退，而非纯启发式
        └─ 激进几何清理只放管线末尾（merge_overshoot=true 只在几何冻结后）

Step 5  回归三件套（缺一不可）
        ├─ 节点坐标 diff（必须不变，除非本就该动节点）
        ├─ label 重叠严重度（用穿透面积，不只是计数）
        └─ 相关单元测试（既有失败先 stash 钉死，避免混谈）

Step 6  用注释固化「为什么」，防止回滚
        └─ 写清「保守 vs 激进」「为何在此阶段启用」
```

## 5. GLM5.2 自检清单（改布局/路由前过一遍）

- [ ] 我是在 `cargo run` 上验证，还是在旧 binary 上猜？
- [ ] 我能用坐标描述问题吗？还是只有「看起来重叠」？
- [ ] 我画了管线写时序图吗？知道「最终输出是谁写的」吗？
- [ ] 我的改动在「几何冻结点」之后吗？如果在之前，会不会反馈进节点重定位？
- [ ] 我改的是选择逻辑，还是只在调阈值？候选是否恒等？
- [ ] 我复用了函数已有参数吗？还是新加了签名？
- [ ] 我做了节点坐标 diff 吗？还是只看了「视觉更好 / 计数更少」？
- [ ] 我的规则是通用的吗？有没有偷偷塞图名 / 特定 id 判断？
- [ ] 仓库既有的测试失败，我 stash 钉死基线了吗？
- [ ] 我把「为什么这么改」写进注释了吗？

## 7. 诚实边界

- 本文不声称 GLM5.2 能「一次性零退化」解出所有同类问题。`布局与路由改造踩坑复盘` 里提到的「合法单调台阶暂留」「极少量 label 重叠残留」仍然是真实边界，需要避让搜索空间/走廊宽度层面的继续投入。
- 「陈旧 binary」是工具链痛点，本文用「优先 `cargo run`」绕过，未改 Cargo profile；若频繁踩坑，应另开工程项。
- 本文的工作流针对**布局/路由后处理**类问题（时序、死锁、去冲突、几何冻结）。对**新算法设计**（如全新的边路由策略）不一定适用——那需要更多「先写规格、再写实现」的前置工作。
- 本次提交还包含一份 `layout-lint-agent-guidance-2026-07.md` 方案文档（LintAdvice 提案），与本复盘主题不同，不在本文范围内。
