## 0. 一句话结论

**这套管线的冗余早已被前人抽干；剩下的复杂度绝大多数是「本质异构」，不是「可合并的重复」。**
凡是「看起来重复、实则各自承重」的 pass，删除都会在门禁上现形。原方案「合并 ~5,000 行」的目标不成立——
实际可安全精简的只有默认关闭的实验性代码与纯诊断模块（第一阶段 ~1,144 行），其余多为**减阶段/固化认知**而非减行数。

---

## 1. 核心判据：什么才算「可安全删除」

一个 pass 可被安全删除，必须**同时**满足：

1. **有下游最终写者覆盖**：它写的几何/label 会被管线更靠后的步骤（通常是 D 期 pipeline 末尾）重做并覆盖。
2. **不参与 C 期反馈闭环**：它的改动不会经 `space-budget` / `refine` 反馈去**移动节点**。

只满足 1 不满足 2 的 pass **不是纯冗余**——见 §2 实验 B。
判据落地方式：删除后跑全量门禁，`node_fp` 任一变化即证明它承重（product 硬 FAIL）。

### 2.1 `resolve_exact_stub_occupancy_post_route`（一阶段）
- 原以为是可删的后处理，实测它在 architecture D 末保住 `product.cloud-native` 的紧密重叠严重度。
- **教训**：名字里带 `post_route` / `exact` 不代表「可选优化」；它可能是唯一守住某图 node_fp 的最终写者。

### 2.2 C 期 dock 分离（实验 B）——最重要的一条
- A（删 run.rs C 末 dock_sep）PASS、C（删 phase_lane C 期 min_gap）PASS，唯独 **B（删 phase_lane C 期 dock_sep）FAIL**。
- 原因：**C 期节点尚未冻结**，dock 分离改动的边几何会经反馈**移动节点**，`user-auth` 的 node_fp 因此改变。
- 而 A/C 之所以能删：A 的调用有 D 末最终写者覆盖；C 是 2 点直连正反向对，不触发节点反馈。
- **教训**：C 期（未冻结）与 D 期（已冻结）的同名分离 pass **不是同一件事**。C 期分离承重，删不得；只有「D 期已覆盖且不参与 C 期后续反馈」的调用才可删。

### 2.3 `SeparationEngine`（否决建引擎）
- 进入实施前读了 B 类各 pass 的真实 shift/validate 原语，发现**原语早已共享**，各 pass 的差异是**作用域/时机异构**（interior 段 vs 全局、C 期 vs D 期），不是可抽取的重复。
- 强行建引擎只会新增一层抽象去包裹本就不同的东西，**增加复杂度而非减少**。
- **教训**：合并的前提是「重复」，不是「相似」。相似但各自承重的东西，抽象只会更难维护。

### 2.4 S4 监控走廊（3.2.3）
- 门控 `s4_monitor_corridor = profile.semantic_merge && diagram.groups.is_empty()` + 监控枢纽（某目标 ≥3 条被动 `-->` 入边）。
- 24 样本中**仅 `typical-microservice-architecture` 触发**（触发率极低），一度被判为「低价值可删」。
- 但删除后该图 tight_sev **1048 → 3044（~3×）**：监控枢纽的密集被动入边失去外环疏解 → 紧密重叠激增。
- **教训**：**触发率低 ≠ 可删**。低触发的特化往往正是为「普通规则搞不定的少数难图」兜底；删掉它，难图立刻裸奔。要删，得先有**通用替代**（非图名特判）在该图上不劣于原指标（§7 算法级重写范畴）。

### 2.5 Scoring 惩罚项合并（二轮 C.1，SKIP）
- 评估 `crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/scoring.rs`（1240 行）的 10+ 惩罚因子，计划合并 `NODE_NEAR_MISS_PENALTY` + `GROUP_NEAR_MISS_PENALTY` 入 `obstacle_penalty` 距离衰减、合并 `channel_load_penalty` + `corridor_overflow_penalty` + `corridor_misalignment_penalty` 入 `overlap_penalty`。
- 评估发现 `obstacle_penalty` 是路由候选打分**核心**（直接驱动路径选择），所有 `*_NEAR_MISS_PENALTY` / `*_CROSSING_PENALTY` / `*_PIERCE_DEPTH_WEIGHT` 等都活跃在路径选择权重计算中。keep-list 6 项（`protected_trunk_crossing_penalty` / `outer_ring_path_bonus` / `NODE_CROSSING_PENALTY` / `NODE_PIERCE_DEPTH_WEIGHT` / `EDGE_OVERLAP_PENALTY` / `GROUP_TRANSIT_PENALTY`）已锁定不能动；剩余可合并项任何权重数值变化都必影响路径选择。
- 基于二轮 B.2 教训「几何等价 ≠ perf 等价」（5 个 arch 样本 node_fp 字节级一致但 cloud-native median_ms 退化 +18.54%），即使权重数值不变的"提取公共衰减函数"也可能扰动 inline / cache 行为 → 重蹈 B.2 覆辙。
- 任务说明已预案：「如果方案 B 也导致门禁 FAIL，说明 scoring 任何改动都会扰动路径选择，C.1 整体放弃，记 keep-list」。直接采用此预案 SKIP，避免实测代价。
- **教训**：**核心打分函数无安全保守简化空间**。任何权重调整、函数提取、内联重构都可能扰动编译器优化决策与 CPU cache 行为，对大图 perf 影响不可预测。要简化 scoring，需走算法级重写（spec §7 创新模式通道）并接受帕累托评判，而非日常棘轮。

### 2.6 `demand/grid.rs` + `demand/pierce.rs` 移除（二轮 C.2，SKIP）
- 评估删除 `crates/plotgram-core/src/layout/demand/grid.rs`（211 行）+ `demand/pierce.rs`（176 行），任务说明预案「前置验证：Grep 调用方，若仅诊断/边序微调且 scoring `pierce_depth` 可兜底则删；若活跃消费者则跳过」。
- Grep 发现 4 个文件引用：`demand/grid.rs` / `demand/pierce.rs` / `demand/mod.rs` / `demand/features.rs`。其中 `demand/features.rs:11-12` 直接 `use` `compute_grid_demand` / `edge_grid_overflows` / `obstacle_hits_for_edge`，并在 `features.rs:195-196,254` 调用它们产出 `EdgeFeatures`。
- `EdgeFeatures` 被两处活跃消费：
  - `crates/plotgram-core/src/layout/edge/edge_routing_orthogonal/run.rs:62-69`：边序注入（默认开启，`PLOTGRAM_EDGE_ORDER_SCORE` 默认 on），影响 `score_edges` 输入。
  - `crates/plotgram-core/src/layout/space_budget.rs:267-278`：`enrich_from_edge_features` 改 `pair_gaps` 几何（默认开启，`PLOTGRAM_EDGE_PRESSURE_BUDGET` 默认 on）。
- 这是**活跃生产链路**（非诊断/边序微调），任务说明的"前置验证"判据生效 → SKIP 而非强行删除导致回归。
- **教训**：**看似诊断模块实为活跃生产链路**。`demand/` 目录名 + `dump.rs` 已删（一阶段）让人觉得整个目录是诊断专用，但 `grid.rs` / `pierce.rs` 产出的 `EdgeFeatures` 已被默认开启的边序注入 + space_budget 几何改写消费。删之前必须验证：`(a)` 调用方是否仅诊断/边序微调；`(b)` 是否有默认开启的下游消费几何。任一为真即判 keep-list。

### 2.7 D.1 spline_fallback 简化保守变体（二轮 D.1，PASS — 保守分支须保留）

- Tier D D.1 删除 `crates/plotgram-core/src/layout/refine/spline_fallback.rs` 的 Bezier + 多段样条密采样降级路径（手册 §3.5 ★ 红线）。
- **激进变体 FAIL**：删除 spline/bezier + 非正交原图（State / Er / Mindmap）也改走 dogleg → `product.saas-schema.pgm: tight_sev 0 → 3436.747`（ER 用 spline router，紧密成对边原走平滑曲线；dogleg 正交折线与其他边/节点正交线段重合，引入大量共线严重度）。
- **保守变体 PASS**：删除 spline/bezier + 非正交原图直接保留原边 + degraded 标注（`spline_fallback_removed:bezier_or_multi_segment_spline`）→ 24 样例全持平，5 个 arch 样本 node_fp 字节级一致。
- **激进变体虽修复穿组**（lint_err 2→0）**但引入共线严重度**（tight_sev 0→3436.747）→ 按 §7 创新模式帕累托评判仍超阈值，且是几何破坏非 perf 噪声。
- **教训**：
  1. **spline/bezier 平滑曲线对共线严重度的天然避免**：spline/bezier 输出是密采样点或 Bezier 曲线，与正交边/节点框天然不共线；dogleg 是正交折线，与正交边/节点框的正交线段重合时引入共线严重度。
  2. **dogleg 在正交原图（Flowchart / Architecture router 输出）上是等价替换**：原边已是正交折线，dogleg 也是正交折线，几何等价 → node_fp 不变。
  3. **dogleg 在非正交原图（State / Er / Mindmap router 输出）上是几何破坏**：原边是 spline/circular/organic 平滑曲线，dogleg 是正交折线，几何完全不同 → tight_sev / node_fp 退化。
- **判据**：删 spline/bezier 降级路径前，必须确认调用方的原边几何类型——
  - 若原边正交（Flowchart / Architecture router 输出）：可改 dogleg（等价替换）
  - 若原边非正交（State / Er / Mindmap router 输出）：**不能改 dogleg**，只能保留原边 + degraded 标注
- **代码位置**：`crates/plotgram-core/src/layout/refine/spline_fallback.rs:113-130` 的 `use_orthogonal_fallback` 判定 + 保守分支；`mark_degraded` helper 复用 `RouteAnnotationSet.degraded` 字段（与 `recheck_lint_pierce_post_freeze` 同语义）。

## 4. 方法论：为什么这些结论可信

这些结论之所以站得住，靠的不是观感，而是一套可复现的实验纪律（AGENTS.md §4/§5）：

1. **每步都有 before 基线**：改动前 `snapshot.sh --tag xxx-before`，与上一稳定点校验零漂移。
2. **单步单变量**：一次只删一个 pass，避免多改混谈导致归因失败（A/B/C 分别独立跑门禁才分出承重者）。
3. **门禁即判据**：`compare.sh` 的 product 硬门禁（node_fp / exact_sev / tight_sev 任一退化即 FAIL）是唯一裁判，不信单图观感。
4. **FAIL 即回滚，且回滚要验证**：回滚后再 `compare` vs before，必须**零漂移**才算干净——否则回滚本身引入了新漂移。
5. **区分「本次改动」与「既有基线失败」**：19 项单测失败经 `git stash` 核实早于本工作，不与本次改动混谈。

### 4.1 回滚踩坑：工作树混有未提交成果时不能 `git restore`
- 3.2.3 回滚时工作树混着未提交的 Phase1/2 成果，整体 `git restore` 会连带丢失前两阶段。
- 正确做法：按文件 diff 组成分类——
  - **纯本次改动文件**（numstat 与本次删除量吻合 → HEAD == before）：`git checkout HEAD -- file` 精确还原；
  - **混合文件**（含更早阶段改动，如 `port_slot.rs` 的 Phase1 port_pressure、`refine.rs` 的 Phase2 min_gap）：**手动只逆向本次那部分**，保留更早成果。
- **教训**：回滚前先 `git diff --numstat` 看清每个文件是「纯本次」还是「混合」，不要一把梭。

## 5. 给后来者的三条硬规矩

1. **先证冗余，再删**：满足 §1 两条判据才动手；不确定就先删一个跑门禁，看 node_fp。
2. **低触发不是删的理由**：低触发特化多为难图兜底，删前必须有通用替代且不劣化（§2.4）。
3. **合并 ≠ 精简**：相似但异构的 pass 强行抽引擎会更复杂；真正的收益常是「减阶段 + 固化认知」，不是减行数（§2.3）。
