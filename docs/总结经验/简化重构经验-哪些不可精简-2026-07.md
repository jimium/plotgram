## 0. 一句话结论

**这套管线的冗余早已被前人抽干；剩下的复杂度绝大多数是「本质异构」，不是「可合并的重复」。**
凡是「看起来重复、实则各自承重」的 pass，删除都会在门禁上现形。原方案「合并 ~5,000 行」的目标不成立——
实际可安全精简的只有默认关闭的实验性代码与纯诊断模块（第一阶段 ~1,144 行），其余多为**减阶段/固化认知**而非减行数。

---

## 1. 核心判据：什么才算「可安全删除」

一个 pass 可被安全删除，必须**同时**满足：

1. **有下游最终写者覆盖**：它写的几何/label 会被管线更靠后的步骤（通常是 D 期 pipeline 末尾）重做并覆盖。
2. **不参与 C 期反馈闭环**：它的改动不会经 `space-budget` / `refine` 反馈去**移动节点**。

只满足 1 不满足 2 的 pass **不是纯冗余**——见 §2 实验 B。
判据落地方式：删除后跑全量门禁，`node_fp` 任一变化即证明它承重（product 硬 FAIL）。

### 2.1 `resolve_exact_stub_occupancy_post_route`（一阶段）
- 原以为是可删的后处理，实测它在 architecture D 末保住 `product.cloud-native` 的紧密重叠严重度。
- **教训**：名字里带 `post_route` / `exact` 不代表「可选优化」；它可能是唯一守住某图 node_fp 的最终写者。

### 2.2 C 期 dock 分离（实验 B）——最重要的一条
- A（删 run.rs C 末 dock_sep）PASS、C（删 phase_lane C 期 min_gap）PASS，唯独 **B（删 phase_lane C 期 dock_sep）FAIL**。
- 原因：**C 期节点尚未冻结**，dock 分离改动的边几何会经反馈**移动节点**，`user-auth` 的 node_fp 因此改变。
- 而 A/C 之所以能删：A 的调用有 D 末最终写者覆盖；C 是 2 点直连正反向对，不触发节点反馈。
- **教训**：C 期（未冻结）与 D 期（已冻结）的同名分离 pass **不是同一件事**。C 期分离承重，删不得；只有「D 期已覆盖且不参与 C 期后续反馈」的调用才可删。

### 2.3 `SeparationEngine`（否决建引擎）
- 进入实施前读了 B 类各 pass 的真实 shift/validate 原语，发现**原语早已共享**，各 pass 的差异是**作用域/时机异构**（interior 段 vs 全局、C 期 vs D 期），不是可抽取的重复。
- 强行建引擎只会新增一层抽象去包裹本就不同的东西，**增加复杂度而非减少**。
- **教训**：合并的前提是「重复」，不是「相似」。相似但各自承重的东西，抽象只会更难维护。

### 2.4 S4 监控走廊（3.2.3）
- 门控 `s4_monitor_corridor = profile.semantic_merge && diagram.groups.is_empty()` + 监控枢纽（某目标 ≥3 条被动 `-->` 入边）。
- 24 样本中**仅 `typical-microservice-architecture` 触发**（触发率极低），一度被判为「低价值可删」。
- 但删除后该图 tight_sev **1048 → 3044（~3×）**：监控枢纽的密集被动入边失去外环疏解 → 紧密重叠激增。
- **教训**：**触发率低 ≠ 可删**。低触发的特化往往正是为「普通规则搞不定的少数难图」兜底；删掉它，难图立刻裸奔。要删，得先有**通用替代**（非图名特判）在该图上不劣于原指标（§7 算法级重写范畴）。

## 4. 方法论：为什么这些结论可信

这些结论之所以站得住，靠的不是观感，而是一套可复现的实验纪律（AGENTS.md §4/§5）：

1. **每步都有 before 基线**：改动前 `snapshot.sh --tag xxx-before`，与上一稳定点校验零漂移。
2. **单步单变量**：一次只删一个 pass，避免多改混谈导致归因失败（A/B/C 分别独立跑门禁才分出承重者）。
3. **门禁即判据**：`compare.sh` 的 product 硬门禁（node_fp / exact_sev / tight_sev 任一退化即 FAIL）是唯一裁判，不信单图观感。
4. **FAIL 即回滚，且回滚要验证**：回滚后再 `compare` vs before，必须**零漂移**才算干净——否则回滚本身引入了新漂移。
5. **区分「本次改动」与「既有基线失败」**：19 项单测失败经 `git stash` 核实早于本工作，不与本次改动混谈。

### 4.1 回滚踩坑：工作树混有未提交成果时不能 `git restore`
- 3.2.3 回滚时工作树混着未提交的 Phase1/2 成果，整体 `git restore` 会连带丢失前两阶段。
- 正确做法：按文件 diff 组成分类——
  - **纯本次改动文件**（numstat 与本次删除量吻合 → HEAD == before）：`git checkout HEAD -- file` 精确还原；
  - **混合文件**（含更早阶段改动，如 `port_slot.rs` 的 Phase1 port_pressure、`refine.rs` 的 Phase2 min_gap）：**手动只逆向本次那部分**，保留更早成果。
- **教训**：回滚前先 `git diff --numstat` 看清每个文件是「纯本次」还是「混合」，不要一把梭。

## 5. 给后来者的三条硬规矩

1. **先证冗余，再删**：满足 §1 两条判据才动手；不确定就先删一个跑门禁，看 node_fp。
2. **低触发不是删的理由**：低触发特化多为难图兜底，删前必须有通用替代且不劣化（§2.4）。
3. **合并 ≠ 精简**：相似但异构的 pass 强行抽引擎会更复杂；真正的收益常是「减阶段 + 固化认知」，不是减行数（§2.3）。
