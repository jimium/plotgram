channel 模块图解

crates/plotgram-core/src/layout/atlas/channel/  · Atlas 三相架构 · 组合相 I.6 · 2026-07
channel 回答的唯一问题：
「在没有坐标的世界里，一条边应该走哪几条轨道？」 路径不是一串像素点，而是一个 track 序列。坐标由度量相（相 II）事后一次性求出，
所以路径永远不会因为坐标变动而失效 —— repair loop 从根上失去存在理由。

1为什么需要它：旧世界的死循环

今天的 layout::routing 是「几何路由」：先有临时坐标，才能算可见图、才能走线。坐标一变，路径作废。

旧：几何路由路径 = 像素点序列
路径绑定具体坐标：任何后续空间调整都可能让它作废。
新：通道图选路路径 = track 序列
节点再怎么被撑开，「先走 cross₁ 再转 main₁」这句话依然成立。
几何可见图（kernel/route::ResourceGraph）通道图（ChannelGraph）
顶点坐标点（障碍角点投影，带 Point）轨道（TrackId，无坐标）
边轴向可见段（依赖临时坐标）link（轨道交口）/ gate（组闸口）
规模O(V²)，需规模开关 ovg_enabled ≤ 50O(层数 × 通道数)，小约两个数量级
坐标变动路径失效 → repair loop不受影响（无坐标可失效）

2一个比喻：先选街道，再修马路

把图想成一座规划中的城市 —— 关键是：这座城市还没动工，只有规划图。

城市channel 概念说明
街道（还没修，只在规划图上）Track（Cross 层间缝 / Main 纵向走廊）没有宽度、没有坐标，只有「第几条」（gap 索引）和走向
十字路口link只有横竖异向的街道才有交口 —— 每个转弯 = 一次 link 转移
封闭小区的大门Gate（边界段容量池）进出小区（组）只能走大门；翻墙的路在地图上根本不存在
门牌 / 停车位PortSlot（node, side, slot_index）边从节点哪一侧、第几个槽位出入
某条街上跑了几辆车lane_demand（输出）选路时不限流；事后告诉修路队「这条街要修 N 车道」
导航偏好LexCost（词典序：折点 > 长度）先比谁转弯少，再比谁路程短

旧管线的顺序是「先修好马路（定坐标）→ 再让车找路（几何路由）→ 发现路不够宽 → 拆了重修」。 channel 把顺序倒过来：先在规划图上给所有车选好街道序列，再按实际车流量一次性决定每条马路修多宽。

3世界长什么样：Substrate（基底）

输入只有三样无坐标信息：节点的 (rank, order) 槽位、组树、边列表（ChannelBlueprint）。derive_substrate 据此铺出轨道网格。

6 个节点只声明了「第几层、层内第几个」。derive 自动在每条层间铺 Cross 缝、每条列间铺 Main 走廊 （含包围盒外圈各一条），异向轨道相交处生成 link。整张图没有一个像素坐标。

4例子一：一条边怎么选路（词典序代价）

边 A → F。搜索器是词典序 Dijkstra：先比 Q3 折点数（= link 转移次数，拓扑事实），再比 Q4 长度（跨度权重和）。

候选track 序列Q3 折点（link 数）Q4 长度词典序判定
P1[cross₁, main₂]1短胜折点更少，Q4 不用比
P2[main₀, cross₂, main₂]2长Q3 已输
注意：「折点 = link 转移」是构造保证的 —— link 只允许 Main × Cross 异向轨道相连（平行轨道无交点，ParallelLink 拒绝）， 所以折点计数是拓扑事实，不需要任何几何测量。返回值 RouteOutcome 就是这串 track 序列 + gate 序列 + LexCost。

5例子二：组与 gate —— 穿组「不可表达」

旧世界里「边穿组」是路由完再检测、再修补的缺陷。channel 里它连发生的资格都没有：跨 scope 的轨道 link 在构建期就被拒绝（CrossScopeConnection），跨组转移只能经 Gate。

gate 是边界段容量池：覆盖组边界的一段，服务多对（内轨道, 外轨道），穿越的每条边占 1 单位容量。 满容后该 gate 的全部转移从图上消失 —— 后来的边「看不见门」，只能绕道或返回 Infeasible。 生产路径容量是自适应的：max(下限, 组边界度数)，探针实测三集 100% 通过。

6例子三：lane 数是「输出」，不是「上限」

这是删除 SpaceBudget 单向预告回环的核心机制（B1 不变量）：轨道占用无上限，N 条边挤同一轨道全部成功，需求 N 作为 Demand 交给度量相。

相 I 选路时3 条边挤 cross₁，没有一条被拒
占用账本只记账：Occupancy::lane_demand(cross₁) = 3。
相 II 度量相按 demand 一次性撑开通道
先有需求，后有空间 —— 与旧世界「先猜预算、不够再返工」方向相反。
与之相对，只有两种「硬」容量（满了就是满了，可行性信号必须诚实）：
  • gate 容量池 —— 组边界段的物理长度有限（= 边界段长 / 最小间距），满容后转移从图上消失；
  • 端口侧容量 —— 同一挂接点可容纳的边数上限（capacity=0 视为不限），满容后该端点此刻不可布。
无路可走时返回 SolverStatus::Infeasible + 空路径。本模型无坐标，连伪造一条「直线兜底」都做不到 —— 这正是可行率探针需要的诚实信号。

7例子四：边从节点哪一侧出发？—— PortSlot 与候选端点（24 号文）

「选哪几条轨道」之前还有半个问题：「从节点的哪一侧、哪个槽位接进轨道网」。channel 用 PortSlot 回答，且支持把「候选侧」交给搜索器一起选。

四侧语义（无几何、与基底轴对齐）
每侧宿主轨道由 resolve_host_track 纯函数解析（上表四条规则）。同侧多条边靠 slot_index 区分 —— (node, side, slot_index) 全局唯一（P-inv-2）， 平行边从「隐式覆盖」变成「显式建模」。
候选端点选路：route_candidates
满容端口直接跳过；全部不可行 → Ok(infeasible()) 不伪造路径；空候选 → Err(EmptyCandidates)。 便利入口 route_node_sides(a, [下,右], b, [上,左], …) 按「节点 + 侧」查槽位后转此函数。
边界 channel 只负责「给定端点（或候选端点）→ track 序列」。 「到底该选哪一侧」的全局决策（反馈边启发、平行边全局求解等）属相 I.5，落点在 atlas/port / Plan 装配层 —— channel 不读 Diagram、无图名分支、零几何。

8例子五：合流是拓扑事实，不是几何巧合

今天 semantic_trunk_merge 要在渲染坐标上「找共线段」来猜测哪些边该合并主干。channel 里合流有精确定义：≥2 条边共享 track 序列后缀 = bundle。

detect_bundles 在反向后缀 trie 上找共享后缀。合流成为可以证明的拓扑事实： 两条边在 track 语言里字面上写了同一个结尾。落笔相（相 III）据此画主干合并，不再需要几何共线检测。

11它刻意不回答的问题

Q：这条边最终画在哪些像素上？
不回答。折点展开、坐标落地是落笔相（相 III / Ink）的职责。channel 里没有 Point、没有 Rect、没有一个像素。
Q：多条边之间怎么排布最好看（交叉最少 / 对称）？
不回答。Q2/Q5/Q6 是跨边全局量，属上层全局协调（有界块坐标下降，I.7）。本层单边只算折点与长度。
Q：边该从节点哪一侧出发？
半回答。channel 提供机制（PortSlot 四侧 + 候选端点选路），但「选侧」的全局决策是相 I.5（atlas/port）的事。
Q：track 上挤了 N 条边，通道要多宽？
不回答，只上报。lane_demand 输出裸计数，由度量相换算成实际宽度。
Q：什么时候接生产管线？
现在是纯旁路（孵化中），生产仍走 layout::routing；接线时机是 23 号文 Stage 4（对拍 → 切换 → 删补救），回滚 = 删目录。
